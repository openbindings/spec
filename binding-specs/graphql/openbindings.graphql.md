**[convention]** Every normative paragraph and normative table row carries one visible provenance label. An `incorporated` rule is one the cited source states, and the citation names that source, whether an incorporated authority or the OpenBindings Core; the remaining five are this specification's own explicitly classified bridge. A `convention` is a choice this specification makes where no authority speaks, and it states why neither an incorporated authority, nor preservation of an authority's permitted set, nor a named configuration point, nor a refusal or exclusion answered. A `limit` states a boundary of this specification's coverage that is neither a defect nor a deferral.

## 2. Scope and incorporated authorities

**[convention]** This binding specification defines how GraphQL executable documents and schemas govern OpenBindings sources against a live GraphQL service: which sources are accepted and when loading refuses, how operation targets are addressed and synthesized, what an invocation's inputs and outputs mean, and which wire mechanics the incorporated transports fix. The scope is this specification's own because Core states no scope for a family beyond OBI-B-02's floor.

**[pin]** This specification incorporates exactly version **0.2.0** of the [OpenBindings Specification](../../openbindings.md) as its Core authority. Throughout this document, **Core** means that exact version; no other Core version is incorporated.

**[convention]** This specification accepts exactly three editions of the GraphQL Specification: **September 2025**, **October 2021**, and **June 2018**. Section numbers in this document cite the September 2025 edition unless another edition is named. No GraphQL artifact declares its edition, so acceptance is not an artifact gate: the three editions are the introspection shapes a live service may present or a pinned result may carry (§3.3), and every carried document and schema is read under the governing text below. The accepted set is this specification's own because no artifact declares an edition and no authority states which editions a live service may speak: October 2021 and June 2018 are accepted because live services implementing them refuse the September 2025 introspection query and the program's survey observed such services, not because any rule reads them differently.

**[exclusion]** Editions before June 2018 are excluded: no live service of an earlier introspection shape was observed, and the reopen trigger is a real cohort of live services whose introspection refuses the June 2018 base selection; a later edition than September 2025 is a new identifier under §1, not a reopening.

**[pin]** Each accepted edition is incorporated as the source tree of the `graphql/graphql-spec` repository at the commit its release tag names: September 2025 at commit `89d93ebbe05db06787646d76a696ead8de117b2b`, October 2021 at commit `51337a9b820e296fa7d03ae77d534cb4b247c201`, and June 2018 at commit `cdf792cf3b21584cc65b353d7f5eb90e4116f707`; a tag is a movable pointer and the commit is the pin, the losing reading being the rendered pages at `spec.graphql.org`, which are renderings of these trees and not the trees.

**[pin]** For every rule in this specification the governing GraphQL text is the September 2025 edition, with one stated exception: the six introspection positions that October 2021 and September 2025 added or first required (§3.3) are read, when absent from or null in a pinned introspection result or unobserved on a live service, under the earlier edition that lacks them. This pin is between two readings the editions leave open: govern every source under the newest accepted edition, or govern each source under the edition its service is discovered to speak. The first is pinned because one identifier carries one meaning (Core OBI-B-01), because the three editions agree on every wire correspondence this specification defines, and because no artifact declares its edition, so the losing reading would make the same document mean different things under one identifier depending on a live probe. The observable consequences of the pin are stated as limits: the fourteen places where September 2025 validates more strictly than an earlier edition (§5), and the September 2025 grammar an older service refuses with a request error that §8's classification already carries.

**[convention]** The GraphQL over HTTP draft is incorporated as the transport for queries, mutations, and live introspection (§8), and for the request of the graphql-sse lane, which that protocol defers to it; the graphql-ws protocol and the graphql-sse protocol are incorporated as the two subscription transports (§9). The transports are this specification's choice because the GraphQL specification defines no transport and states no rule for carrying a request over HTTP or a socket.

**[pin]** Those three are incorporated immutably at exact commits: the [GraphQL over HTTP draft](https://github.com/graphql/graphql-over-http/blob/d746195047ac4ae5c4bb11042b4941e6631726e8/spec/GraphQLOverHTTP.md) at commit `d746195047ac4ae5c4bb11042b4941e6631726e8` of `graphql/graphql-over-http`, the [graphql-ws protocol](https://github.com/enisdenjo/graphql-ws/blob/839ca7d652004513a063dd44e9bcfe7a3301f6f0/PROTOCOL.md) at commit `839ca7d652004513a063dd44e9bcfe7a3301f6f0` of `enisdenjo/graphql-ws`, and the [graphql-sse protocol](https://github.com/enisdenjo/graphql-sse/blob/0e899300dca583cd5aa5a2fa1d4f15d6e9cafb0e/PROTOCOL.md) at commit `0e899300dca583cd5aa5a2fa1d4f15d6e9cafb0e` of `enisdenjo/graphql-sse`. A later commit is a different authority and reopens nothing by itself; the losing reading, each repository's moving default branch, is disclosed.

**[convention]** [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) governs the HTTP semantics the over-HTTP draft does not restate, [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112) the HTTP/1.1 message framing fields §8 reserves, [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) the JSON texts on every lane, [RFC 6265](https://httpwg.org/specs/rfc6265.html) the cookie contributions of §8, the [WHATWG URL Standard review draft of 18 August 2026](https://url.spec.whatwg.org/review-drafts/2026-08/) the `application/x-www-form-urlencoded` serialization of §8's GET lane, [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455) the WebSocket handshake and closure of §9's graphql-ws lane, and the [W3C Server-Sent Events Recommendation of 3 February 2015](https://www.w3.org/TR/2015/REC-eventsource-20150203/) the event-stream format of §9's graphql-sse lane. ## 3. Source carriage and refusal architecture

### 3.1 Accepted representations

**[convention]** This family is **service-addressed**: `location` names a live GraphQL HTTP endpoint, and `content` carries the executable document that denotes the source's operations together with, optionally, the schema those operations are validated and typed against and the endpoint on which subscriptions are served. `content` is REQUIRED (§4); `location` is REQUIRED (§4). No other representation is accepted, because a GraphQL service is addressed by its endpoint and no artifact form names one.

**[convention]** `content` MUST be a JSON object with exactly these members and no other, the set being closed because Core carries one `content` value and a closed set is what makes gate 2 decidable; the members exist because neither artifact alone can bind an operation, as the paragraph after the list states:

- `document` (REQUIRED, string): the source text of one executable GraphQL document under the governing edition's grammar (§2 of that edition). The JSON string's code points are the document's `SourceCharacter` sequence: no transport-encoding question arises because JSON carries code points, and a U+FEFF between tokens is ignored exactly as §2.1 of the governing edition states, while one inside a token is whatever §2's grammar makes it there, a string character inside a string value and otherwise a parse failure at gate 3. A JSON string RFC 8259 admits but that is not a sequence of Unicode scalar values, one carrying an unpaired surrogate, is not a `SourceCharacter` sequence, because §2.1 defines `SourceCharacter` as a Unicode scalar value, and fails gate 3 (or gate 4 for `schema`). One document per source; documents share fragments internally, which is why the unit of carriage is the document and not the operation.
- `schema` (OPTIONAL, string or object): when a string, the source text of a `TypeSystemExtensionDocument` under §3.1 of the governing edition, the production that admits type-system definitions and extensions alike, read as `SourceCharacter` code points exactly as `document` is; when an object, the execution result of an introspection query with an object at `data.__schema` and no `errors` entry. Discrimination between the two is by JSON type. When present, `schema` is the interpreted schema and displaces live introspection (§3.3, §4); when absent, the processor introspects `location` under §3.3.
- `subscriptions` (OPTIONAL, object): exactly `{"transport": <"graphql-ws" | "graphql-sse">, "location": <absolute URI>}`, naming the endpoint and protocol on which the document's subscription operations are served. `location` MUST be an absolute URI (§4's definition) whose scheme is `ws` or `wss` when `transport` is `graphql-ws` and `http` or `https` when it is `graphql-sse`; any other pairing refuses at load (§3.2). The member is OPTIONAL in the content shape and its absence is never a load gate: when it is absent and the document contains a subscription operation, every subscription operation definition in the document is accounted `invalid` for want of a target, its selector resolves because the definition is addressable, its invocation refuses before dispatch, and queries and mutations are unaffected (§9). No default is derived, because a derived endpoint would be wrong for every deployment whose realtime endpoint differs from `location` in host or path, and would fail only at first connection rather than at load.

**[convention]** The three-member envelope is this specification's own: GraphQL has two artifacts, an executable document and a schema, and Core carries one `content` value, and neither artifact alone can bind an operation, since a document without a schema cannot be validated or typed and a schema without a document denotes no operation. The rejected alternatives were a root-field target with a derived selection (it authors wire behaviour no authority states), a selection set supplied by the caller (the output ceases to be a contract), and an introspection-only `content` (it cannot carry the executable document and refuses the normative type-system language).

**[incorporated]** Both member syntaxes are the authority's: the executable-document grammar is §2 of the governing edition, the type-system language is §3, and the introspection result shape is §4.2, whose listing defines the `__Schema`, `__Type`, `__Field`, `__InputValue`, `__EnumValue`, and `__Directive` types this specification consumes.

**[incorporated]** `subscriptions` lives in the carried content and not in configuration because it is target identity: Core [OBI-D-13](../../openbindings.md#102-document-rules) requires the information needed to identify a binding's target to be in the binding and its source alone, so no configuration point may supply or replace it (§11.1).

### 3.2 Closed load gates and confined defects

**[convention]** Source loading, target addressability, synthesis accounting, and invocation outcome are independent axes. A result on one axis changes another only where a rule in this document states that propagation explicitly, because no authority couples them and an implicit coupling would let a defect on one axis change an outcome on another silently.

**[convention]** A source **refuses at load** only at §3.2's closed gates. After those gates, a source **refuses as a source**, at resolution, only when no addressable target remains. A source-level **exclusion** instead declines an upstream-valid feature under a stated coverage limit; it is not a defect, and this revision declares none at source scope. This architecture is this specification's own, because no incorporated authority defines source loading, and it is stated in the three parts every project binding specification uses, closed load gates, one derived source refusal, and source-scope exclusions, so that a reader of a sibling can predict it.

**[convention]** An **addressable target** is an operation definition in the parsed document that a conformant `selector` can reach: a named operation definition whose name no other operation definition in the document shares, or the lone operation definition of the document, which may be anonymous. An operation definition that is anonymous while not alone, or that shares its name with another, occupies no addressable position. A defect at an addressable target or below does not erase its addressability: a `selector` naming an addressable target resolves even when that target is accounted `invalid` or `excluded`, and invocation then refuses before dispatch; a selector reaching no addressable target does not resolve and invocation refuses at resolution (§5). Addressability is defined this way because §6.1 of the governing edition resolves an operation by its name or as the document's sole operation and no authority defines any other way to reach one.

**[convention]** Synthesis accounts each operation definition as **represented** when an emitted operation and binding preserve the operation's meaning; **invalid** when the owning definition is upstream-invalid or this specification's own rules make it so; **excluded** when this specification removes an upstream-valid unit under a stated exclusion; **lossy** when an emitted operation's contract cannot state part of the source's meaning; or **implementation-unsupported** when this specification defines a behaviour an implementation does not implement. Where an operation definition qualifies for more than one, the first in the order `invalid`, `excluded`, `implementation-unsupported`, `lossy`, `represented` is its disposition. A **projection** entry records a schema-fidelity concern at one position of a represented or lossy operation (a `lossy` disposition is itself recorded by such an entry), named as the next paragraph states, without being a disposition. These spellings are normative within this specification and do not depend on any interface-synthesizer contract (§11.2); they are this specification's own because Core states no coverage vocabulary and two synthesizers must report alike, and they are the spellings every project binding specification uses.

**[incorporated]** A position is named by its schema coordinate, which §2.14 of the governing edition defines for every schema element; positions §2.14's grammar cannot name (a variable, a position inside a `__schema` or `__type` selection) are named by §7's rule.

**[convention]** An addressable target that is `invalid`, `excluded`, or `implementation-unsupported` **refuses before dispatch** when invoked, as does a target whose source did not complete loading (§3.3). A **context-required** refusal names a configuration point or credential that can make the same invocation proceed; a plain **refusal** names a condition no supplied context can change. Neither sends the operation, and neither has an observable side effect at the service beyond the two introspection requests the loading of a schema-absent source sends (§3.3), because no authority defines a pre-dispatch refusal and a loud refusal before the operation reaches the wire is the choice under which nothing is guessed. Loading precedes resolution and every refusal below it, so a schema-absent source is introspected even when the selected target will then refuse before dispatch.

**[convention]** An interaction that reaches the wire and whose outcome §8 or §9 does not admit as successful **completes unsuccessfully**. Values already emitted before an unsuccessful completion stand as successful values at the moment they crossed the operation boundary (§7, §9); no later ending withdraws them, because Core §5.1 states the output contract per value as it crosses and no authority withdraws a delivered value.

**[limit]** The load gates are the following closed ordered set, and no condition outside it is a load gate:

1. **`location` presence, absoluteness, and scheme** (§4): absent, not a string, not an absolute URI under §4's definition, or a scheme other than `http` or `https`.
2. **`content` shape** (§3.1): absent, not an object, a missing `document`, a `document` that is not a string, a `schema` that is neither string nor object, an unknown member, or a `subscriptions` member that is not exactly the two-member object of §3.1, whose `location` is not an absolute URI under §4's definition, or whose `transport` and `location` scheme do not pair.
3. **Document grammar**: `document` is not a `SourceCharacter` sequence or does not parse as a `Document` under §2 of the governing edition, or parses but contains a type-system definition or extension, which the incorporated rule below places at this gate as the document's failure and not one operation's.
4. **Schema grammar**: a string `schema` does not parse as a `TypeSystemExtensionDocument` under §3.1 of the governing edition, which admits definitions and extensions and no executable definition, or is not a `SourceCharacter` sequence; an object `schema` has no object at `data.__schema` or carries an `errors` entry. With `schema` absent, the live introspection of §3.3 precedes this gate as the family's schema acquisition, as a location-only OpenAPI source is dereferenced before its representation gate (precedent, not authority), and the result of either introspection step fails this gate under the same test as a carried object: a request error result, a null `data`, an `errors` entry, or, for the composed query, no object at `data.__schema`, because no interpretable schema representation arrived.
5. **Schema validity** of the interpreted schema, carried or live-introspected alike, under exactly the subset of the governing edition's §3 type-validation rules whose violation makes correspondence undefined: a type referenced but not defined, where in an introspection result a type is referenced by `queryType`, `mutationType`, `subscriptionType`, an `interfaces` or `possibleTypes` entry, or the innermost named element of a `type` on `__Field` or `__InputValue`, of an `interfaces` or `possibleTypes` entry, or of any `ofType` chain, a chain of zero wrappers included, and is defined when `types` holds an entry of that `name`; a field or argument without a type; two types, two directives, or two fields or two arguments of one definition with the same name, an extension that redefines a field its type already defines included; a non-input type in an argument or input-field position; a non-output type in a field position; more than one `schema` definition, or a schema extension when no schema is defined, a schema being defined by a `schema` definition or, in its absence, by §3.3.1's default root type names, under which the types named `Query`, `Mutation`, and `Subscription` are the roots and `Query` must exist; and a `query` root operation type that is absent or is not an Object type, under the incorporated rule below. In an introspection result the last is `__Schema.queryType` null or naming a type whose kind is not `OBJECT`.

**[incorporated]** The gates' content is the governing edition's: §2.1 defines `SourceCharacter` as a Unicode scalar value (gates 3 and 4); §2.3 says "A Document which contains TypeSystemDefinitionOrExtension must not be executed" (gate 3); §3.1 defines the `TypeSystemExtensionDocument` production (gate 4); §4.2 defines the introspection result shape (gate 4); and §3.3.1 says the `query` root operation type "must be provided and must be an Object type" (gate 5), §3.3 says "All types within a GraphQL schema must have unique names" and states the same for directives, §3.3.1 says that "a document must include at most one schema definition" and that the definition may be omitted when each root operation type uses its default root type name, no other type uses one, and the schema has no description, and §3.3.2 says that for a schema extension "The Schema must already be defined" (gate 5), and §3.6 forbids an Object type extension from redefining a field already defined on the type (gate 5); the remaining gate-5 items are §3's type-validation rules for defined types, typed fields and arguments, unique field and argument names, and input and output positions.

**[incorporated]** A mutation or subscription operation whose root operation type the schema does not provide is not a load failure, because §3.3.1 of the governing edition makes those two roots optional; it is a validation failure under §5.2.1.1 of the governing edition and is handled by §5's validation rule. Documentation-only constraints of the governing edition (deprecation placement, default-value compatibility, deprecation inheritance) are never load gates, and an introspection result that carries an unreferenced built-in scalar is accepted.

**[convention]** Which §3 rules gate is this specification's choice, with this reason: a rule whose violation changes no correspondence has no binding consequence to attach to, and a rule whose violation leaves a type unresolvable or a position untyped has no confined owner, because no contract can be derived below it.

**[limit]** **§3.2's smallest-owner rule**: after the load gates pass, a defect confines to its smallest owning unit, and an unreachable defect destroys no target. The owning units are, from largest to smallest: the source's target inventory, for a validation failure under §5 of the governing edition (§5 of this document states why every such failure is inventory-wide; §5.1.1's executable-definitions rule is the one exception, because gate 3 already refuses it at load under §2.3); one operation definition, for the operation-scoped failures this specification itself defines, which are §3.3's structural-member and annotative-member rules and the absent `subscriptions` member of §3.1; one variable or one selection position, for a value-level projection concern (§6, §7).

**[limit]** **§3.2's source-refusal rule**: after the closed load gates, a source refuses as a source, at resolution, only when the document declares at least one operation definition and no addressable target remains: every operation definition is either anonymous while not alone or shares its name with another. A target-confined invalidity never contributes to this rule: a document whose every operation definition is accounted `invalid` under §5 loads, its selectors resolve, and every invocation refuses before dispatch.

**[convention]** A document with no operation definition is accepted and synthesizes no operation, because §2.3 of the governing edition says such documents "may still be parsed and validated to allow client tools to represent many GraphQL uses", which permits the parse without stating what a source is, and an empty target inventory has nothing to invalidate; the failure its unused fragments incur under §5.5.1.4 reaches no operation, so such a document denotes no target rather than a destroyed one.

**[limit]** How a processor names or presents a confined defect is not portable meaning of this identifier. It MUST identify the affected unit and the responsible position in the document or schema well enough to make the confinement observable, but this specification defines no defect-class taxonomy, per-class authority citation, or per-defect coverage-entry vocabulary.

**[limit]** An `invalid`, `excluded`, or `implementation-unsupported` operation definition is removed from the effective inventory consumed below its owning boundary: no synthesis, dispatch, or classification rule reads it as usable, and synthesis emits no operation for it, only its coverage entry. Removal does not erase its addressable position.

### 3.3 Schema interpretation

**[convention]** The **interpreted schema** is the schema every rule of this specification validates and types the document against: the carried `schema` when present, and otherwise the result of live introspection under this section. Exactly one interpreted schema exists per source per interpretation, because §6.1 of the governing edition validates and executes a document against exactly one schema.

**[incorporated]** A string `schema` is read under §3 of the governing edition as a `TypeSystemExtensionDocument`, the §3.1 production whose definitions and extensions together describe one schema. Its interpreted schema comprises what the string writes together with the five built-in scalars (`Int`, `Float`, `String`, `Boolean`, `ID`), of which §3.5 says that in the type system definition language "all built-in scalars must be omitted for brevity", and the built-in directives of §3.13 (`@skip`, `@include`, `@deprecated`, `@specifiedBy`, `@oneOf`), of which §3.13 says "any built-in directive may be omitted for brevity"; gate 5's defined-type test and §5.7.1's directive test read them as defined. An October 2021 or September 2025 introspection result carries the built-in directives the service provides, as §4.2 requires, and the referenced built-in scalars, as §3.5 requires; June 2018 requires neither and lets a service omit the built-in scalars, so gate 5's defined-type test reads the five built-in scalars as defined in every introspection result, whatever its `types` holds. A **custom scalar position** throughout this specification is a position whose type is a scalar not among those five names.

**[convention]** The built-ins supplement the string and never duplicate it, so gate 5's duplicate-name test does not fire on a built-in name the string writes. A directive the string writes under a built-in name is read as written, in place of the built-in, for §5.7's directive validation (locations, arguments, repetition), because §3.13 permits the omission and states no precedence for a written one; the type-system consequences the edition keys to the name apply whatever the string writes, `@oneOf` making its input object a OneOf input object under §3.10.1, `@deprecated` declaring the deprecation facts, and `@specifiedBy` declaring the scalar specification URL, because the edition attaches them to the name and not to a definition. A scalar the string writes under a built-in name remains that built-in: §3.5 says a service "which provides a type by these names must adhere to the behavior described for them in this document", so the written definition contributes only its directives, the built-in's coercion governs §5.2 and §6, and the position is not a custom scalar position; the string is read this way rather than refused because §3.5's requirement addresses the producer of the representation and no type-validation rule of the edition names a consequence for a consumer, so refusing it would add a gate outside §3.2's closed set.

**[convention]** Its definitions are applied first and its extensions after them, in document order, so that an extension may precede the definition it extends; an extension whose target the document does not define is a referenced-but-undefined type at gate 5. The order is this specification's own because §3.1 of the governing edition defines extensions and states no application order.

A pinned result SHOULD be at least the result of this query; whatever it carries, it is read for exactly the members below, and the absence rules of this section state the consequence of each missing member, because this specification cannot detect a result taken otherwise. The query is listed because no edition lists an introspection query and two implementations must consume one member set; its members are exactly the members the derivations of §5 to §7 read.

**[convention]** The members that query requests are the **consumed members**, and every derivation in this specification reads only them: on `__Schema`, `queryType`, `mutationType`, `subscriptionType`, `types`, and `directives`; on `__Type`, `kind` and `name` at every element, and the remaining members only at the kinds §4.2 makes them applicable to: `specifiedByURL` at `SCALAR`, `fields` and `interfaces` at `OBJECT` and `INTERFACE`, `possibleTypes` at `INTERFACE` and `UNION`, `enumValues` at `ENUM`, `inputFields` and `isOneOf` at `INPUT_OBJECT`, and `ofType` at `LIST` and `NON_NULL`, which the listed query carries to nine levels, a member outside its kinds being unconsumed so that its absence carries nothing; on `__Field`, `name`, `args`, `type`, `isDeprecated`, and `deprecationReason`; on `__InputValue`, `name`, `type`, `defaultValue`, `isDeprecated`, and `deprecationReason`; on `__EnumValue`, `name`, `isDeprecated`, and `deprecationReason`; and on `__Directive`, `name`, `locations`, `isRepeatable`, and `args`. An operation's **positions** are those of its own selection set, its variable definitions, and every fragment definition it reaches by spread, transitively, which is the set §6.3.2's field collection visits. An operation **reaches** an element when a derivation of §5, §6, or §7 reads it: the `__Schema` element, of which it reads its own kind's root-type member and, when a directive is used at one of the operation's positions, `directives`, so that an absent root-type member of another kind and an absent `directives` at an operation using no directive have no consequence; the root operation type of its own kind; every type, field, argument, input field, enum value, and wrapper that validating its selections and variables under §5 or deriving its input and output schemas under §6 and §7 reads, which excludes a field's own type below the depth the operation selects; and every directive definition used at one of its positions. An operation reaches no root type of another kind and no directive used at none of its positions. A `__Type` element at a `type`, `interfaces`, `possibleTypes`, or `ofType` position is a **reference**: only `kind`, `name`, and `ofType` are consumed there, and a named type's own members are read at its entry in `__Schema.types`, which is the element an operation reaches for them, so the stub elements the listed query's `TypeRef` fragment returns carry no absence. Descriptions are consumed by no derivation. The directive members are consumed because §5.7.1 to §5.7.3 of the governing edition validate directive existence, location, and repetition.

**[convention]** The load gates of §3.2 run first, over the whole interpreted schema and before any operation inventory exists; the absence rules of this section govern only what the gates admit, so a null `queryType`, a field or argument without a type, or a referenced type `types` does not hold is gate 5's refusal and never an operation-scoped absence. A consumed member that is **absent**, as distinct from present with `null`, at an element an operation reaches has one of two consequences. An **annotative** member (`defaultValue`, `isDeprecated`, and `deprecationReason`, at any element, save the six edition exceptions below) makes every operation reaching the element `lossy`, with a projection entry naming the element and the member; the derivations of §6 and §7 read the member as declaring nothing, and a §5 rule that reads it is not evaluated at that position (§5.2). Every other consumed member is **structural**: without it no contract can be derived, and its absence makes every operation reaching the element `invalid`. The split covers every consumed member outside the six edition exceptions. A consumed member present with `null` at a position §4.2 of the governing edition declares non-null (`directives` on `__Schema`; `kind` on `__Type`, and `name` on a `__Type` whose kind is not `LIST` or `NON_NULL`, which §4.2's per-kind prose says "must return a String"; `name`, `args`, and `isDeprecated` on `__Field`; `name` and `isDeprecated` on `__InputValue`; `name` and `isDeprecated` on `__EnumValue`; `name`, `locations`, `isRepeatable`, and `args` on `__Directive`), or at a position §4.2's kind comments make non-null for the element's kind (`fields` and `interfaces` on `OBJECT` and `INTERFACE`, `possibleTypes` on `INTERFACE` and `UNION`, `enumValues` on `ENUM`, `inputFields` and `isOneOf` on `INPUT_OBJECT`, `ofType` on `LIST` and `NON_NULL`), is read as absent, with its class's consequence, because no service can produce such a result and the fact it would have carried is missing; the non-null positions gate 5 reaches, `queryType` and `types` on `__Schema` and `type` on `__Field` and `__InputValue`, are that gate's refusal and are not in this list; for `isRepeatable`, `isOneOf`, and `__InputValue.isDeprecated` that consequence is the edition exception below, so a null there reads as `false`; and `interfaces` on an `INTERFACE` element, null or absent, is the sixth exception below, because June 2018 declares it null there. Absence has these two consequences because a pinned result declares no edition and the authority states no rule for a member a result omits; the structural class is the set without which no contract can be derived, and the annotative class is the set whose absence loses a declared fact and nothing else.

**[pin]** Six consumed positions are exceptions to the absence rule, because a pinned result declares no edition and an earlier accepted edition lacks or nulls them: `__Type.specifiedByURL` and `__Directive.isRepeatable` were added in October 2021, `__Type.isOneOf`, `__InputValue.isDeprecated`, and `__InputValue.deprecationReason` in September 2025, and `__Type.interfaces` on an `INTERFACE` element, which June 2018 declares null and October 2021 first requires (the schema-introspection section of each edition states the members, not this rule: §4.2 in October 2021 and September 2025, §4.5 in June 2018). An absent `specifiedByURL` is read as `null`, an absent `isRepeatable` as `false`, an absent `isOneOf` as `false`, an absent `__InputValue.isDeprecated` and `deprecationReason` as `false` and `null`, and an absent or null `interfaces` on an `INTERFACE` element as the empty set, each the earlier edition's own declaration, with no `lossy` disposition. This is §2's governing-text pin applied; the losing reading, the September 2025 declaration at every position, would make every result of an earlier edition structurally incomplete.

**[limit]** A result taken from a September 2025 service by a query that omitted `isOneOf` is indistinguishable from an earlier edition's result and loses the OneOf constraint in the emitted input schema (§6 states this as one of its disclosed floor breaches); the service's request error for a violating value classifies as an unsuccessful completion under §8. An author avoids it by taking the pinned result with the listed query.

**[limit]** The introspection arguments `includeDeprecated: true` change the length of a list, not the presence of a member, and a result taken without them is indistinguishable from a schema with nothing deprecated. This specification asks for a pinned result that is the complete result of the listed query and states that it cannot detect a result taken otherwise; the derived contract of such a result omits deprecated fields, arguments, input fields, and enum values the service still serves.

**[limit]** The listed query's `TypeRef` fragment carries nine nested `ofType` levels, so a named type reached through more than nine list and non-null wrappers is not carried: the tenth wrapper's `ofType` is a structural absence at the element that reaches it, and every operation reaching that position is `invalid`. A string `schema` has no such bound. Nine is this specification's choice, with the reason that a listed query must be finite and nine exceeds by a margin the deepest chain any accepted edition's own text exhibits; the losing reading, an unbounded chain, is not expressible in a listed document.

**[convention]** No derived schema is ever an empty `anyOf`: a selection on an abstract type with no possible types, an interface no object implements or a union with no member types, derives `{"type": "null"}` at a nullable position and `false` at a non-null one, because value completion under §6.4.3 of the governing edition can resolve no concrete type there and the field completes to null or to an execution error (§7).

**[convention]** **Live introspection.** The rules that follow, to the end of this section, apply when `schema` is absent, because live introspection is the only other schema acquisition this family defines.

**[convention]** The processor first sends one edition-independent **capability probe**, listed normatively and exactly the document below. That `__type(name:)` resolves an introspection type by name is stated only by its signature and, in October 2021 and September 2025, by §4.2's requirement that "any named type which can be found through a field of any introspection type must be included" in the schema's type set; no edition states that it resolves an introspection type, whose name begins with two underscores (each edition's worked example resolves a user type), so the probe is this specification's bridging convention in every edition, chosen because it is the one selection every accepted edition parses and answers.

```graphql
query { t: __type(name: "__Type") { fields { name args { name } } } f: __type(name: "__Field") { fields { name args { name } } } d: __type(name: "__Directive") { fields { name args { name } } } i: __type(name: "__InputValue") { fields { name } } }
```

**[convention]** The probe's four positions observe every optional member and argument the listed query carries: `specifiedByURL` and `isOneOf` on `__Type`, `isRepeatable` on `__Directive`, `isDeprecated` and `deprecationReason` on `__InputValue`, and the `includeDeprecated` argument on `__Type.inputFields`, `__Field.args`, and `__Directive.args`. Four positions suffice because those are the only consumed members and arguments any accepted edition added after June 2018; `__Schema.description`, added in October 2021, is consumed by no derivation and needs no position.

**[convention]** The processor then composes the **introspection query** from the listed query of this section by removing each optional member or argument the probe did not observe, each unobserved member (`specifiedByURL`, `isOneOf`, `isRepeatable`, and `isDeprecated` and `deprecationReason` on `__InputValue`) deleted together with the whitespace that precedes it, and each unobserved `includeDeprecated` argument deleted together with the parentheses that enclose it, so that `inputFields(includeDeprecated: true)` becomes `inputFields` and `args(includeDeprecated: true)` becomes `args` and every remaining token keeps the listed spelling, and sends it. A probe position that resolves to `null`, or whose alias the result omits, observes no capability for that type, and the base selection is used for it whatever `__schema.types` would have shown, so that one probe shape fixes one composition; a composed query therefore requests exactly what the service has, and a service that implemented the additions incrementally is served rather than refused. This is the preserve rung, because refusing a service on which a probe position resolves to `null` would reject a working June 2018 service, and reading a null as no capability is the only reading under which the composed query is valid on every accepted edition.

**[convention]** The result of either step is tested under §3.2's gate 4 exactly as a carried object is, so a request error result, a null `data`, an `errors` entry, or a composed-query result without an object at `data.__schema` refuses the source at load, because a service that answers the probe or the composed query with a request error, an `errors` entry, or no schema object discloses no interpretable schema, a partial result having an undetermined shape at its errored paths, no operation can be typed, and no authority states what a client does with such an answer. Gates 4 and 5 then apply to the live result exactly as to a carried one. A request at either step that yields no response (a name-resolution, connection, or TLS failure, or a runtime's timeout) reaches no gate and leaves the closed set unchanged: the load does not complete, an invocation refuses before dispatch for want of an interpreted schema, and synthesis reports the source as not loaded rather than accounting its operations, because no interpretable schema representation was seen; document conformance is unaffected, GQL-D-03's schema clause and GQL-D-04 reaching carried content only (§11.3).

**[convention]** Both introspection requests are always POST, whatever §8's `httpMethod` selects, because the composed query's length has no guaranteed URL carriage and the over-HTTP draft requires POST support of every service. Both carry the same configured `protocolFields`, the same configured `extensions` map, and the same credentials the loading carries: when a source is loaded for an invocation, those are the invocation's, so the schema observed is the schema that invocation's request reaches; when it is loaded for synthesis, they are whatever the synthesizer supplies, none by default, and the emitted contract is a claim about that credential set under the limit below. The interpreted schema is the one those requests obtain at that loading.

**[limit]** Whether a runtime loads a schema-absent source once per invocation or reuses a loaded source across invocations that carry the same credentials is runtime policy under Core §1.2; a runtime that reuses one accepts §4's staleness posture for the reused interval.

**[limit]** With `schema` absent, the interpreted schema is whatever the service discloses to the invocation's own credentials, so a role-filtered or contract-variant service yields a contract that varies by caller. Portability of a contract across callers is obtained by pinning `schema`; a live-introspected contract is a claim about one credential set. The alternative, refusing live introspection, would narrow the dominant case in which a document is carried against a service the author does not control.

**[convention]** Live introspection always composes `includeDeprecated: true` at every position the probe observed the argument, so it is subject to the `includeDeprecated` limit above for a service that deprecates a position without exposing the argument for it, which no accepted edition permits, and for a service whose probe position resolves to `null` while its `__schema.types` would have shown the argument, which the null-probe rule above serves with the base selection; both are stated here as the residual cases, because the arguments are the authority's own way of asking for the complete set and omitting them would hide declared facts.

## 4. `location`, `content`, and composition

**[incorporated]** A present `location` MUST be an absolute URI (Core [OBI-D-05](../../openbindings.md#102-document-rules)); a bare filesystem path is not conformant.

**[pin]** Core OBI-D-05 requires an absolute URI or a binding-specification-defined absolute address, this family defines no other form, and [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) defines both `URI` (§3), which admits a fragment, and `absolute-URI` (§4.3), which does not. This specification pins `absolute-URI` here and at `content.subscriptions.location` alike, because a fragment has no meaning at an HTTP or WebSocket endpoint and one grammar must decide the load gate; the losing reading, admitting a fragment, is disclosed.

**[convention]** `location` is REQUIRED and its scheme MUST be `http` or `https`; it names the GraphQL HTTP endpoint that serves the document's queries and mutations and answers live introspection. The scheme set is this specification's choice, because the over-HTTP draft is the only incorporated transport for single-result operations and defines no other scheme, so a `location` in another scheme has no incorporated mapping and refuses at load (§3.2).

**[limit]** Whether a request to `location` yields a response at all is the address scheme's own affair: a name-resolution failure, a connection failure, a TLS failure, or a runtime's timeout is decided by the scheme and the runtime, and this specification attaches one outcome to each kind of request that yields no response: §3.3's for an introspection request, §8's for an operation request. Responses that do arrive are classified under §8.

**[convention]** `location` supplies no reference base, because GraphQL documents and schemas contain no references, so Core [§7](../../openbindings.md#7-reference-resolution)'s clause on references internal to embedded source content has nothing to resolve for this family; schema and transform references in the OBI document itself are Core §7's as for every family.

**[convention]** `content` is REQUIRED. No source mode this specification governs forbids `content`: the only mode it governs is the one in which `content` carries the document, so the set of `content`-forbidding modes Core [OBI-B-02](../../openbindings.md#104-binding-specification-rules) item 3 asks for is empty, and a location-only source is not accepted, because a source without a document denotes no operation. This discharges item 3's forbidden-mode clause in the opposite direction, stated explicitly, at the refuse rung: the alternative, deriving a document from the schema, authors an operation no author wrote.

**[incorporated]** `content` has primacy (Core [§5.4](../../openbindings.md#54-sources)): a present `schema` is the interpreted schema and the processor never replaces it with an introspected one.

**[limit]** The carried `document` is the document sent, never rewritten (§5): a stripping or rewriting rule would author wire behaviour no authority states, so this specification defines none.

**[convention]** Composition is therefore fixed: `location` is the invocation target of every query and mutation and the introspection point of §3.3; `content.document` denotes the operations; `content.schema`, when present, is the interpreted schema, and when absent `location` supplies it; `content.subscriptions`, when present, is the invocation target of every subscription. No member of `content` is retrieved from `location` and no member of `location` is derived from `content`, because no authority defines a retrieval of a document from an endpoint or a derivation of an endpoint from a document.

**Staleness posture.** A service-addressed family states what happens when a pinned artifact and the live service disagree. This family's posture has two faces.

**[convention]** A pinned `schema` is dispatched against as carried, because no authority defines a repair of a carried schema. Dispatch proceeds against it; the processor never re-introspects to repair a pin, and a live service that rejects a document the pin validated produces that service's own request error result, which classifies as an unsuccessful completion under §8.

**[pin]** A service that has evolved beyond the pin, with a new enum value, a new implementation of an interface, or a new field, succeeds while the contract derived from the pin does not admit its value, because the derived `output` is closed exactly as the pinned schema is closed (§7). That is staleness too, not a defect of the derivation: the governing edition's own result coercion returns one of the schema's defined set of values, and the defined set is the pinned schema's, so a closed contract is the faithful contract for the schema carried. Two readings survive for the invocation: emit the value as the service returned it, or validate every execution result against `output` and fail loudly on a mismatch. This specification pins the first, because Core §5.1 makes `output` a claim the document states and the binding attests, not a check the binding performs, and the project's OpenAPI siblings decode a response without validating it against the declared schema, precedent this family follows rather than authority; the losing reading is disclosed and rejected because it would make the binding's behaviour a runtime test of the document's own claim and would fail a partial result whose nulls §7 already admits. Whether a consumer validating the emitted value against `output` treats the disagreement as a contract breach is the consumer's, and the drift is the author's to repair.

**[convention]** Drift of either face is repaired by the document author, by re-pinning `schema` or by omitting it, in which case live introspection tracks the service and an additive change is absorbed at the next interpretation. Pinning is the author's choice of a stable contract over a current one, and this specification says so rather than choosing for the author, because no authority states which of the two an author wants.

## 5. Selector, operation resolution, and document validation

### 5.1 Selector and resolution

**[convention]** `selector` is OPTIONAL. When present it is one GraphQL `Name` under §2.1.8 of the governing edition, naming the operation definition of the carried document that bears that name; the target is an operation definition and nothing narrower or wider, because the operation is the unit §6.1 of the governing edition executes, and no authority defines any other address for one. When absent, the target is the document's lone operation definition, which the governing edition permits to be anonymous only when it is the sole operation. The rejected spellings are a schema coordinate (§2.14 addresses schema elements, not operations), a JSON Pointer (a GraphQL document is not JSON), and a root-field selector (the operation is the document's, not the schema's).

**[incorporated]** Resolution mirrors §6.1's `GetOperation`: with no operation name, the document must contain exactly one operation, and otherwise the operation of that name is selected and a name that matches none raises a request error; §5.2.2.1 makes a named operation definition unique within a document, and §5.2.3.1 forbids an anonymous operation definition in a document that holds more than one operation definition. Names compare by exact code-point equality under §2.1.8.

**[convention]** A `selector` naming an addressable target (§3.2) resolves, whatever the target's disposition; an `invalid`, `excluded`, or `implementation-unsupported` target then refuses before dispatch. A `selector` that is not a `Name`, a `selector` naming no operation definition, a `selector` naming a name two definitions share, an absent `selector` over a document holding two or more operation definitions, and an absent `selector` over a document holding none do not resolve, and the invocation **refuses at resolution**, because the request that would result fails at the service, under §6.1's request error or, for a shared name, §5.2.2.1's validation, and this specification refuses it earlier and loudly rather than sending it. Each of these conditions is decidable from the binding and its carried document alone, so a binding meeting one over a parsing document is also non-conformant under GQL-D-05; the document rule and the processor's refusal compose as Core's document rules and processor behaviour compose everywhere.

**[convention]** The selected operation's name is what §8 and §9 carry as `operationName`, sent whenever the selected operation is named, whether or not the document holds other operations. The over-HTTP draft makes the parameter optional and, when the document holds one operation, admits sending it, omitting it, or the empty string on GET; the preserve rung fails there because that set is not one of equivalent spellings but of different information, a sent name being the selection stated on the wire and an absent one not, and a service, registry, or trace observes which was chosen, so preserving the set would make the presence of the selection implementation-dependent. For the lone anonymous operation no `operationName` is sent on any lane, because the draft's empty-string equivalence is stated only for GET, its JSON encoding equates `null` and not the empty string to absence, and §6.1's `GetOperation` treats a string as a name to find, so omission is the one spelling every lane admits; the losing reading, the empty string, is disclosed as a request error off the GET lane.

### 5.2 Document validation

**[incorporated]** Validity is a property of the whole request: §5 of the governing edition says "execution should only occur for valid requests", §6.1.1 says that where validation errors are known "the request must fail without execution", and the over-HTTP draft says validation of a request SHOULD apply all of §5's rules and that a request failing validation is answered with a request error result, so a failure anywhere in the carried document is a failure of every operation the document holds.

**[convention]** Before synthesis or dispatch the processor validates the whole carried document against the interpreted schema under every rule of §5 of the governing edition. Any failure invalidates the source's entire target inventory: every operation definition is accounted `invalid`, and §5.1.1 is the one rule gate 3 already refuses at load. Validation runs before dispatch because deriving the output contract already requires the validated selection, so the check exists regardless, and refusing before dispatch is the loud choice where the draft makes the service's own validation a SHOULD; the losing reading, leaving validation to the service, would make an invalid document's refusal silent and per-request.

**[pin]** §5.2.1.1's Operation Type Existence is included in that: its explanatory text says the operation lacking a root type "is invalid since it cannot be executed", while its formal rule ranges over every operation in the document, so the edition admits an operation-scoped reading and an inventory-wide one. This specification pins the inventory-wide reading and discloses the other, because the request carrying the document fails as a whole at the service under §6.1.1 there as under every §5 rule.

**[convention]** A position at which a §5 rule cannot be evaluated for want of an absent structural introspection member, or at which a §5 rule reads an absent annotative member (§5.4.3, §5.6.4, and §5.8.5 read `defaultValue`), is not a §5 failure, because the service's own schema is complete and the rule is the service's to apply there; the structural absence makes every operation reaching the position `invalid` and the annotative one makes them `lossy`, both under §3.3, and the rest of the inventory is left to the remaining rules.

**[convention]** §5.6.1's test that a literal input value is coercible to its type is applied under the coercion rules the governing edition fixes: §3.5's built-in scalar rules, §3.9's enum values, §3.10's input-object fields, §3.11's list coercion, and §3.12's nullability. Where the edition leaves the judgement to the service, this specification treats the literal as coercible and dispatches: a literal at a custom scalar position, whose rules §3.5 makes the service's, and a literal a built-in rule directs the service to refuse only as a SHOULD, an `Int` outside its range among them. This is the preserve rung, because refusing a custom scalar literal would author a coercion no authority fixes, refusing a literal under a SHOULD-scoped rule would make a judgement the authority leaves to the service, and either would invalidate the whole inventory on a judgement two conforming processors could make differently; the service's own request error is §8's unsuccessful completion.

**[pin]** A selection of the `__schema` or `__type` meta-fields is validated, and its output derived (§7), against the introspection types as §4.2 of the governing edition defines them in type-system language, not against the carried schema's type set. Two readings survive, since a carried string schema never writes the introspection types under any edition and June 2018 does not require them to appear in an introspection result's `__Schema.types` while October 2021 and September 2025 do: validate against the carried set, under which every introspection selection over a string schema, or over a June 2018 result that omits the introspection types, is invalid, or against §4.2's definitions, under which a selection an earlier service refuses answers with the request error §8's classification already carries. This specification pins the second and discloses the first, because the first invalidates working documents against every string schema and on an accepted edition. `__typename` needs no such rule: §4.1 defines it on every object, interface, and union type of the schema it is selected on, the carried schema's outside a meta-field selection and §4.2's inside one, and §7 derives it from that type.

**[limit]** Validation runs under the September 2025 rules for every service, and the places where that edition is stricter than an earlier accepted edition are the observable consequence of §2's governing-text pin. The list holds every grammar, schema-validity, or document-validation rule an accepted edition added or strengthened; the September 2025 §3.6 constraints on deprecation placement, default-value compatibility, and deprecation inheritance are outside it because this document's §3.2 classes them as documentation-only and gates none, and September 2025 §3.13's requirement that a directive definition name at least one location restates a grammar every edition already has and is not one. Each lands on the axis its rule belongs to. Three are grammar rules and refuse at gate 3, or at gate 4 in a string `schema`: the lexical lookahead restrictions on numbers (October 2021 §2.9.1 and §2.9.2, under that edition's §2 preamble); a lone fixed-width Unicode escape that is not a Unicode scalar value and not half of a surrogate pair (September 2025 §2.10.4); and `SourceCharacter` redefined as a Unicode scalar value (September 2025 §2.1), where the earlier editions admit U+D800 to U+DFFF. One is a schema rule gate 5 enforces: argument names must be unique within a field, an interface field, or a directive definition (September 2025 §3.6, §3.7, and §3.13). Five are schema rules no rule of this specification reaches, because a schema violating them yields the same contract at every position this specification derives: an input object with an unbroken chain of non-null singular self-references (October 2021 §3.10) input-object default values that form a cycle (September 2025 §3.10), the requirement that the query, mutation, and subscription root types be distinct (October 2021 §3.3.1, which June 2018 states only for two of the three), the requirement that an introspection result's `types` hold every referenced built-in scalar and no unreferenced one (October 2021 §3.5, which §3.2 declines to gate in either direction), and the constraints on a OneOf input object's fields, nullable and without defaults (September 2025 §3.10, applied by name under §3.3) load and dispatch as declared, §6 stating the input schema of such a type, and the service's own answer is the only consequence. Five are document rules, and a document an older service would accept but September 2025 rejects is inventory-invalid under §5.2: an operation whose kind's root operation type the schema does not provide (September 2025 §5.2.1.1, Operation Type Existence, which the earlier editions state nowhere, a tightening ordinary documents reach); a literal for a `@oneOf` input object with other than exactly one entry (September 2025 §3.10.1 under §5.6.1 and §5.8.5), which §3.3's name-keyed rule applies to a schema written under an earlier edition; a subscription's single root field must not be an introspection field (October 2021 §5.2.3.1); `@skip` and `@include` are forbidden on a subscription's root selection set (September 2025 §5.2.4.1); and the `includeDeprecated` argument of `fields` and `enumValues` is non-null in September 2025 §4.2 where the earlier editions declare it nullable, so an explicit `null` there fails §5.6.1 (the argument on `args` and `inputFields` is a September 2025 addition, not a tightening).

**[limit]** The over-HTTP draft lets a service apply additional validation rules at its discretion. A service-added rule (depth, complexity, or an allow-list) that rejects a document this specification accepted produces that service's own request error result, which completes the invocation unsuccessfully under §8; it is not a defect of the document or of this specification, because the rule is the service's and no authority states it.

**[limit]** The carried document is the executable document: this binding sends it as carried and strips or rewrites nothing (§4). A directive the interpreted schema does not define, a client-cache directive or a compiler directive among them, fails §5.7.1 and invalidates the inventory exactly as the service would refuse the request; authors carry the document a persisted-document pipeline would carry, after client directives are compiled away. A pinned schema that differs from what the service executes, a role-filtered schema or a gateway contract, is repaired by omitting `schema` so that live introspection with the invocation's own credentials supplies the schema the service will enforce (§3.3). Any stripping rule would author wire behaviour no authority states, so this specification defines none.

## 6. Caller envelope and input contract

**[convention]** The caller-facing input value is the operation's **variables map**: one JSON object whose keys are the selected operation's variable names without their `$`. An absent key means the variable is not provided, so its declared default applies or it is unset; a key present with `null` is an explicit null. This is the value §8 and §9 carry as `variables`, unchanged, and absent input carries no `variables` member at all (§8). The correspondence is this specification's own because Core states the boundary and the governing edition states the coercion but neither names the JSON object a caller supplies; the variables map is the one value the edition's own request already carries, so nothing narrower or wider is invented.

**[incorporated]** An unknown key passes to the wire unchanged: §6.1.2's `CoerceVariableValues` iterates over the operation's variable definitions and defines no error for a surplus entry, so the service ignores it. This specification therefore does not refuse an unknown key, because refusing would narrow what the authority admits on the exact wire value.

**[convention]** The operation's `input` schema is `{"type": "object", "properties": {<variable>: <schema>, ...}, "required": [<the non-null variables without a default>]}` with no `additionalProperties` keyword, so that the pass-through above is expressed rather than contradicted; the spelling is this specification's because JSON Schema offers several and two synthesizers must emit one. Each variable's schema derives from its declared type under the following table, then under the nullability composition below.

| GraphQL input type | JSON Schema | provenance |
| --- | --- | --- |
| `Int` | `{"type": "integer", "minimum": -2147483648, "maximum": 2147483647}` | **[pin]** the bounds, below; **[incorporated]** the integer type, §3.5.1 |
| `Float` | `{"type": "number"}` | **[incorporated]** §3.5.2 admits integer and float input values |
| `String` | `{"type": "string"}` | **[incorporated]** §3.5.3 |
| `Boolean` | `{"type": "boolean"}` | **[incorporated]** §3.5.4 |
| `ID` | `{"type": ["string", "integer"]}` | **[pin]** the integer branch, below; **[incorporated]** §3.5.5 admits string and integer input values |
| enum | `{"enum": [<value names, as strings>]}` with no `type` member, so that *admit null* wraps it in `anyOf` rather than leaving `type` and `enum` in disagreement | **[incorporated]** §3.9 coerces an enum input value by its name; the spelling is **[convention]** |
| input object | `{"type": "object", "properties": {<field>: <schema>}, "required": [<the non-null fields without a default>], "additionalProperties": false}` | **[incorporated]** §3.10: an entry not defined by a field is a request error |
| OneOf input object | the input-object schema with `"minProperties": 1`, `"maxProperties": 1`, and *exclude null* applied to every property | **[incorporated]** §3.10.1: exactly one entry, non-null |
| list of T | `{"anyOf": [{"type": "array", "items": T}, T′]}`, T′ being the item schema after *exclude null* | **[incorporated]** §3.11 coerces a non-list input value to a one-element list and never coerces a bare `null` to `[null]`; the spelling is **[convention]** |
| non-null T | T under *exclude null* | **[incorporated]** §3.12 |
| custom scalar | unconstrained, with §7's carriage of the scalar's identity | **[incorporated]** §3.5 leaves a custom scalar's input coercion to the service |

**[pin]** **The `4.0` pin.** JSON Schema's data model cannot distinguish the number `4.0` from `4`: `integer` admits any number with a zero fractional part, so no emitted schema can express "an integer token". The governing edition speaks twice: §3.5 says that under a serialization that does not discriminate integers from floats, such numbers "are interpreted as an integer input value if they have an empty fractional part", while §3.5.5 says a float input value "such as 4.0" must raise a request error and §3.5.1 admits only integer input values. The disagreement is whether §3.5.5's `4.0` denotes a JSON token or a GraphQL float literal. This specification pins the §3.5 reading for JSON variables, because JSON is a non-discriminating serialization in §3.5's own words and because a JSON Schema can state no other reading, and discloses the losing reading: a service that preserves the `4.0` token as a float raises a request error the schema did not predict, which §8 classifies as an unsuccessful completion. The binding passes the caller's value through unchanged and never normalizes it.

**[pin]** **The `Int` bounds pin.** §3.5.1 says an integer input value outside the 32-bit signed range "should" raise a request error, so a service may accept one. The emitted schema states the bounds anyway, because Core §5.1's floor forbids admitting a value the authority's SHOULD directs services to refuse, and a service that accepts more than the floor is exactly what Core permits. The losing reading, a bound-free `integer` that admits what a lenient service accepts, is disclosed; it would breach the floor on every conforming service.

**[pin]** **The `ID` pin.** §3.5.5 says a string or integer input value "should be coerced to ID as appropriate for the ID formats a given GraphQL service expects", so a service whose identifier format cannot absorb an integer may refuse one. Two readings survive: emit `string` alone, which never over-admits but makes this binding refuse an integer the SHOULD directs services to coerce; or emit `["string", "integer"]`, which follows the SHOULD's direction and over-admits on a format-restricted service. This specification pins the second on the SHOULD's own words and states the resulting breach as a limit below; a format-restricted service's request error classifies as an unsuccessful completion under §8. This is the opposite resolution from the `Int` bounds pin, and deliberately so: there the SHOULD directs a refusal, here it directs an acceptance, and the floor follows the SHOULD's direction in both.

**[limit]** **The floor and its five disclosed breaches.** Core §5.1 makes `input` a floor: a realization accepts at minimum every value validating against it and may accept more. Every row above therefore admits only values the service accepts, with five exceptions this specification states rather than hides: the `4.0` token the pin cannot exclude; the `ID` integer branch; a custom scalar position, which is unconstrained because the scalar's value domain is service-defined and no schema can state it, so the coverage report's `projection` entry for the position discloses it (§7); `Float` as `number`, which admits a value outside binary64 precision that §3.5.2 makes a request error, because JSON Schema has no keyword for that range; and an input-object position whose pinned result lacks `isOneOf`, read as `false` under §3.3's edition exception, which is exact for a pre-2025 result and over-admits for a September 2025 result taken with an incomplete query. A service's request error in each case classifies as an unsuccessful completion under §8 and is never silent. The list `anyOf` is kept not because the floor demands width but because a tool validating caller input against `input` would, under an array-only schema, refuse a bare scalar the service accepts, against the rule that this binding never refuses what the authority admits.

**[convention]** A declared default, on a variable, an argument, or an input field, is never inserted into a request; it is emitted as JSON Schema `default` at that position, the GraphQL const literal mapped to JSON by one fixed image: `Int` and `Float` literals to JSON numbers with the literal's own digits (§2.10's numeric grammar is a subset of JSON's), `String` literals to strings, enum literals to the value name as a string, `Boolean` and `null` literals to their JSON counterparts, and list and object literals recursively; a pinned result's `defaultValue`, which §4.2 defines as a GraphQL-language string encoding of the value, is parsed under §2's const-value grammar first. The image is total over const values, so it has no failure case. The keyword and the image are this specification's own because the edition defines the literal and JSON Schema the keyword and neither fixes the image, so one must be chosen; the losing reading, no `default` keyword, is disclosed as hiding a declared fact from the caller.

**[convention]** **Nullability composition.** Two total operations on a derived schema S. *Admit null*: when S has a `type` member, `"null"` is added to it unless already present; otherwise S becomes `{"anyOf": [S, {"type": "null"}]}`. *Exclude null*: when S has a `type` member, `"null"` is removed from it, S becoming `false` when that would leave `type` empty; otherwise S becomes `{"allOf": [S, {"not": {"type": "null"}}]}`. Every result is valid against the 2020-12 meta-schema (Core OBI-D-17), which is why an empty or repeated `type` is never produced. A nullable position applies *admit null* to its schema and a non-null position *exclude null*, which reaches an unconstrained custom-scalar schema and a list's `anyOf` alike. §3.12 states what null means at each position; the two operations' spellings are this specification's, because JSON Schema offers several equivalent spellings and two implementations must emit one. For a list position the single-value branch of the `anyOf` is the item schema after *exclude null*, because §3.11 coerces a bare non-null value to a one-element list and never a bare `null` to `[null]`; the list position's own nullability is then applied, so `[Int]!` admits `[null]` and refuses `null`, and `[DateTime]!` refuses `null` at the list and admits it inside, exactly as §3.11 and §3.12 state. A OneOf input object's properties are the exception: §3.10.1 makes their declared types nullable but requires the one present value to be non-null, so the OneOf row governs and *exclude null* is applied to each.

**[convention]** The schemas above are stated as inline structures. A synthesizer MAY emit the schema of any named type once, in the document's `schemas` map or a `$defs` member, and reference it with a same-document `$ref` (Core §7), and MUST do so for a type that reaches itself, since an inline structure for it is not finite; the cut points and the spelling of their keys are synthesis policy (§11.4), and the structure every reference resolves to is the one this section states. Nullability composition applies to a reference as to any schema without a `type` member.

**[incorporated]** At `inputTransform` the source-facing value is the variables map and at `outputTransform` the `data` map of one execution result, or of each event's execution result for a subscription (Core §5.5); this specification provides no context bindings at either position, evaluation uses Core's closed environment unaugmented, and synthesis emits no transform (§11.2).

## 7. Output contract and custom scalars

**[convention]** The successful output value of a query or mutation is the whole `data` map of the execution result, not a projected root key, because the operation is the document's operation definition (§5) and §7.1.5 of the governing edition defines `data` as the result of executing it, so nothing narrower is the operation's value. A subscription's output values are §9's.

**[incorporated]** The shape facts the derivation rests on are the governing edition's: which response names are collected is §6.3.2's `CollectFields`, fragment merging included, with `@skip` and `@include` evaluated on a spread before recursing into it; what type completes each is §6.4.3's `CompleteValue`; a completed list value is always a list (§6.4.3); the result map holds exactly the collected response names, an entry for every collected field, null included (§6.3.3 and §7.1.5); an execution error null propagates to the nearest nullable position or to `data` itself (§6.4.4); and `__typename` on an abstract type completes to the concrete object type's name (§4.1).

**[convention]** The `output` schema is derived from the selected operation's validated selection set. For each collected response name, the schema is the field's type under the leaf and composite rules below with nullability under §6's composition operations. Every derived object schema carries `"additionalProperties": false` and lists in `required` every collected response name except one all of whose contributing selections, across fragments and merged field sets, are variable-conditioned, a selection being variable-conditioned when it carries a `@skip` or `@include` whose condition is a variable, itself or through a fragment spread or inline fragment it is reached by; a selection with a literal condition is included or excluded exactly as `CollectFields` would at execution. A selection on an abstract type yields one object schema per possible concrete type, in the order the interpreted schema lists them (`possibleTypes` order in an introspection result, definition order in a string schema), combined with `anyOf`, each branch carrying `__typename` as `{"type": "string", "const": <type name>}` when the selection includes it, branches whose derived schemas are identical, `const` included, collapsing to one, which is the only collapse criterion; a list position maps to `{"type": "array", "items": <schema>}`, never the input side's `anyOf`. The encoding is this specification's own because the authority states the facts and no schema spelling, and two implementations must emit one.

**[pin]** **Output leaf schemas.** `Int` is `{"type": "integer"}` with no bounds, because §3.5.1 makes an out-of-range result an execution error only as a SHOULD and Core §5.1 requires every successful value to validate against `output`, so a lenient service's larger integer must not be refused; this is the mirror of §6's input bounds pin, the asymmetry being the two contract directions', and the losing reading, bounded output, is disclosed. `Float` is `number`, `String` is `string`, `Boolean` is `boolean`, `ID` is `string` because §3.5.5 says an `ID` "must always serialize as a String", an enum is `{"enum": [<value names>]}`, `__typename` is `string` and a `const` inside an abstract-type branch, a custom scalar is unconstrained with the carriage below, and a selection inside `__schema` or `__type` derives from §4.2's introspection types under §5.2's pin.

**[convention]** A value emitted as an operation value is a successful value at the moment it crosses the boundary, and a later unsuccessful ending does not withdraw it; the partial `data` value §8 emits before an unsuccessful completion is such a value and validates against `output`, because §6.4.4's propagation confines an execution-error null to a position the derivation already made nullable or nulls `data` itself, which §8 classifies without a value. The distinction between a null that is a value and a null that stands for an execution error is not expressible in the output schema; that is why §8 carries the `errors` list as failure data beside the emitted value.

**[incorporated]** Custom scalar values pass through unchanged in both directions: §3.5 leaves a custom scalar's serialization and coercion to the service.

**[convention]** The schema of a custom scalar position is unconstrained and carries the scalar's exact name in the JSON Schema `format` keyword and, when the schema declares one, its `specifiedByURL` in the annotation keyword `x-graphql-specifiedBy`, because Core §5.2 makes `format` an annotation and never an assertion at operation boundaries, so a scalar name there can neither refuse a value nor be mistaken for a syntax claim, `format` is where JSON Schema consumers already look for a value's named semantic type, and Core §5.2 admits unknown keywords as annotations, which carries the URL; no authority names a carrier, so this is this specification's.

**[limit]** A custom scalar whose name equals a registered JSON Schema format (`uuid`, `date`, `email`) is annotated identically, and a tool outside OpenBindings that asserts formats may apply the registered meaning; this specification states the collision and defines no renaming.

**[convention]** The coverage report carries a `projection` entry per custom scalar position, per annotative introspection member absent at a reached element (§3.3), and per deprecated field, argument, input field, or enum value the operation reaches (§11.2). A schema-element position is named by its schema coordinate (§2.14 of the governing edition), and a position §2.14's grammar cannot name by one of two fixed spellings: a variable position by the operation name, `(`, `$`, the variable name, and `)`, as in `GetUser($id)`, and a position inside a `__schema` or `__type` selection, which §2.14 says is not a schema element, by the operation name, `#`, and the response path as an [RFC 6901](https://www.rfc-editor.org/rfc/rfc6901) JSON Pointer, as in `Probe#/__schema/types`; the operation name is the empty string for the lone anonymous operation in both forms. The two spellings are this specification's because the authority defines no coordinate for document positions.

## 8. Queries and mutations over HTTP

**[convention]** This section governs queries and mutations; the interaction is unary, one input value, at most one output value, completion, because §6.2 of the governing edition executes a query or mutation to exactly one execution result. Subscriptions are §9.

**[exclusion]** Queries and mutations over the graphql-ws socket, which that protocol admits as single-result operations, are excluded: the over-HTTP draft is the incorporated transport for single-result operations and the socket adds no semantics to them. The reopen trigger is a real cohort of services that serve queries or mutations over graphql-ws and not over HTTP.

**[incorporated]** A **POST request** carries a JSON body whose members are `query`, the whole carried document's source text; `operationName` per §5.1; `variables`, the variables map, when input is present; and `extensions` when configured. No other request member is ever emitted: the draft says implementers "MUST NOT add additional properties to the request object". The draft's JSON encoding equates `null` and absence for an optional parameter.

**[pin]** The POST body's `Content-Type` is exactly `application/json` with no parameter, because RFC 8259's registration defines no `charset` parameter for that media type and the draft's UTF-8 assumption makes one redundant; the losing reading, appending `charset=utf-8`, is disclosed as naming a parameter the registration does not define.

**[configuration point]** `extensions` is a JSON object the binding sends verbatim as the request's `extensions` member on every lane, absent by default. The draft defines the member as "reserved for implementers to extend the protocol however they see fit", so no content is incorporable and the binding may carry a declared map but never author one; the point exists because a service may key routing or persisted-operation lookup on it.

**[configuration point]** `httpMethod` selects `post` (default) or `get` for the query or mutation request and for §9's graphql-sse request. Under `get` the same parameters ride the query component of the request URL in `application/x-www-form-urlencoded` form as the WHATWG URLSearchParams class serializes it, which the draft incorporates: `query` as the document text, `operationName` as a string, `variables` and `extensions` each as a JSON string, in that order, each parameter present only when it has something to carry. `post` is the zero-configuration default because the draft says a service "MUST support GraphQL-over-HTTP request via POST" and only MAY support other methods; `get` exists because the draft defines it and a caller may need a cacheable or body-less request.

**[convention]** An optional request parameter with nothing to carry is omitted, on every lane. The draft's equivalences are per lane, the empty string on GET and `null` in the JSON encoding, and intersect only at omission, so omission is the one spelling every lane admits; the losing reading, preserving each lane's own set, is disclosed as making the wire lane-dependent for no observer's benefit. The parameter order on GET is fixed as listed above because the serializer preserves order and two implementations must emit one URL.

**[incorporated]** A mutation is never sent by GET: the draft says "GET requests MUST NOT be used for executing mutation operations" and requires the service to reject one, so an invocation of a mutation under `httpMethod: get` refuses before dispatch.

**[configuration point]** `protocolFields` names explicit HTTP contributions: a `headers` map of field name to field value and a `cookies` map of cookie name to cookie value. It governs every HTTP request this binding makes: the operation request, the two live introspection requests of §3.3, §9's graphql-sse request, and §9's graphql-ws opening handshake. A header name MUST be an RFC 9110 `token` and a value an RFC 9110 `field-value`; a cookie name and value MUST form an RFC 6265 `cookie-pair`, and the pairs are sent as one `Cookie` field holding their `cookie-string`. A contribution that violates those grammars, two header contributions whose names differ only by ASCII case, or a `cookie` header contribution beside the `cookies` map refuses before dispatch, because HTTP field names compare case-insensitively and the wire cannot carry both. The point exists because a service may require a field no authority declares, a tenant or trace header among them.

**[incorporated]** The reserved fields' semantics are their authorities': `Connection` and the fields it lists (RFC 9110 §7.6.1), `TE` (§10.1.4), `Upgrade` (§7.8), `Transfer-Encoding` (RFC 9112 §6.1, to which RFC 9110 §7.6.1 defers), `Trailer` (RFC 9110 §6.6.2), `Proxy-Authorization`, which is "consumed by the first inbound proxy" (§11.7.2), the historic `Keep-Alive` and `Proxy-Connection`, which §7.6.1 names as connection-scoped, `Sec-WebSocket-Key`, `Sec-WebSocket-Version`, and `Sec-WebSocket-Protocol`, which RFC 6455 §4.1 fixes as a fresh nonce, the version 13, and the sub-protocol §9 fixes, `Sec-WebSocket-Extensions`, which §4.1 makes a negotiation, and `Last-Event-ID`, whose meaning is the W3C Recommendation's resumption.

**[convention]** Those fields, and the processor-owned `content-type`, `content-length`, `accept`, and `host` on every request whether or not it carries a body, cannot be contributed, and a contribution naming one refuses before dispatch; `Last-Event-ID` is never sent because the binding never resumes a stream (§9), and the graphql-ws handshake carries no `Accept` because RFC 6455 §4.1 defines the handshake's own negotiation. The reservation itself is this specification's, because no authority reserves a field against a caller, and it reserves exactly the fields a caller cannot set correctly without owning the connection or the message framing. A proxy and its credentials, `Proxy-Authorization` included, belong to the runtime's transport configuration under Core §1.2.

**[convention]** **Redirects are not followed.** A `Location` field is never acted on. A 3xx response is classified by media type first, like every response under the rules below: one carrying `application/graphql-response+json` is a GraphQL result whatever its status, and any other 3xx is "any other response" and completes the invocation unsuccessfully with no failure data; the same rule governs §9's graphql-sse request, and §9 states the graphql-ws handshake's own rule. RFC 9110 §15.4 leaves automatic redirection to the user agent, so this is this specification's choice, because `location` is the endpoint the document declares, a redirect is the service stating that the endpoint is elsewhere, and relocating a request silently is the downgrade class this specification refuses everywhere else; following would also change a POST to a GET under §15.4's method-change step for some codes, which the draft forbids for a mutation. The losing reading, following the method-preserving 307 and 308 to the same origin, is disclosed.

**[pin]** **`Accept`.** The request carries exactly `application/graphql-response+json, application/json;q=0.9`. The draft says a client SHOULD send that value "If it is not known that the server supports application/graphql-response+json"; a binding never learns a service's capabilities, so the antecedent always holds and the SHOULD is pinned to a requirement. The losing reading, `application/graphql-response+json` alone for a client that knows the service supports it, is never available to this binding and would make classification vary by consumer.

**[convention]** **Classification.** Media types compare by type and subtype, ASCII case-insensitively, and every parameter other than `charset` is ignored. A response carrying `application/graphql-response+json` is a GraphQL result whatever its status; a response carrying `application/json` is a GraphQL result only with a 2xx status; any other response, and any body that is not a well-formed execution result or request error result, completes the invocation unsuccessfully with no failure data, as does a request that yields no response at all (a connection, name-resolution, or TLS failure, or a runtime's timeout, whose value is runtime policy under Core §1.2). The `application/json` rule is this specification's: the draft's informative note observes that intermediaries produce `application/json` failures a client cannot distinguish from a legacy service's, and states no client rule, so this specification fixes the reading the note recommends.

**[pin]** The `application/graphql-response+json` rule is pinned from the draft's lowercase "should" (clients "should process a response using the application/graphql-response+json media type as a well-formed GraphQL-over-HTTP response independent of the HTTP status code") to a requirement, because a status-dependent reading would make classification vary by consumer; the losing reading, trusting only 2xx even under that media type, is disclosed.

**[pin]** **`charset`.** Two authorities speak: the draft says `utf-8` "MUST be assumed" when a recognized GraphQL media type carries no encoding, and RFC 8259 §8.1 says JSON text exchanged between systems "that are not part of a closed ecosystem" MUST be UTF-8, its registration defining no `charset` parameter for `application/json`. This specification decodes every JSON body as UTF-8: an absent `charset`, or one equal to `utf-8` ASCII case-insensitively, is the expected case; any other value declares an encoding both authorities exclude, so the response is not a GraphQL result and completes unsuccessfully with no failure data. The losing reading, honouring the declared encoding, is disclosed and rejected because it would author a non-UTF-8 JSON reading no authority admits; the closed-ecosystem deployment §8.1 exempts is the population the pin declines to serve.

**[convention]** **Within a GraphQL result.** An `errors` entry that is an empty list is read as absent before anything else, because §7.1.1 forbids the entry when no error was raised, so the shape is malformed, but it carries no error and the `data` beside it is the operation's value; the losing reading, discarding a value the caller can use over a serialization slip, is disclosed. Then: a request error result (no `data` entry) completes unsuccessfully with the `errors` list as application-authored failure data; an execution result with non-null `data` and no `errors` completes successfully with `data` as the one output value; an execution result with non-null `data` and `errors` emits `data` as the output value and then completes unsuccessfully with the `errors` list as failure data (RULING-02); an execution result with `data: null` and `errors` carries no value and completes unsuccessfully with the `errors` list; and an execution result with `data: null` and no `errors` completes unsuccessfully with no failure data, because §7.1.5 ties a null `data` to an error that prevented a valid response only as a SHOULD, the draft's note says no circumstance allows the shape, and a null cannot validate against the derived output schema, so no successful reading exists and the authority states no rule. This last rule is decided by response content, which the sibling doctrine otherwise avoids; here the draft itself makes the body the status for its media type, so the content is the declared status and not a sniffed one. The failure-data carriage is this specification's: Core's item 7 places diagnostic preservation outside its completeness test, and §7.1.6's error result format is the reason the `errors` list is admissible as such data.

**[incorporated]** Unknown top-level entries of a result are ignored, as §7.1.8 instructs, and so is the `extensions` entry, which §7.1.7 reserves to implementers and which is never an operation value. The draft's recommended `294` status for a partial result lies inside 2xx and needs no rule.

**[limit]** An execution result means the operation executed, so an unsuccessful completion that emitted `data` is an executed interaction with a partial result, never a failure to execute; retry policy is a runtime concern under Core §1.2, and this sentence exists so that no runtime reads such a completion as licence to execute the operation again.

## 10. Security considerations

**[convention]** The binding never sends an operation document it did not carry, and the only documents it authors are §3.3's capability probe and introspection query, which select introspection fields alone: only the variables map and the configured points of §11.1 vary per invocation, and none of them can alter the document text or the operation selected. Live introspection is an ordinary query against the addressed endpoint, carrying exactly the configured fields and credentials the load carries, an invocation's or a synthesizer's (§3.3). This family defines no executable address form, names no local resource, and runs no composition engine, so it adds no exposure beyond Core [§9](../../openbindings.md#9-security-considerations)'s threat surface and states no normative floor of its own beyond this section.

**[convention]** A credential from runtime context is carried only at the declared endpoint: `location`, and `content.subscriptions.location` for a subscription, because §8's redirect rule leaves no other destination and no authority names one.

**[limit]** No accepted edition and no incorporated transport document defines a security scheme, so this specification infers none; credential acquisition is a runtime concern under Core §1.2, and the carriage of a supplied credential is §8's and §9's.

## 11. Configuration, synthesis, and conformance

### 11.1 Configuration vocabulary

**[configuration point]** The complete binding-specific configuration vocabulary is `httpMethod` (§8), `protocolFields` (§8), `extensions` (§8), `connectionParams` (§9), and `partialEvent` (§9). Every requirement is typed and preflightable from declarations; none appears in the caller envelope or the operation contract, and none supplies target identity. Zero configuration dispatches: POST, no extra fields, no `extensions`, no connection parameters, and `partialEvent: drop`; a subscription additionally needs its carried endpoint, which is document content and not configuration (§3.1). Each point's own ground is stated where it is introduced.

### 11.2 Synthesis boundary and coverage

**[incorporated]** Operation contracts remain protocol-neutral (Core [§5.1](../../openbindings.md#51-operations), [invariant 1](../../openbindings.md#2-core-invariants)).

**[convention]** Synthesis emits one operation per operation definition accounted `represented` or `lossy`; an `invalid`, `excluded`, or `implementation-unsupported` definition yields a coverage entry and no operation (§3.2). One operation per definition because the operation definition is the unit §6.1 of the governing edition executes. Operation-key spelling, the key derived for a lone anonymous operation, and the resolution of a name collision between two sources under Core [OBI-D-04](../../openbindings.md#102-document-rules) are synthesis policy, not binding meaning, since Core states no key policy and this specification states none; §11.4 declares the freedom and what holds across it. The input schema is §6's, the output schema §7's, and the operation description the executable definition's own description when the governing edition's §2.2 carries one.

**[convention]** Synthesis emits no transform: the source-facing value at `inputTransform` is the variables map itself and at `outputTransform` the `data` map of one execution result, so both are already the operation's own values (§6, §7) and none is emitted because no transform has anything to construct. This binding defines no context bindings at either position; evaluation uses Core's closed environment unaugmented (Core [§5.5](../../openbindings.md#55-transforms), [OBI-T-10](../../openbindings.md#103-tool-rules)).

**[convention]** A synthesizer MUST account for every operation definition in the document using exactly one status defined by §3.2, under §3.2's precedence, and MUST record a projection entry for every position §3.3, §6, or §7 names as one: a custom scalar position, an annotative introspection member absent at a reached element, and a deprecated field, argument, input field, or enum value the operation reaches, the four positions being the ones that carry an `isDeprecated` declaration in the governing edition. Root fields of the schema are not interaction units of this binding and receive no status. The status vocabulary and spellings are normative within this binding specification and do not depend on an interface-synthesizer contract; an interface may encode them differently only if it preserves their stated meaning. The accounting is this specification's own because Core states no coverage vocabulary.

**[convention]** Every binding-specific configuration requirement remains in coverage accounting and invocation context, assigned to its represented operation, and MUST NOT enter the operation input schema, because a configuration requirement is not what the operation is about and Core §5.1's `input` is the operation's own value.

### 11.3 Conformance rules

**[convention]** A document conforms to **GQL-D-01** when every source governed by this identifier carries a `location` that is an absolute URI whose scheme is `http` or `https` (§4).

**[convention]** A document conforms to **GQL-D-02** when every such source carries a `content` object with exactly §3.1's members: a string `document`, an optional `schema` that is a string or an object, and an optional `subscriptions` object of exactly `transport` and `location`, the location an absolute URI under §4 whose scheme pairs with the transport as §3.1 states, and no other member.

**[convention]** A document conforms to **GQL-D-03** when each such source's `document` parses as an executable document under §2 of the governing edition and contains no type-system definition or extension, and its `schema`, when carried, passes §3.2's gate 4: a string parses as a `TypeSystemExtensionDocument` under §3.1 of the governing edition, an object carries an object at `data.__schema` and no `errors` entry, each string being a `SourceCharacter` sequence.

**[convention]** A document conforms to **GQL-D-04** when each such source's carried `schema` satisfies §3.2's schema-validity gate: every referenced type is defined, every field and argument has a type, no two types or directives share a name and no definition or extension repeats a field or argument name, input positions carry input types and output positions output types, at most one `schema` definition exists and any schema extension extends a defined schema, and the `query` root operation type is present and is an Object type.

**[convention]** GQL-D-03's schema clause and GQL-D-04 reach carried content only, so a schema-absent source has nothing for them to decide and satisfies them; the live result's gates are the processor's under GQL-P-01 and GQL-P-03, never a document rule's, because Core's fifth invariant makes every document rule decidable from the document and locally available resources and never by reaching the network, and a rule that reached the service would make the verdict vary by the verifier's credentials (§3.3's limit).

**[convention]** A document conforms to **GQL-D-05** when every binding whose source names §1's identifier and carries a `document` that parses (GQL-D-03) carries either a `selector` that is one `Name` under §2.1.8 of the governing edition naming exactly one operation definition of its source's carried document, or no `selector` over a document holding exactly one operation definition (§5.1); a binding whose source carries no parsing document gives this rule nothing to decide and satisfies it.

**[convention]** A synthesizer conforms to **GQL-S-01** when it emits one operation per operation definition accounted `represented` or `lossy`, emits none for an `invalid`, `excluded`, or `implementation-unsupported` definition, and accounts every operation definition with exactly one status under §3.2's precedence (§11.2).

**[convention]** A synthesizer conforms to **GQL-S-03** when it derives every operation's `input` schema as §6 states: the object shape without `additionalProperties`, the type table with its three pins, the `default` image, the nullability composition operations, and by-reference schemas for a type that reaches itself.

**[convention]** A synthesizer conforms to **GQL-S-04** when it derives every query's and mutation's `output` schema as §7 states, the whole `data` map, the collected names with `required` and `additionalProperties: false`, abstract-type branches with `__typename` constants and the single collapse criterion, the leaf pins, custom scalar `format` and `x-graphql-specifiedBy` carriage, and the projection-entry spellings.

**[convention]** A synthesizer conforms to **GQL-S-02** when it emits no transform, keeps every configuration requirement out of the operation input schema, and records a projection entry for every position §3.3, §6, or §7 names (§11.2).

**[convention]** A processor conforms to **GQL-P-01** when it implements §3.2's closed load gates in their stated order and nothing else as a load gate, confines every later defect to §3.2's smallest owning unit, refuses a source as a source only under §3.2's source-refusal rule, and keeps the source, addressability, synthesis-status, and invocation-outcome axes independent, including for a document whose every operation definition is invalid.

**[convention]** A processor conforms to **GQL-P-02** when it interprets the interpreted schema as §3.3 states: a carried string under §3 of the governing edition; a carried object, or the live-introspected result, for exactly the consumed members of the listed query, with a structural absence making every operation reaching the element invalid, an annotative absence making every operation reaching the element lossy with a projection entry, the six edition exceptions read as their earlier edition's declarations, a wrapping chain beyond the listed depth read as a structural absence, and a null at a position §4.2 declares non-null, by type or by its kind comment, read as an absence.

**[convention]** A processor conforms to **GQL-P-03** when, with `schema` absent, it sends exactly §3.3's capability probe and then the introspection query composed from the listed query by removing each capability the probe did not observe, reads a null probe position as the base selection for that type, refuses the source at load, at gate 4, on a request error result, a null `data`, or an `errors` entry at either step, or a composed-query result without an object at `data.__schema`, treats a step that yields no response as an incomplete load that refuses before dispatch, applies gates 4 and 5 to the live result as to a carried one, sends both requests by POST whatever `httpMethod` selects, and sends them with the same configured `protocolFields`, `extensions`, and credentials the load carries, an invocation's or a synthesizer's.

**[convention]** A processor conforms to **GQL-P-07** when it carries a supplied input value as the `variables` map unchanged, unknown keys and explicit nulls included, carries no `variables` member for absent input, and provides no context binding at any transform position (§6).

**[convention]** A processor conforms to **GQL-P-08** when it sends exactly §8's request on the configured lane: the POST body of `query`, `operationName`, `variables`, and `extensions` with `Content-Type: application/json`, or the GET query component in the stated order, `Accept` as pinned, `protocolFields` contributions validated, reserved fields and collisions refused before dispatch, a mutation refused before dispatch under `get`, and no redirect followed.

**[convention]** A processor conforms to **GQL-P-09** when it classifies every response and every absent response exactly as §8 states: media type first, the `charset` pin, `errors: []` read as absent, the five GraphQL-result outcomes including the partial `data` emission, unknown and `extensions` entries ignored, and no re-execution.

**[convention]** A processor conforms to **GQL-P-04** when it dispatches against a pinned `schema` as carried, never re-introspects to repair it, classifies a service's request error against a pin-validated document as that service's own unsuccessful completion under §8, and emits a value the service returns beyond the pin's closed contract as the operation's value under §4's second staleness face.

**[convention]** A processor conforms to **GQL-P-05** when it resolves a present `selector` to the operation definition of that exact name and an absent one to the lone operation definition, refuses at resolution a selector that is not a `Name`, names no definition, or names a shared name and an absent selector over zero or several definitions, resolves a selector naming an `invalid`, `excluded`, or `implementation-unsupported` definition and then refuses before dispatch, and carries the selected operation's name as `operationName` when it is named and none for the lone anonymous operation, on every lane (§5.1).

**[convention]** A processor conforms to **GQL-P-06** when it validates the whole carried document against the interpreted schema under every §5 rule of the September 2025 edition before synthesis or dispatch, accounts every operation definition `invalid` on any failure, treats a position unevaluable for a structural absence, or read by a §5 rule for an absent annotative member, under §3.3 rather than §5, treats a literal at a custom scalar position or under a SHOULD-scoped built-in refusal as coercible, validates meta-field selections against §4.2's introspection types, sends the document as carried, and classifies a service-added rule's rejection under §8 (§5.2).

### 11.4 Permitted variation and stated limits

This section collects the points at which two implementations conforming to `openbindings.graphql@1` may still reach different outcomes, together with what this specification declines to cover. It is an index over rules stated elsewhere in this document and carries no provenance of its own. Rows for §9 arrive with that section.

**Declared freedoms.** At each site the specification states the latitude rather than removing it, and states what survives across implementations that take it differently.

| what may differ | where | what holds across the permitted set |
| --- | --- | --- |
| which credentials and configured fields a synthesizer supplies when loading a schema-absent source, and whether a runtime loads such a source once per invocation or reuses the loaded source across invocations carrying the same credentials | §3.3 | the two introspection requests, their order, and their method are fixed, and both carry the same fields and credentials as each other and, when loaded for an invocation, as that invocation; the contract emitted for a given credential set is fixed and is a claim about that set (§3.3); a reused schema is subject to §4's staleness posture for the reused interval |
| how a processor names or presents a confined defect | §3.2 | the affected unit and responsible position remain observable; no defect-class taxonomy, per-class citation, or per-defect coverage vocabulary is portable |
| where a synthesizer cuts a named type's schema into a referenced schema, and the spelling of the `schemas` or `$defs` key it uses | §6 | the inline structure every reference resolves to is fixed; a type that reaches itself is always cut |
| the order of header fields on the wire, and of cookie-pairs within the `Cookie` field | §8 | every field's name and value are fixed; the request's members and their values are fixed |
| operation-key spelling, the key derived for a lone anonymous operation, and the resolution of a name collision between two sources under Core OBI-D-04 | §11.2 | one operation per represented or lossy operation definition; the emitted input and output schemas and every disposition are fixed |

**Exclusions and reopen triggers.** Each declines an upstream-valid feature behind a stated trigger; rows for §9 arrive with that section.

| excluded | where | reopen trigger |
| --- | --- | --- |
| GraphQL editions before June 2018 | §2 | a real cohort of live services whose introspection refuses the June 2018 base selection |

**Stated limits.** Each is a boundary of this revision's coverage, stated with its reason where it is introduced, and none is a deferral.

| limit | where |
| --- | --- |
| a pinned introspection result taken without `includeDeprecated: true`, or a live result composed from a probe position that resolved to `null`, is indistinguishable from a schema with nothing deprecated at the affected positions, and its derived contract omits what the service still serves | §3.3 |
| a pinned result taken from a September 2025 service by a query that omitted `isOneOf` loses the OneOf constraint | §3.3, §6 |
| a wrapping chain deeper than the listed query's nine `ofType` levels is a structural absence in a pinned or live-introspected result | §3.3 |
| a live-introspected contract is a claim about one credential set; portability across callers is obtained by pinning `schema` | §3.3 |
| acquisition failure at `location` is decided by the address scheme and the runtime; this specification attaches one outcome to an introspection request and one to an operation request that yields no response | §3.3, §4, §8 |
| a pinned `schema` is never repaired by re-introspection; drift of either face is the author's to repair | §4 |
| the carried `document` is sent as carried and never rewritten; no stripping rule exists, so a directive the interpreted schema does not define invalidates the inventory | §4, §5.2 |
| validation runs under the September 2025 rules for every service; the fourteen tightenings over earlier editions are listed, each on its axis | §5.2 |
| a service-added validation rule's rejection is that service's own unsuccessful completion | §5.2 |
| a literal at a custom scalar position, or one a built-in rule refuses only as a SHOULD, is treated as coercible; the service decides it | §5.2 |
| the `input` floor is breached at five disclosed positions: the `4.0` token, the `ID` integer branch, custom scalar positions, `Float` beyond binary64, and a pinned result lacking `isOneOf` | §6 |
| a custom scalar named like a registered JSON Schema format is annotated identically | §7 |
| output `Int` is unbounded; a JSON null in a value cannot be told from an execution-error null in the schema | §7 |
| a `charset` other than `utf-8` makes the response not a GraphQL result; a closed-ecosystem deployment is not served | §8 |
| an unsuccessful completion that emitted `data` is an executed interaction; retry policy is the runtime's | §8 |
| the load gates are a closed ordered set; defects below them confine to their smallest owner; a source refuses as a source only when no addressable target remains | §3.2 |
| how a processor names or presents a confined defect is not portable meaning; an invalid or excluded definition is removed from the effective inventory without erasing its addressable position | §3.2 |
