# `openbindings.openapi` Binding Specification

## 1. Status and identifier

**Status: unreleased first-revision candidate.** This document proposes **`openbindings.openapi@1`** as the first project identifier for this family. The identifier has not been published and this candidate remains mutable. Publication will mint the exact, opaque identifier under core [OBI-B-01](../../openbindings.md#104-binding-specification-rules); later incompatible changes will require a different identifier under [OBI-B-03](../../openbindings.md#104-binding-specification-rules).

The key words "MUST", "MUST NOT", "REQUIRED", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP 14](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals.

## 2. Scope and incorporated authorities

This is the **openbindings project's** candidate binding specification for [OpenAPI](https://spec.openapis.org/) documents. It is authored under this project's authority, not by or for the OpenAPI Initiative. Under that authority, this candidate deliberately incorporates the OpenAPI Specification (OAS) to govern the artifact and the HTTP mechanics it describes — document structure and reference resolution, parameter locations and serialization, request/response media declarations and encodings, server objects and variables, security scheme declarations, and everything else the artifact says about the wire. It likewise incorporates [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) for plain HTTP semantics and the WHATWG HTML server-sent-events processing model at the immutable source snapshot named below for `text/event-stream` framing. This specification chooses close upstream deference and defines only the OpenBindings overlay: how a source carries or addresses an OpenAPI document, how a binding selects an operation, and how caller-facing operation values correspond to an HTTP exchange.

Like the core specification, this document defines portable meaning rather than an invocation API. Its HTTP-exchange, refusal, and ordering language states what acting on the binding denotes and which effects remain conformant; request objects, context negotiation, retries, cancellation APIs, and client architecture remain runtime or SDK surface.

**Normative upstream snapshot.** This candidate accepts only the published OAS editions [3.0.0](https://spec.openapis.org/oas/v3.0.0.html), [3.0.1](https://spec.openapis.org/oas/v3.0.1.html), [3.0.2](https://spec.openapis.org/oas/v3.0.2.html), [3.0.3](https://spec.openapis.org/oas/v3.0.3.html), [3.0.4](https://spec.openapis.org/oas/v3.0.4.html), [3.1.0](https://spec.openapis.org/oas/v3.1.0.html), [3.1.1](https://spec.openapis.org/oas/v3.1.1.html), and [3.1.2](https://spec.openapis.org/oas/v3.1.2.html), each interpreted under its own immutable official text. The string carriage grammar is [YAML 1.2.2](https://yaml.org/spec/1.2.2/). The SSE authority is the WHATWG HTML source at commit [`24c5e48bf66ea61bc199ec6338c81258275ba9c6`](https://github.com/whatwg/html/blob/24c5e48bf66ea61bc199ec6338c81258275ba9c6/source); the living rendered page and later upstream revisions are informative and do not alter this identifier. A later OAS patch or minor is never admitted merely because it matches a supported line; accepting another edition or advancing a normative authority pin publishes a new binding-specification identifier.

**Patch uniformity within a line.** Within one accepted line, this specification's behavior does not turn on the **patch** component of the artifact's `openapi` field; where the patch texts of one line differ, the governing reading is the one consistent with every accepted patch of that line. This is not this specification's own convention — it is the OAS's own instruction to tooling, and **every** accepted edition's §4.1 carries it: "The patch version SHOULD NOT be considered by tooling, making no distinction between 3.0.0 and 3.0.1 for example" in **3.0.0, 3.0.1, 3.0.2 and 3.0.3**, and that same sentence naming 3.1.0 and 3.1.1 in **3.0.4, 3.1.0, 3.1.1 and 3.1.2**. What each §4.1 states *around* that sentence differs by edition, and is quoted here per edition rather than aggregated. **3.0.0 through 3.0.3** state of their own line that "Typically, `.patch` versions address errors in this document, not the feature set" and that "Tooling which supports OAS 3.0 SHOULD be compatible with all OAS 3.0.\* versions". **3.0.4, 3.1.0, 3.1.1 and 3.1.2** state instead that "`.patch` versions address errors in, or provide clarifications to, this document, not the feature set", and name the 3.1 line; 3.0.4's own §4.1 is the 3.1 line's paragraph throughout, down to its "(for example 3.1)", so 3.0.4 carries no 3.0-line compatibility sentence at all, and the instruction governing an artifact that declares 3.0.0 through 3.0.3 is the one in **its own** text, where it names its own line. On the 3.0 line the consequence therefore rests only on what those four editions do carry: a `.patch` release of the line addresses this document rather than the feature set, tooling supporting the line is to be compatible with every `3.0.*` version, and the patch component is not to be considered — so where a later `3.0.*` patch describes a mechanism an earlier one left undescribed, the described reading is the one consistent with every accepted patch of that line, and emitting different bytes on either side of a patch boundary is exactly the distinction those four editions instruct against. On the 3.1 line those editions' own "or provide clarifications to" states the same thing directly. Reading an accepted edition under its own immutable text therefore **includes** reading that instruction, and the edition-scoped rules elsewhere in this document are consequently stated per line rather than per patch: the reference-traversal branches of [§6](#6-composition), and in [§9.2](#92-request-and-response-media) the form-path selection predicate, the 3.1 line's single `contentType` default table, and the 3.0 line's five-edition type-absent part refusal.

**That clause governs how an accepted edition is READ. It does not widen WHICH editions are accepted.** The accepted domain remains exactly the eight editions enumerated above, and discrimination remains the artifact's own `openapi` field ([§3](#3-accepted-source-representations)): a value outside that enumeration — including any other 3.0 or 3.1 patch, published or not — is refused loudly at load (**OAPI-P-01**), and nothing in the patch-uniformity clause admits one. The two statements answer different questions: which artifacts this specification governs at all, and how the ones it governs are interpreted. Compatibility *between* this specification's revisions is likewise untouched; adding an edition remains a new identifier under [OBI-B-03](../../openbindings.md#104-binding-specification-rules).

OpenAPI artifacts are substantially complete as actionable descriptions — routing, media types, and status declarations are native — so this specification's interpretation points ([§9.3](#93-servers-and-the-target-url), [§9.4](#94-configuration-points)) are fewer and narrower than an incomplete family's (compare [`openbindings.usage@1`](../usage/openbindings.usage.md)).

## 3. Accepted source representations

This specification accepts the **exact OpenAPI editions listed in §2** — 3.0.0 through 3.0.4 and 3.1.0 through 3.1.2 — in two carried representations:

- **Object** `content`: the parsed OpenAPI document as a JSON object.
- **String** `content`: the document's source text. This specification pins the string grammar — its own pin, not an OAS mandate: string content parses as **YAML 1.2.2** under the OAS's JSON-compatibility recommendations, of which JSON is a valid subset, so one grammar covers both spellings deterministically. Duplicate mapping keys are refused loudly.

  **Scalar resolution is the OAS's own answer, restated for its consequence.** Every accepted edition requires that "Tags MUST be limited to those allowed by [YAML's] JSON schema ruleset" (OAS §4.2), which is YAML 1.2.2 [§10.2.1](https://yaml.org/spec/1.2.2/#1021-tags)'s null, boolean, integer and float alongside the failsafe map, sequence and string. Untagged scalars therefore resolve by YAML 1.2.2 [§10.3.2](https://yaml.org/spec/1.2.2/#1032-tag-resolution)'s core tag resolution — its null, boolean, integer and float patterns, with every other plain scalar a string. YAML 1.1's implicit timestamp, merge, binary, omap, pairs and set types are outside the permitted set: a date- or time-shaped scalar (`2020-01-01T12:00:00Z`, `2020-01-01`, `12:30:45`) is a **string**, and an explicit tag naming an unpermitted type is refused rather than resolved. A resolved value with no JSON image — `.inf`, `-.inf`, `.nan`, which §10.3.2 resolves to floats — refuses the artifact, because an OpenAPI document is a JSON object (OAS §4.2) and the YAML spelling exists to round-trip with JSON; substituting `null` would silently replace a declared value (**OAPI-P-01**).

Discrimination is the artifact's own **`openapi` field**: one of the exact accepted values is interpreted under that edition's OAS text; every other value (including a future 3.0 or 3.1 patch, OpenAPI 3.2, and Swagger 2.0's `swagger` field) is refused loudly at load (**OAPI-P-01**). No other representation is defined; there is no non-textual artifact form.

**Whole-source refusal is not one thing.** This specification answers it in the same three parts, in the same order, as every project binding specification (the [catalog README](../README.md)'s "Whole-source refusal, and what it is not"), and the three parts are exhaustive: no condition outside them refuses a whole source under this identifier (**OAPI-P-01**).

**1. Load gates are enumerated, and the enumeration is closed.** A condition that fires before the artifact has a JSON image, or before its governing edition is determined, is a member of this closed set — each already stated above, gathered here so the set is readable as one:

- **The accepted-representation grammar.** String `content` whose bytes are not a well-formed YAML 1.2.2 stream under the grammar pin above. The verdict is a property of the bytes against YAML 1.2.2's own productions, never of any parser's error recovery: a stream one library happens to repair is still not a well-formed stream, so this member's outcome cannot vary between conformant implementations, and that parser-independence is deliberately part of the member rather than an accident of it.
- **Scalar resolution and key uniqueness.** The string-content refusals stated above: duplicate mapping keys; an explicit tag naming an unpermitted type; a resolved value with no JSON image (`.inf`, `-.inf`, `.nan`).
- **The root's shape.** A parsed `content` whose root is not a JSON object. An OpenAPI document "is itself a JSON object, which may be represented either in JSON or YAML format" (OAS §4.2; every accepted edition carries the sentence), so a root sequence or scalar presents no `openapi` member to discriminate and no position any rule of this specification can read.
- **The edition gate.** The discrimination rule above: `openapi` absent or outside the eight accepted editions.

These cannot be derived from any per-unit rule, because there is no inventory to reason over until they have passed — asking which units survive a defect that prevents the document from existing has no answer, and manufacturing one means inventing a value the artifact does not carry. The edition gate is always evaluated first: no unit-level reasoning exists until the governing edition is determined.

**2. Below the load gates there is exactly one whole-source refusal, and it is derived, not enumerated.** Once the artifact has a JSON image and a determined edition, every defect confines to the smallest unit that owns it — a defect in a position no operation's closure reaches destroys no target and never widens. The source refuses only when **no addressable target remains**: no conformant `ref` ([§7](#7-ref)) resolves to an operation object, because every position that would have carried one is defective under the governing edition. This single rule replaces both "the artifact declares no addressable target" and "the artifact declares addressable targets and every one of them is destroyed" — an empty set has no survivors, so one sentence covers both. Specific shapes that trigger it — a `paths` value that is an array or a bare reference, a path item that is an array or a string, an operation position holding a string — are illustrations, never a closed list. Where the triggering defect is a missing `paths` member altogether, the upstream requirement violated is per line, because the accepted editions do not state one requirement: **3.0.0 through 3.0.4** make `paths` a REQUIRED fixed field of the OpenAPI Object, while **3.1.0** requires that the document "contain at least one paths field, a components field or a webhooks field" and **3.1.1** and **3.1.2** state the same disjunction as "at least one paths field, components field, or webhooks field". The derived rule itself is edition-neutral: it turns on what remains addressable, not on which sentence was violated.

  **"Addressable" is the test, and it is deliberately not "representable."** A target that resolves and is then unusable for another reason — no admissible request media candidate ([§9.2](#92-request-and-response-media)), an unavailable prerequisite, an alternative this revision excludes — is still an addressed target. It refuses at invocation, or is accounted as an exclusion, and never here. Whether a target is ultimately *represented* is a synthesis outcome ([§10](#10-conformance)) and may differ between conformant implementations; whole-source refusal must not.

  **What the artifact never declared is not a defect.** An artifact that conformantly declares no target is accepted and yields an interface with no operations: the rule reaches the artifact whose targets were destroyed, never the artifact that had none to begin with. The incorporated editions state that permission themselves, and each is quoted under its own text. An empty Paths Object is conforming in all eight — "The Paths Object MAY be empty." in **3.0.0 through 3.0.3**, "The Paths Object MAY be present but empty" in **3.0.4, 3.1.0, 3.1.1 and 3.1.2** — as each edition's Paths Object section also states: "The Paths MAY be empty, due to ACL constraints" (**3.0.0 through 3.0.3**), "The Paths MAY be empty, due to Access Control List (ACL) constraints" (**3.1.0**), "The Paths Object MAY be empty, due to Access Control List (ACL) constraints" (**3.0.4, 3.1.1, 3.1.2**). And an empty Path Item Object is conforming in all eight: "The Path Item Object MAY be empty." Neither triggers the derived rule.

**3. This revision declares no source-scope exclusion.** A revision MAY decline an upstream feature at source scope, as an explicit coverage limit with its reason, where it cannot confine the consequence — [`openbindings.usage@1`](../usage/openbindings.usage.md)'s load-time refusal of `include`, `mount`, and the configuration-file and external-parse lanes (**USAGE-P-07**, **USAGE-P-08**) is the family pattern. This specification currently needs none: no OpenAPI feature this revision declines to bind determines the artifact's own inventory or imports an execution or filesystem authority the revision does not define, so every declined feature is confined and accounted where it lives — webhooks and callbacks as [§7](#7-ref)'s addressability definition, schema-guided XML generation as [§9.2](#92-request-and-response-media)'s excluded lane — and no whole source is refused by exclusion.

## 4. `location`

A source's `location`, when present, is an **absolute URI addressing the OpenAPI document itself** (**OAPI-D-02**) — `https://example.com/openapi.json`, `file:///srv/api/openapi.yaml`. Dereferencing it yields an accepted representation ([§3](#3-accepted-source-representations)). A bare filesystem path is a relative reference in form and is not a conformant `location` (core [OBI-D-05](../../openbindings.md#102-document-rules)).

## 5. `content`

A source's `content`, when present, MUST be one of the two accepted representations of [§3](#3-accepted-source-representations): the parsed document object, or its source text as a string (**OAPI-D-01**). No other JSON type is an accepted `content` value under this specification.

## 6. Composition

When `content` is present it is the artifact the processor interprets, per the core's content-primacy floor ([§5.4](../../openbindings.md#54-sources)).

A co-present `location` is the document's origin, and it serves as the embedded artifact's **base URI**: references internal to the embedded document (relative `$ref`s, relative server URLs) resolve against it per the OAS's own reference-resolution rules, exactly as they would had the document been retrieved from that address. The base travels in the OBI, so resolution is identical everywhere the OBI goes; the OBI's own retrieval URI is never a base (core [§7](../../openbindings.md#7-reference-resolution)). Embedded content with **no** co-present `location` has no base and MUST be self-contained: every internal reference resolves without one (bundle before embedding).

Self-containment is RECOMMENDED even when a `location` is present: a document whose embedded artifact leans on its base for `$ref` resolution requires that address to be reachable to interpret, which reintroduces the network dependence embedding exists to remove.

For a `location`-only source, the document's base URI is the `location`, per the OAS.

**Reference scope.** A reference that leaves the current document composes the value at the referenced JSON Pointer together with that value's transitive closure of references, and nothing else. This is the incorporated authority's own answer rather than an addition to it, on both edition lines: under OAS 3.0.0–3.0.4 the Reference Object is defined by [JSON Reference], which denotes the value a pointer identifies and says nothing about the document that value was found in; under OAS 3.1.0–3.1.2 §4.6 makes a reference's fragment a JSON Pointer resolved "per the fragment resolution mechanism of the referenced document", and [JSON Schema 2020-12 Core] §8.2.3 gives `$ref` the same reach — "this allows the possibility to externalise or divide a schema across multiple files" — with §9.2.1 tying a pointer fragment to "the structure of the schema document". Two consequences are normative here because processors have been observed to assume otherwise. A referenced document is **not** required to be a conforming OpenAPI Document — the OAS's own Reference Object examples address a bare schema file with no `openapi`, `info`, or `paths` — so a target is never refused for failing a conformance test the OAS does not apply to it. And a defect **outside** the composed closure does not make the referencing artifact unresolvable, however the referenced document is stored: only a reference reachable from the composed pointer, and unresolvable there, does. Reachability follows the artifact, so adding an operation that reaches further into a shared schema library can make a previously resolvable artifact unresolvable; that is the pointer's meaning, not a defect in it.

**Reference traversal.** A separate question, asked by the same pointer: what a reference's fragment means when its own path runs **below** another reference — `#/components/schemas/Alias/properties/name`, where `Alias` is a `$ref` object. The accepted editions answer it differently, and each is read under its own text (§2), so this specification states both branches rather than one average of them.

- **Under OAS 3.0.0–3.0.4 the reference standing in the path is resolved and evaluation continues into the target.** These editions process `$ref` as per [JSON Reference] twice over: §4.6 "Relative References in URLs" ("Relative references used in `$ref` are processed as per JSON Reference, using the URL of the current document as the base URI") and the Reference Object ("The Reference Object is defined by JSON Reference and follows the same structure, behavior and rules", and "reference resolution is accomplished as defined by the JSON Reference specification and not by the JSON Schema specification"). [JSON Reference] states its own basis as transclusion, "the use of a target resource as an effective substitute for the reference" (§1); requires that "Any members other than `"$ref"` in a JSON Reference object SHALL be ignored" (§3), so such a node has no other denotable members at all; and resolves it to the referenced value (§4).
- **Under OAS 3.1.0–3.1.2 it is not, and the reference is unresolvable.** §4.6 — titled "Relative References in URIs" in 3.1.0 and "Relative References in API Description URIs" in 3.1.1 and 3.1.2 — states that "If a URI contains a fragment identifier, then the fragment should be resolved per the fragment resolution mechanism of the referenced document. If the representation of the referenced document is JSON or YAML, then the fragment identifier SHOULD be interpreted as a JSON-Pointer as per [RFC 6901]" — over the referenced document, not over a substituted image of it. The 3.1 Schema Object "is a superset of the JSON Schema Specification Draft 2020-12", whose [JSON Schema 2020-12 Core] §8.2.3.1 makes `$ref` "an applicator … Its results are the results of the referenced schema", with the note that "other keywords can appear alongside of `"$ref"` in the same schema object": nothing is substituted, the referencing node keeps its own members, a token naming none of them resolves no concrete value, and [RFC 6901] §4's error condition arises. No 3.1 edition incorporates [JSON Reference].

A `$ref` object that itself declares the next token as a member is answered per branch, because only one branch gives the sibling a meaning. Under **OAS 3.1.0–3.1.2** it is not a traversal: keywords sit beside `$ref` in 2020-12, the node keeps its own members, and the token names the member of the node in hand. Under **OAS 3.0.0–3.0.4** the declared sibling is not denotable at all — [JSON Reference] §3 requires members other than `$ref` to be ignored, so such a node has no other denotable members, as the 3.0 branch above concludes — and the token therefore traverses into the reference target exactly as it would beside no sibling.

The governing edition is the **artifact's own** — the `openapi` field of the document the source addresses or carries ([§3](#3-accepted-source-representations)) — because a referenced document need not be an OpenAPI Document at all and so need not declare one. Which unit an unresolvable reference refuses is not decided here; it is whatever this specification's refusal rules make of any other unresolvable reference.

## 7. `ref`

A binding's `ref` is REQUIRED — the OAS defines no whole-artifact invocation — and MUST be a JSON Pointer of the form `#/paths/<escaped-path>/<method>`, addressing an **operation object**: the path segment carries [RFC 6901](https://www.rfc-editor.org/rfc/rfc6901) escaping (`/` → `~1`), and `<method>` is one of the OAS's HTTP method keys, **lowercase exactly as the artifact spells them** (**OAPI-D-03**). `#/paths/~1tasks/post` addresses the POST operation on `/tasks`.

The pointer is a **verbatim string**. Its `#/` shape is JSON Pointer notation, not an invitation to URI processing: no percent-decoding is ever applied, at authoring or at resolution. Each addressable operation has exactly one conformant spelling — the RFC 6901-escaped form above — and a `ref` matches it byte-for-byte, extending the core specification's literal-form doctrine (core [§7](../../openbindings.md#7-reference-resolution)) to this family's selector. A percent-encoded rendering of that spelling (`#/paths/~1users~1%7BuserId%7D/get` for `#/paths/~1users~1{userId}/get`) is not the spelling and denotes nothing.

**A path item that is a `$ref` (including a 3.1 `components.pathItems` target) is resolved before the method segment evaluates**, so bundled artifacts using path-item references stay addressable, on every accepted edition. That is **this specification's rule**, not the OAS's: no accepted edition says anything about a pointer whose path runs through a reference, and it does not have to, because this pointer is not the artifact's. Core [OBI-B-02](../../openbindings.md#104-binding-specification-rules) item 5 assigns `ref` syntax and resolution to the binding specification, and [RFC 6901] §7 hands the disposition of a pointer that resolves nothing to "an application of JSON Pointer", which it says SHOULD specify that disposition — here, that application is this specification. The artifact's own `$ref` fragments are a different pointer with a different owner, and their traversal is decided by the incorporated edition ([§6](#6-composition), "Reference traversal"); the two answers coincide on the 3.0 line and deliberately differ on the 3.1 line, because only one of them is the OAS's to decide.

A well-formed `ref` whose path or method is absent from the resolved artifact makes the binding unresolvable; verification requires the artifact, per the core's partial-verification posture.

Only `paths` operations are addressable. **Webhooks and callbacks are excluded** from this candidate: they describe inbound calls the service makes to the consumer, an interaction this revision does not bind. The exclusion is a definition, not an open item.

## 8. Target and interaction

The binding denotes the addressed operation as **one HTTP exchange** against the resolved server ([§9.3](#93-servers-and-the-target-url)).

**Success classification and response declaration lookup are separate.** Classification is the final-status 2xx rule of [§9.4](#94-configuration-points). After a response arrives, its governing OAS Response Object is selected exactly as the OAS Responses Object declares: the exact status-code entry first, then the matching `2XX` range entry, then `default` when neither more-specific entry exists (**OAPI-P-06**). Thus `default` can govern the shape and media of a successful 2xx response; it does not itself make a non-2xx response successful. A **success response declaration** below means any entry that can govern at least one 2xx status under that lookup: an exact 2xx entry, `2XX`, and — unless `2XX` covers the whole class — `default`.

The interaction shape is bounded by declaration and selected by framing (**OAPI-P-06**):

- An operation is **streaming-capable** iff at least one media declaration in a success response can match a concrete media type whose type and subtype are `text/event-stream`: an exact declaration (its declared parameters included), `text/*`, or `*/*`. Capability is static: a consumer knows from the artifact alone whether streaming can occur.
- For an actual successful response, the exact status first selects its governing Response Object by the lookup above. Only that object's `content` map can govern framing. An actual concrete `text/event-stream` representation selected by an exact or range declaration there yields a **server-streaming** interaction; every other selected concrete representation yields a **unary** interaction. A media declaration belonging only to a different status, response range, or shadowed `default` entry is irrelevant to this response.
- A non-empty successful response with no governing Response Object, or whose concrete `Content-Type` does not select one declaration in that object's `content` map, contradicts the artifact and is a protocol error. An empty body needs no media declaration and is unary. Thus a `text/event-stream` response is never accepted merely because SSE appears somewhere else in the operation.

A **unary** interaction carries zero or one caller input value and **zero or one output value**: a non-empty successful response emits one decoded value, while an empty successful response completes without emitting a value. Absence of a representation is not the JSON value `null`; a non-empty JSON body whose bytes spell `null` emits that explicit value. A **server-streaming** interaction likewise carries zero or one caller input value; each received SSE event emits one output value per the WHATWG processing model: the event's `data` lines joined with U+000A form the event's text; a block that carried no `data` line — comment-only blocks included — dispatches nothing and emits no value, while a received `data` line whose value is empty dispatches like any other, so a lone empty `data` line emits the empty string; and the `event`, `id`, and `retry` fields **never enter the abstract invocation**. An artifact runtime or HTTP/SSE tool may retain those fields below the OpenBindings bridge. Stream end — as HTTP message framing determines it — completes the interaction; abnormal termination — transport failure before stream end — is a failure outcome, and output values already emitted **stand**. NDJSON and other streaming framings are excluded from this candidate as interaction shapes: no framing authority for them is incorporated in [§2](#2-scope-and-incorporated-authorities), so per-record extraction rules would be authored rather than incorporated. Such a response body remains an ordinary representation under [§9.2](#92-request-and-response-media)'s response lanes.

## 9. Operation-boundary correspondence

### 9.1. Input mapping

The operation-facing input is one JSON object (or absent). Parameter and body values are application data; their HTTP destinations are binding facts and do not become required operation property names, schemas, or caller-visible wrappers. The source-facing value at the binding's input-transform boundary has two representations (**OAPI-P-03**):

1. A **flat object** MAY be used when every effective parameter and every property in a finite, named selected request-body property set has a unique name. Fields map by that name, preserving revision 1 behavior.
2. A **routed one-tuple** carries independent source fields when names collide, an explicitly dynamic object body as one application value, or a declaration-complex JSON body as one complete application value. It has the exact form below. This representation is binding-private: an OBI may produce it with core `inputTransform`; it is not an operation contract and synthesis MUST NOT copy its HTTP identity members into the operation schema.

The one-item array makes the routed representation structurally disjoint from the object-shaped application input. Therefore `$openbindings` and even an otherwise envelope-shaped application object always remain ordinary flat application fields; no valid caller property can be mistaken for private routing data. The tuple exists wholly below the operation boundary.

```json
[
  {
    "$openbindings": "openbindings.openapi@1",
    "value": { "account": "a", "request": "q", "record": "b" },
    "parameters": [
      { "in": "path", "name": "id", "field": "account" },
      { "in": "query", "name": "id", "field": "request" }
    ],
    "body": {
      "properties": { "id": "record" },
      "whole": "payload"
    }
  }
]
```

`value` is the transformed application object. Each `parameters` entry identifies one effective OAS parameter by its exact name-plus-location identity and names the field in `value` that supplies it. Duplicate entries for one identity refuse. `body.properties` maps each artifact body-property name to its field in `value`; `body.whole` names the field used for a selected non-object body, an explicitly dynamic object body, or a declaration-complex JSON body. The selected candidate determines which body form applies. A referenced field's presence is distinct from its value, so explicit JSON `null` is preserved. A malformed routed tuple, an entry that does not identify a declaration, or a supplied field with no derivable destination refuses before dispatch.

Deterministic generation of the operation-facing field names and the transform expression is a synthesis concern, not a rule of this specification. A synthesizer can therefore retain application names and descriptions, choose collision-free protocol-neutral names, and keep the concrete routing solely in the binding transform. For an explicitly dynamic or declaration-complex JSON body, synthesis preserves the complete resolved schema as one operation property (for example, the protocol-neutral `payload` field shown above) rather than pretending that its possible runtime keys form one finite operation-property set. The binding specification defines the transform's source-facing representation because core [§5.5](../../openbindings.md#55-transforms) requires that boundary to be portable; it does not dictate an OBI generator's operation-key or property-naming policy.

The remaining mapping is incorporated or declaration-driven:

- The effective parameter set merges path-level and operation-level `parameters`, operation-level winning on the same name-and-location identity, and applies the OAS ignored-header rule for `Accept`, `Content-Type`, and `Authorization`. The rule's name comparison is read case-insensitively — the rule's own sentence keys on the case-sensitive `name` field, but every accepted edition's parameter-locations text makes header field names case-insensitive, so a differently-cased spelling denotes the same ignored header.
- `path`, `query`, `header`, and `cookie` parameters ride their OAS destinations. Serialization follows the OAS `style`/`explode`/`allowReserved` and `content`-form rules wholesale (**OAPI-P-02**).
- Same-named parameters in different locations and parameter/body-property collisions remain independent and are carried by distinct routed fields; no value is duplicated or identified by inference. Effective header parameters whose names differ only by ASCII case remain unresolvable because HTTP field names are case-insensitive and the wire itself supplies no two distinct destinations; the defect is parameter-owned, so it excludes its target under the exclusion-unit rule below.
- A field matching no parameter or declared body-property route passes through under its own name only for a flattened object-valued JSON-family body, where the artifact supplies that destination without invention. It refuses for no body, a whole-value body, multipart, and form-urlencoded candidates. Runtime members of an explicitly dynamic object and every member of a declaration-complex JSON value belong to that whole application value, not to unmatched top-level operation fields.
- Object-or-not is decided from the resolved candidate declaration. Direct `properties` and explicit object type are object-shaped; `allOf` contributes the recursively collected property union; reference identities are visited once. A typeless schema is non-object.
- An object is **explicitly dynamic** when its resolved top-level schema, including any `allOf` member, declares at least one `patternProperties` entry or explicitly declares `additionalProperties` as `true` or as a Schema Object. The trigger keywords are read under the governing edition's dialect: on the 3.0 line the Schema Object is a defined subset whose own text makes unmentioned JSON Schema keywords "strictly unsupported" (every 3.0 edition), so `patternProperties` there is a keyword the dialect strips of meaning and decides as if absent — exactly as [§9.2](#92-request-and-response-media) treats the Content vocabulary on that line — and the 3.0-line trigger is an explicit `additionalProperties` alone. Such a body uses `body.whole`; it is never flattened. A merely omitted `additionalProperties` does not select this revision's dynamic carriage, even where the governing schema dialect gives the keyword an open default. This narrow trigger preserves the immutable flattened contract for ordinary named-property artifacts while closing every case in which the author explicitly declared runtime property names.
- A schema is **declaration-complex at the JSON body boundary** when its resolved top level, including an `allOf` member, contains `oneOf`, `anyOf`, `not`, `if`, `then`, or `else`, declares at least one `dependentSchemas` entry, or carries an explicit `unevaluatedProperties` (any value). These keywords are likewise read under the governing edition's dialect: the 3.0 line's Schema Object carries `oneOf`, `anyOf`, and `not` only, so `if`/`then`/`else`, `dependentSchemas`, and `unevaluatedProperties` are strictly-unsupported keywords there and decide as if absent. For an exact JSON-family media declaration, that complete schema and value use `body.whole`; no branch is selected and no body property is routed independently. JSON serialization applies to the supplied value exactly as it does for every other JSON-family body. This rule preserves the authored validation contract and needs no value-dependent binding logic. It does not define form, multipart, text, raw, or media-range serialization for such a schema; those candidates remain inadmissible unless another rule independently supplies faithful carriage.

**A style-lane declaration carrying a member with no defined expansion is refused at admission, and the exclusion is accounted** (**OAPI-P-02**). The lane is the one `form`, `spaceDelimited`, `pipeDelimited` and `deepObject` serve: a `schema`-form `query` or `cookie` parameter, and a form-body property whose Encoding Object writes an explicit control ([§9.2](#92-request-and-response-media)). A member offends when its resolved schema is `object` or `array` — an array whose resolved `items` resolve to either, or an object one of whose resolved property schemas does. Each of those styles expands a composite value exactly one level, so every member becomes a member *string*, and a member that is itself composite has no representation. **The refusal is decided by the declaration and not by a supplied value**: every value conforming to such a declaration carries that member as a composite, so the unit is excluded during synthesis with a recorded reason rather than published as represented and refused at invocation. A member declaring no type, a choice declaring more than one non-null branch, and an object declaring no members at all are **not** refused — their runtime values may be scalars, and a declaration-keyed rule must not reach a declaration that admits one. The single-non-null-branch and array-valued-`type` collapses of [§9.2](#92-request-and-response-media) apply before the member kinds are read, so the nullable spelling of a declaration is classified as the declaration it restates.

**Each claim below names the editions whose own text states it**, because [§2](#2-scope-and-incorporated-authorities) reads every accepted edition under its own immutable text and does not aggregate them. The style rows are §4.7.12.3 on the 3.0 line and §4.8.12.3 on the 3.1 line. The `form` row cites the incorporated authority by section on **every** accepted edition — "Form style parameters defined by [RFC6570] Section 3.2.8" — and [RFC 6570] §2.4.2 applies "the expansion process … to each member of the composite as if it were listed as a separate variable", whose expansions append member strings; a member that is itself a list or an associative array has no expansion there. `spaceDelimited`, `pipeDelimited` and `deepObject` cite **no** RFC section in any accepted edition. For `deepObject` the row's own text differs by line: **3.0.0, 3.0.1, 3.0.2, 3.0.3 and 3.1.0** read "deepObject | object | query | Provides a simple way of rendering nested objects using form parameters", beside a worked example whose members are all scalars (`color[R]=100&color[G]=200&color[B]=150`); **3.0.4, 3.1.1 and 3.1.2** read "Allows objects with scalar properties to be represented using form parameters. The representation of array or object properties is not defined." The five earlier editions' row therefore **governs this case and does not define it**, and the three later ones say so in as many words. On no accepted edition does an authority this specification incorporates supply a representation for a composite member, and **this specification authors none either**: the declaration is refused and the exclusion is accounted. Whether to expose an interpretation choice for these declarations is left open to a later revision rather than settled by a default here. This clause covers the four styles named above; `simple`, `label` and `matrix` are not addressed by it.

**Which unit the exclusion names is the smallest unit that owns the defect.** A parameter has no sibling alternative to fall back to, so an offending parameter excludes its **target** and the operation is not published. A form-body property's enclosing request media does have siblings, so an offending property excludes that **alternative**, and the operation is represented through another candidate or not at all.

**Required declarations.** Exactly two conditions refuse before dispatch, and each applies to absent and supplied-but-incomplete input alike: a required request body with no value to carry — the artifact's own `requestBody.required` — and an unsupplied path parameter, because the URL cannot be built. Every other missing declaration is sent as supplied, whether the input was absent or an object that omits it: no accepted edition imposes a client-side enforcement duty for a non-path required parameter, and the server's validation remains authoritative.

**Body and candidate election.** Each supported media candidate is evaluated using its own resolved Media Type Object and schema. A configured concrete `requestMedia` can cause a media-range declaration to govern; its schema, not another declaration's schema, then decides routing and admissibility. A JSON-family object body with no fields is `{}` when required and omitted otherwise. No-body invocation bypasses media selection and emits neither a body nor `Content-Type`.

### 9.2. Request and response media

Media types throughout this section are parsed under RFC 9110 — the editions' own citation for the content-map grammar is its predecessor RFC 7231, and this specification reads the materially identical rules at their pinned successor, its §2 HTTP-semantics authority. Type, subtype, and parameter names compare case-insensitively; parameter ordering and quoted-string versus equivalent token spelling do not create distinct identities; parameter values compare under the parameter's governing media-type semantics, and otherwise byte-for-byte after quoted-string unescaping. Two keys in one OAS `content` map that denote the same parsed media type are a **normalized collision** and make that request or response candidate set unresolvable — no first-key rule is invented.

Parameters are never discarded. A concrete media type or media range **matches** a concrete selected media type when its non-wildcard type and subtype agree and every parameter present in the declaration is present with the same value in the concrete selection; additional selected parameters do not disqualify it. Matching declarations are ordered first by range specificity — exact type/subtype, then `type/*`, then `*/*` — and then by greatest number of declared parameters. If several distinct declarations tie at the greatest specificity, selection is ambiguous and refuses rather than depending on content-map order. This most-specific-subset rule is an explicitly labeled OpenBindings convention, and the label covers all of it: OAS requires the most-specific matching content entry, but neither it nor HTTP supplies the subset-matching predicate, the parameter-count order, or the equal-specificity tie-break this boundary needs — those three are this specification's.

For **request selection**, `requestMedia`, when supplied, is one concrete media type. It selects the most-specific matching declaration under the rule above, and that declaration's Media Type Object governs the value. The emitted `Content-Type` is the configured concrete value, including its parameters; a range key is never emitted as a field value. Without configuration, a processor may choose any admissible **concrete** declaration in the artifact, preserving the artifact's unordered alternatives. A range alone supplies no concrete representation, so `requestMedia` is required whenever that range will carry a body. For a **required** range-only body, the requirement is knowable during preflight: before reading caller input, a processor requests a retryable choice and performs no dispatch; under the project's portable invocation interface this is `CONTEXT_REQUIRED` with one `config.value` requirement for the `requestMedia` point. An optional range-only body still bypasses media selection when the caller supplies no body. If the caller supplies that optional body without a prior effective choice, the invocation refuses before dispatch; whether and how a runtime then acquires the choice and re-invokes is implementation surface this specification does not assume. Object shape, examples, or payload bytes never imply `application/json`. Once a concrete value is supplied, a value that matches no declaration, selects an unsupported lane, or is inadmissible for the input is likewise a pre-dispatch refusal.

For **response matching**, the actual `Content-Type` is the concrete selected media type. It selects the most-specific matching exact or range declaration under the same range-specificity and parameter-subset rule used for configured requests. The selected declaration's Media Type Object governs decoding; the actual field value supplies the concrete framing and is not exposed as an operation value. An absent, unmatched, normalized-colliding, or equally specific ambiguous declaration is a protocol error; a non-empty response carrying no concrete `Content-Type` at all is the absent case — this specification does not adopt RFC 9110's permission to assume `application/octet-stream`, because a silent assumption is the guess the loud-refusal posture exists to prevent. No body bytes are inspected to repair or replace the selection.

When the invocation will emit a body, the governing declaration is selected from the operation's **declared** `requestBody.content` under the **`requestMedia`** configuration point (**OAPI-P-04**, [§9.4](#94-configuration-points)). Once a concrete media type and governing declaration are known, this candidate defines these request carriage lanes:

- Exact or range-selected `application/json` and `+json` types serialize the application value as JSON.
- `multipart/form-data` and `application/x-www-form-urlencoded` serialize object fields under the OAS's `encoding` rules. For an explicitly dynamic object, each runtime member name resolves its effective property schema by applying an exact `properties` schema and every matching `patternProperties` schema, or the `additionalProperties` schema when neither exact nor pattern schemas match; applicable constraints contributed by `allOf` all apply. The resolution keywords are read under the governing edition's dialect ([§9.1](#91-input-mapping)): on the 3.0 line `patternProperties` has no meaning, so the chain there is `properties`, then `additionalProperties`. JSON Schema regular expressions use the governing OAS edition's dialect. An OAS Encoding Object can govern only a statically named property as required by OAS; a dynamic member with no such entry uses the OAS default encoding. A resolved property schema — statically named or a dynamic member's effective schema — whose top level declares exactly one `anyOf` or `oneOf` and no other applicator, with branches comprising one non-null branch beside branches declaring `{ "type": "null" }` alone, is interpreted as that non-null branch's declaration: the artifact declared exactly one carriage, so the branch's schema governs the member's serialization. A supplied JSON `null` for that member elides it from the emitted form — an omitted optional part, not a serialized null. The elision is **this specification's convention**, stated as its own: the OAS's later editions say outright that determining how to handle null values "depends on how null values are being serialized", naming entire omission as one option, so the upstream leaves the choice open — and the elision agrees with the authorities each serialization path points at, RFC 6570 expanding nothing for an undefined variable and RFC 1866 permitting fields with null values to be omitted. The collapse itself is interpretation of the declared schema, not value-dependent branch selection; with a single non-null branch there is no alternative to choose. A choice declaring more than one non-null branch does declare value-dependent alternatives, leaves no single faithful form carriage, and refuses. Under the 3.1 line, an array-valued `type` whose members are one non-`"null"` type beside `"null"` is the **same declaration** and takes the same collapse, with the same null elision and with its sibling keywords still applying; two or more non-null members refuse exactly as a multi-branch choice does. This clause restates an incorporated consequence rather than adding a convention: the 3.1 Schema Object is a JSON Schema 2020-12 schema, and [JSON Schema 2020-12] §6.1.1 defines an array-valued `type` as a union — "if the value of `type` is an array, then an instance validates successfully if its type matches any of the types indicated by the strings in the array" — so the two spellings assert the same thing and cannot take different carriage. The 3.0 line answers for itself and answers differently: every 3.0 edition states of the Schema Object that "`type` - Value MUST be a string. Multiple types via an array are not supported," so an array-valued `type` is not a union declaration there and no form carriage follows from one. The 3.0 line's null spelling is `nullable: true`: a declaration carrying it restates the same single-non-null-carriage declaration, takes the same collapse, and elides a supplied JSON `null` the same way — the 3.0.4 encoding note's open null-handling question, answered by the same labeled elision convention. **A resolved part schema that declares no `type` refuses before dispatch on every accepted edition; the ground is per line, because the accepted editions do not speak alike.** Every accepted **3.1** edition states a definite default for that part, and all three state `application/octet-stream`. **3.1.1** and **3.1.2** carry it as the first row of the Encoding Object's own default table — `type` *absent*, `contentEncoding` *n/a*, default `contentType` `application/octet-stream` — beneath a lead-in stating that "an n/a in the contentEncoding column means that the presence or value of contentEncoding is irrelevant". **3.1.0** reaches the same answer through the total catch-all that closes its prose enumeration: "for object - application/json; for array – the default is defined based on the inner type; for all other cases the default is application/octet-stream." In each case the key is the *declared* `type` rather than the supplied value — 3.1.1 and 3.1.2 tabulate the `absent` row beside the typed rows, and 3.1.0's clause leaves no residue for a typeless declaration to fall out of. This specification defines no correspondence from a JSON application value to octets for a form part, so on those three editions such a part **refuses before dispatch** and its alternative is an accounted exclusion; an operation is represented through another candidate or not at all. **The 3.0 line states no row for it.** 3.0.0 through 3.0.3 enumerate a `string` with `format` being `binary`, "other primitive types", `object`, and `array`, and close without a catch-all; 3.0.4 tabulates the same cases keyed on `type` with `format` as a second column. Every stated row there is keyed on a declared `type` and none reaches a declaration carrying none. This specification **authors no row for that residue**: a typeless part on 3.0.0, 3.0.1, 3.0.2, 3.0.3, and 3.0.4 likewise refuses before dispatch, its alternative the same accounted exclusion. The two lines thus reach one outcome on different grounds — the 3.1 editions state a default this revision defines no boundary to cross, the 3.0 editions state nothing and this revision fills nothing — so a part whose resolved schema declares no `type` refuses uniformly, and no supplied value's JSON type ever selects a part's carriage. **A part whose resolved schema declares `type: string` with `format: byte` is a stated cell on the 3.0 line, and its default is 3.0.4's row read line-uniformly.** 3.0.4's default-`contentType` table gives `string` with `format` `binary` or `byte` the default `application/octet-stream`, while 3.0.0 through 3.0.3's prose names only `binary` before "other primitive types"; under the editions' own §4.1 patch-uniformity instruction ([§2](#2-scope-and-incorporated-authorities)) the line answers uniformly, 3.0.4 read under its own text fixes what the uniform default is, and emitting different part framing on either side of a patch boundary is exactly the distinction those editions instruct against — the same incorporated ground the form-path selection predicate below rests on. The part's value is the caller's artifact-encoded Base64 text, sent as-is per the `format: byte` carriage rule stated with the request lanes. 3.0.4 additionally equates a `byte` part with an Encoding Object whose `headers` field carries a `Content-Transfer-Encoding` schema requiring `base64`; this specification reads that equivalence as declaration semantics, and emits no `Content-Transfer-Encoding` header unless the artifact itself declares that header. An invalid value or a member for which the resolved schema leaves no faithful form carriage refuses before dispatch. **Percent-encoding inside an `application/x-www-form-urlencoded` body is the OAS's own two-authority assignment, restated here rather than added.** Each claim below names the editions whose own text states it, because [§2](#2-scope-and-incorporated-authorities) reads every accepted edition under its own immutable text and does not aggregate them. That media type's two serialization paths are percent-encoded under two different specifications: the *style path* under [RFC 6570], the *content path* under [RFC 1866] §8.2.1, whose escaping in turn defers to [RFC 1738]. **3.0.4, 3.1.1 and 3.1.2** state that pairing in a normatively-cited-standards table — noting of [RFC 6570] that it "does not use `+` for form-urlencoded" — at Appendix E.3 in 3.0.4 and 3.1.1 and Appendix E.4 in 3.1.2. A space consequently rides as `%20` through the style path and as `+` through the content path; the paths are not two answers to one question, and **3.1.2** §4.8.12.4 records that both spellings satisfy the media type's own requirements. **Which path an Encoding Object takes is decided by presence, not by value.** **3.0.4, 3.1.1 and 3.1.2** state it in the Encoding Object's own closing note — "the presence of at least one of `style`, `explode`, or `allowReserved` with an explicit value is equivalent to using `schema` with `in: "query"` Parameter Objects. The absence of all three of those fields is the equivalent of using `content`" — and again in the same appendix ("in the Encoding Object when at least one of `style`, `explode`, or `allowReserved` is present"). **3.1.0** reaches the same result through a different sentence, carried on each of the three fields: "If a value is explicitly defined, then the value of `contentType` (implicit or explicit) SHALL be ignored." An `allowReserved: false` that restates the field's own default is therefore an explicit value and selects the style path. **3.0.0 through 3.0.3 state neither sentence, and the predicate governs them too**, by their own §4.1 rather than by any rule stated here: those four editions instruct tooling to make no distinction between the patch versions of the 3.0 line ([§2](#2-scope-and-incorporated-authorities)), 3.0.4 is a member of that line, and 3.0.4 §4.7.15.1.2 fixes what the uniform behavior is — "if all three of `style`, `explode`, and `allowReserved` fields are absent, it is RECOMMENDED that: All three keywords are to be entirely ignored, rather than treated as having their default values; Encoding is to be based on `contentType` alone" — with the worked bytes at its §4.7.15.2.1, whose lead-in is "When there is no `encoding` field, the serialization strategy is based on the Encoding Object's default values". Only one uniform 3.0-line behavior is consistent with that, since the alternative would contradict 3.0.4 read under its own text, which [§2](#2-scope-and-incorporated-authorities) equally requires. So on **every** accepted edition a property carrying no explicit `style`, `explode` or `allowReserved` takes the content path, and one carrying any of them takes the style path. This clause restates an incorporated consequence rather than adding a convention, and it is the same reading three neighbouring rules already rest on: [§6](#6-composition)'s reference-traversal branches, stated per line; the 3.1 line's single `contentType` default table applied alike to 3.1.0, 3.1.1 and 3.1.2; and the five-edition 3.0-line type-absent part default above. Nothing about the *style* path's own residual freedom changes with it — RFC 6570 states no expansion for a composite member of a list (§3.2.1 appends list members "after pct-encoding any characters that are not in the allow set"), which is why a declaration the style path cannot serve refuses rather than being approximated. Beyond the path assignment the exact set of characters left literal is a **permitted set the artifact authorities record rather than narrow**. Every accepted edition reaches it the same way: [RFC 1866] §8.2.1 replaces a space with `+` and escapes the rest "as per [URL]", and [URL] is [RFC 1738], whose §2.2 permits "only alphanumerics, the special characters `$-_.+!*'(),`, and reserved characters used for their reserved purposes" unencoded, permits encoding anything "not required to be encoded ... as long as they are not being used for a reserved purpose", and requires the characters it names unsafe — `~` among them — to "always be encoded". **3.0.4, 3.1.1 and 3.1.2** additionally give two conditional recommendations inside that set, one for [RFC 1738]'s rules (historical interoperability) and one for WHATWG's form-urlencoded rules (browser compatibility); **3.1.2** alone adds that "encoding more characters than necessary is always safe in terms of the decoding process". This specification preserves the permitted set and states no preference inside it. Which member an implementation emits is that implementation's own documented behavior, not portable meaning under this identifier.
- Under OAS 3.0.x, an exact non-JSON, non-form declaration whose governing schema resolves to `type: string` with `format: binary` carries raw octets — the 3.0 line's own definition of `binary` as "any sequence of octets". An exact declaration whose Media Type Object omits `schema` carries the same raw octets as **this specification's reading**, not an OAS-stated rule: no 3.0 edition assigns meaning to an omitted `schema`, and a declaration that asserts nothing selects the byte lane by the same no-assertion reasoning the degenerate-combinations paragraph states. The caller's JSON string is this specification's Base64 boundary representation; the binding decodes it and emits the exact octets. `application/octet-stream: {}`, `image/png`, `application/pdf`, and vendor media types are instances of those two rules, not an allowlist. A media range with an omitted schema does not gain this lane: this candidate does not infer one representation for all of its possible concrete instantiations.
- Under OAS 3.0.x, a non-JSON, non-form concrete selection whose governing schema resolves to `type: string` with `format: byte` carries the caller's string as **artifact-encoded Base64 text**, sent as-is. Every 3.0 edition's own format registry defines `byte` as "base64 encoded characters" — 3.0.4's row citing [RFC 4648] §4 — so the declared value already **is** the encoded characters and the body is that string, the 3.0 line's parallel of the 3.1 `contentEncoding` rule below. The binding does not Base64-decode the string merely because the declared format is `byte`; artifact encoding and the OpenBindings raw-byte boundary encoding remain distinct here exactly as there.
- Under OAS 3.1.x, a non-JSON, non-form concrete selection whose governing Media Type Object omits `schema` carries opaque raw octets. The caller uses the same Base64 boundary representation. This follows OAS 3.1's binary-body form, in which `image/png: {}` or `application/octet-stream: {}` may omit a schema; it also gives an untyped representation exact byte carriage without inventing a logical schema. A media range with an omitted schema does not gain this lane on this line either — the same no-single-representation restraint as the 3.0 bullet, stated for both lines by OAPI-P-04.
- Under OAS 3.1.x, a non-JSON, non-form governing schema with `type: string` and `contentEncoding` carries the caller's string as the artifact-declared encoded text. The binding does **not** Base64-decode that string merely because the declared encoding is `base64`: 3.1.0 states outright that the payload is transferred as text, and 3.1.1 and 3.1.2 imply the same through their encoded-binary tables and the dialect's §8.3. Artifact encoding and the OpenBindings raw-byte boundary encoding are distinct.
- Every **other** concrete non-JSON, non-form selection whose governing schema resolves to `type: string`, and whose media type is **character data** as defined below, carries the supplied string as the body, encoded using the selection's declared `charset` and defaulting to UTF-8. The emitted `Content-Type` remains the configured concrete value with its parameters. This **string-carriage lane is an explicitly labeled OpenBindings convention**: no accepted OAS edition supplies a request serialization for any media type outside the two form types, so both the incumbent `text/plain` case and its generalization are this specification speaking rather than incorporation. What the convention states is deliberately the smallest thing that can be stated. It authors no correspondence and installs no codec: the artifact declared the body to be a string, the caller supplies that string, and the emitted body is that string's characters under the artifact's own header. It is the request-side mirror of the response text lane below, and it is decided by the **declaration** alone: the supplied value's JSON type never selects or deselects a lane.

**The lane's scope is derived, not chosen.** Two authorities answer the two questions it joins, and this specification only bridges them. The **OAS**, with the JSON Schema dialect its edition names, decides what the value is: `type: string` is an assertion, while under the 3.1 line `format` is an annotation with no content-encoding force — 3.1.0 §4.8.14.3 states that "the `format` keyword has no effect on the content-encoding of the schema", 3.1.1 restates it at §4.8.14.3 with a migration table at §4.4.2.1, both direct authors to `contentEncoding` and `contentMediaType` instead, and `binary` is absent from the 3.1 format tables. So a `{ "type": "string", "format": "binary" }` declaration under that line is a string declaration, while under the 3.0 line, where the Data Types section (§4.4; 3.0.4 numbers it §4.4.1) defines `binary` as "any sequence of octets", it is the raw-octet lane above. The **media-type registration** decides whether a string has an octet image at all: a string becomes wire bytes only where a character encoding applies. Where both hold, the carriage is the identity and nothing is authored. Where the second does not hold there is no charset, hence no defined string-to-octets mapping, and the declaration keeps the artifact-authorized byte lanes above rather than gaining a lane this specification would have to invent — an Arrow, CBOR, or Protobuf stream typed `string` by its artifact is not a document a caller can supply faithfully as characters.

**Character data.** A concrete selection is character data when any of the following holds, and otherwise is not:

- Its top-level type is `text`. The `text` tree is "material that is principally textual in form" (RFC 6838 §4.2.1; RFC 2046 §4.1 states the same with "which"), every **new** `text/*` registration MUST state how its charset is determined, and UTF-8 is the default RFC 6838 §4.2.1 directs new registrations to select.
- Its subtype carries the `+xml` structured syntax suffix, or is the exact `application/xml` or `text/xml` registration (the latter is already `text/*` above). An XML MIME entity's content is characters determined by a `charset` parameter, a BOM, or an XML encoding declaration, and UTF-8 without a BOM is RECOMMENDED for all of them (RFC 7303 §3, §9.1, §9.2, §9.6.1).
- Its subtype carries the `+json` structured syntax suffix: this family's JSON lanes already treat such a representation as JSON text, whose encoding is UTF-8 (RFC 8259 §8.1). The JSON lanes above claim these first, so this member is stated for completeness rather than reached.

This test is **closed and structural**, and it is deliberately not RFC 6838 §4.8's "Encoding considerations" registration field. That field does not decide the question and cannot be relied on for it: `application/json` registers `binary` (RFC 8259 §11) while its own §8.1 requires UTF-8 text, and `text/csv` (RFC 4180 §3) records no §4.8 value at all. Keying the accepted domain on a live registry lookup would also contradict [§2](#2-scope-and-incorporated-authorities), where every authority is pinned to an immutable text so that two conformant processors agree a year apart. Admitting a further registered character-data `application/*` subtype is therefore an amendment to the list above, decided against that subtype's registering document, and never a runtime lookup.

The Base64 boundary form above is canonical RFC 4648 §4 Base64: the standard alphabet, no whitespace or other non-alphabet characters (rejection is RFC 4648 §3.3's own default), required `=` padding when needed, and zero unused pad bits (the zero-pad rule of §3.5, whose rejection mandate that section invites referring specifications to state — this specification states it). A non-canonical or invalid boundary string refuses before dispatch. The boundary value's protocol-independent description is a JSON string with `contentEncoding: "base64"` — a claim about the JSON boundary value, not an HTTP header or media type — and a representation of this direct caller contract states exactly that. A body value is never sniffed to choose or change a lane.

The artifact's content map declares alternatives, not a preference order. Different admissible concrete choices remain conformant. A configured media type that matches no declaration, selects a declaration for which this candidate defines no carriage, or is inadmissible for the supplied value refuses before dispatch; configuration never substitutes another declaration's schema. A body-emitting invocation with no admissible candidate likewise refuses. A no-body invocation bypasses this point as defined in [§9.1](#91-input-mapping).

For a successful non-empty unary **response**, the selected declaration and actual concrete media type define one of these lanes (**OAPI-P-07**):

- An actual `application/json` or `+json` representation parses as strict JSON.
- An actual `text/*` representation decodes as text using its declared `charset`, defaulting to UTF-8. The UTF-8 default is **this specification's convention**, stated as its own: the pinned registration texts default `text/*` to US-ASCII (RFC 2046 §4.1.2), UTF-8 is a strict superset of that default, and one stated default keeps two implementations byte-identical. The `charset` parameter is the one encoding source this lane consults; RFC 7303's BOM and XML-declaration sources are not read here. `text/event-stream` instead follows the per-event rule in §8.
- Under OAS 3.0.x, an exact non-JSON, non-text selected declaration whose Media Type Object omits `schema`, or whose resolved schema is `type: string`, `format: binary`, emits the exact response octets as canonical Base64. A schema-omitted media range does not gain this lane.
- Under OAS 3.1.x, a non-JSON, non-text selected Media Type Object that omits `schema` emits the exact response octets as canonical Base64. A schema-omitted media range does not gain this lane on this line either.
- Every other selected non-JSON representation whose concrete media type is **character data** — the same closed test defined above for the request lane — retains the text lane, decoding under its declared `charset` and defaulting to UTF-8. Unsupported or invalid character decoding is loud. A selected representation whose media type is **outside character data** emits the exact response octets as the canonical Base64 boundary instead: where no character encoding applies there is no defined octets-to-string decoding, and an Arrow, CBOR, or Protobuf body that happens to survive a UTF-8 decode would otherwise pass as silent garbage — the same who-determines-the-characters discriminator the request lane applies, in the decode direction. This candidate does not pretend to have decoded an artifact-defined XML, CBOR, or other codec into its logical schema value.

The Base64 form is the same canonical, protocol-independent boundary defined above. It is the output value itself, not an object containing a status, header, media type, or other HTTP fact. When all represented outcomes using a schema position are raw-byte lanes, that position's protocol-independent description is `{ "type": "string", "contentEncoding": "base64" }` — a representation of the contract states exactly that. When a media range admits more than one lane, synthesis represents the union of the application values those concrete instantiations can produce; an unconstrained JSON alternative necessarily leaves the operation output unconstrained.

**Synthesis coverage.** A represented request media-range alternative requires the `requestMedia` point's effective choice, because acting through that alternative always needs a concrete instantiation even when another exact alternative supplies a no-context path. The represented target carries that requirement exactly when a body is required and no represented concrete request candidate can carry it without the choice. Thus a range-only required body has both the target-wide and the alternative requirement; a mixed exact-plus-range operation has the requirement only on each range alternative. The requirement stays in coverage accounting and invocation context, never in the operation input schema; how a coverage record spells it is reference-tool documentation, not this specification's content.

**Degenerate media/schema combinations.** `multipart/form-data` or `application/x-www-form-urlencoded` is not a candidate when its own resolved declaration is non-object; the string-carriage lane is a candidate only when the governing declaration's resolved type is `string` and the concrete selection is character data. The OAS specifies multipart and form-urlencoded serialization over object properties, while the string lane carries one string. A Media Type Object whose `schema` is the JSON Schema boolean `true`, or a Schema Object with no members, **asserts nothing**: the artifact made no claim that the body is a string, so it is the same declaration as an omitted `schema` and takes the artifact-authorized byte lanes with it under either edition. An explicit schema that does assert something, and that neither selects one of those lanes nor declares an encoded string, is not silently reinterpreted as opaque bytes. That reading governs a **Media Type Object's** own `schema` and does not descend to a form part: a part whose resolved schema declares no `type` is governed by the per-line rule stated with form serialization above, and refuses before dispatch on every accepted edition. Candidate exclusion is decided by **declarations alone** — this family has no value-dependent exclusion — never by the supplied value's JSON type and never by payload sniffing. A value that the selected declaration cannot carry is a pre-dispatch refusal at invocation, not a change of candidate set.

**Schema-guided XML generation is excluded.** This specification defines no lane that builds an XML document from an object model. An `application/xml` or `text/xml` request declaration whose governing schema resolves to anything other than `type: string` therefore selects none of the request lanes above: it is an excluded alternative, and a configured `requestMedia` naming it refuses before dispatch. The exclusion is a definition, not an open item, and its reason is authority rather than effort. The OAS XML Object speaks **partially**: `name`, `attribute`, `namespace`, `prefix`, and `wrapped` are incorporable as stated. It is silent on element ordering, escaping, null representation, dynamic object keys, and scalar lexical grammars — and because XML is order-significant, those silences determine the bytes of essentially every non-trivial document. A schema-guided lane would therefore make this specification the author of most of the wire while citing the OAS for the fragment it happens to cover, which is authorship wearing the incorporated authority's name. One falseness-test criterion also fails objectively rather than by judgment: round-trippability, at mixed content, comments, and the attribute-versus-element ambiguity, where decoding destroys information that encoding cannot reconstruct.

What is excluded is generation, not XML. **String carriage of XML documents is admitted**, by the same lane and the same rule as every other character-data media type a declaration types as a string: an `application/xml` or `text/xml` declaration whose governing schema resolves to `type: string` carries the caller's XML document as the body under the artifact's own header, and an XML response representation retains the UTF-8 text lane by rule rather than by fallthrough. Nothing is authored in either direction — the artifact declared a string, the caller supplies the document, and the characters ride — so the two paragraphs describe one consistent position: string carriage of XML documents, yes; schema-guided generation of XML from an object model, no. Schema-omitted XML declarations likewise keep the artifact-authorized raw-byte lanes above. A schema-guided lane, if ever admitted, is a later identifier under OBI-B-03.

**Nonstandard JSON spellings.** The JSON lanes admit exact `application/json` and `+json` suffix types. `text/json` is not JSON-family media: it is an unregistered spelling, and the same discipline that never infers `application/json` from object shape or payload bytes does not adopt a spelling the media-type registry does not define. What follows is only that it never reaches a JSON lane; it is otherwise an ordinary media type under the rules above. A `text/json` response representation is `text/*` and rides the UTF-8 text lane. A `text/json` request declaration selects the string-carriage lane when its governing schema resolves to `type: string`, and is an excluded alternative for every other declared shape — which is where the object and array declarations that occasion this spelling in practice land, since no lane serializes an object into an unregistered media type. Admitting the spelling to the JSON family would be a later identifier under OBI-B-03.

**Multipart parts.** Under OAS 3.0.x, a part schema with `type: string` and `format: binary` uses the same canonical Base64 boundary representation and emits the decoded octets; a part schema with `type: string` and `format: byte` instead carries the caller's artifact-encoded Base64 text without OpenBindings boundary decoding and defaults to `application/octet-stream`, per the line-uniform 3.0.4 row stated with form serialization above, emitting no `Content-Transfer-Encoding` unless the artifact declares that header. Under OAS 3.1.x, `format` has no content-encoding effect; a `type: string` property with `contentEncoding` carries its artifact-encoded string without OpenBindings boundary decoding, and `contentMediaType` without `contentEncoding` is identity-encoded string content rather than a raw-byte signal. **Both keywords have force only on a resolved part schema that declares `type: string`, and this restates an incorporated consequence rather than adding a convention.** The 3.1 Schema Object is a JSON Schema 2020-12 schema, and [JSON Schema 2020-12] §8.1 makes its Content vocabulary annotations that "do not function as validation assertions", while §8.3 and §8.4 each condition their keyword on the instance being a string — "If the instance value is a string" and "If the instance is a string". Every accepted 3.1 edition keys the `application/octet-stream` part row on the same declaration: **3.1.0** §4.8.14.5 on "a `type: string` with a `contentEncoding`", **3.1.1** and **3.1.2** on their default table's `string` row with `contentEncoding` *present*. On a declared non-string type the keywords are therefore inert: the part keeps the row its own declared type names — 3.1.1 and 3.1.2 hold `n/a` in the `contentEncoding` column of the `number, integer, or boolean`, `object`, and `array` rows, which their lead-in defines as "the presence or value of `contentEncoding` is irrelevant", and 3.1.0's prose assigns primitives `text/plain` and complex values `application/json` without reference to either keyword. Such a part is not refused, does not take the encoded-string row, and emits no `Content-Transfer-Encoding`, the MIME header [JSON Schema 2020-12] §8.3 derives `contentEncoding` from. A part declaring no `type` at all is the separate type-absent cell answered above, and carrying either keyword does not change that answer. **On the 3.0 line neither keyword is in the Schema Object's vocabulary** — that line's Schema Object is the Wright Draft 00 subset, `contentEncoding` occurs zero times in 3.0.0 through 3.0.3, and 3.0.4 mentions it outside every default row — so an artifact carrying one there has written a keyword its dialect declares "strictly unsupported", and the part decides as if it were absent. That as-if-absent disposition is **this specification's stated reading** of the strictly-unsupported clause, applied uniformly wherever this document invokes it: the OAS declares such keywords unsupported, not the schema invalid, so the keyword carries no meaning at this boundary and refusing the schema would invent a severity the edition never states. One 3.1.0-internal overlap is reconciled here rather than privately: for a plain `type: string` part without `contentEncoding`, 3.1.0's §4.8.14.5 (`text/plain` for primitives) and its Encoding Object catch-all ("for all other cases … `application/octet-stream`") disagree, and 3.1.0 itself never orders them; this specification reads the specific multipart row over the general catch-all, so such a part defaults `text/plain`. Other parts serialize per the artifact's `encoding` object where present, else per the OAS's per-type part defaults. Nothing here is decided by the value's bytes; the artifact's declarations decide.

The request `Accept` header advertises the declared media types and media ranges of the operation's success response declarations ([§8](#8-target-and-interaction)). Membership and artifact-declared parameters are normative; ordering and quality preferences are not. The mandate to send the header is **this specification's convention**, stated as its own — RFC 9110 makes `Accept` optional and no accepted edition addresses client `Accept` behavior — kept because without it two conformant processors would send different `Accept` sets and could elicit observably different responses from one document; the membership itself is artifact-derived. When that set is empty, the header is omitted unless consumer configuration supplies one — this specification does not invent `application/json` for an artifact that declared no response media.

### 9.3. Servers and the target URL

The target URL is the resolved server joined with the operation's path template. Server resolution is a **named configuration point** (**OAPI-P-05**) with the effective-choice semantics below:

- The **effective server list** is the OAS's: the operation's `servers`, else the path item's, else the document's, else the OAS-defined implied server of `url: "/"`. An **empty** `servers` array at the operation or path-item level declares no alternative and falls through to the outer level — the OAS equates empty-with-absent in its root-field sentence, and this specification reads the override rows the same way, stated here because the editions state it only for the root.
- An effective list with exactly one entry selects that entry. With more than one, the artifact has declared alternatives without a preference and the **server** point is required: a missing selection is missing consumer configuration, and invocation challenges for it through the retryable context negotiation before dispatch — the same lane §9.2 gives a missing request-media selection — never a terminal refusal and never a guessed member.
- Consumer configuration may supply the selected member's server-variable values or replace its resolved base URL outright, whether the member was sole or chosen; a URL replacement changes the target, not which artifact server's declarations and security semantics govern. A supplied server-variable value honors the artifact's declared `enum`; a value outside it is refused. A complete-URL replacement is a distinct target override, not a claim that an out-of-enum substitution satisfies the Server Variable Object. The concrete carriage of a supplied override is implementation surface, not specification content; the reference SDKs document their shapes.

A relative effective-server URL (the implied `/` included) resolves per RFC 3986 against the base URI of **the document containing the Server Object** — the artifact's own base ([§6](#6-composition)) except when the Server Object arrived through an externally referenced document, whose base then governs. The editions carry two spellings of that base: "the location where the OpenAPI document is being served" (3.0.0 through 3.0.3, and 3.1.0) and "the location where the document containing the Server Object is being served" (3.0.4, 3.1.1, 3.1.2). Under [§2](#2-scope-and-incorporated-authorities)'s patch-uniformity reading these are one instruction per line — the two texts coincide for a single-document artifact, and the later patches describe the composed case the earlier texts left undescribed — so both lines resolve against the containing document's base. A missing selection from a multi-entry list is the retryable context challenge above, never a terminal refusal; an out-of-enum variable value, or a server URL that cannot resolve to an absolute URL — the implied `/` with no base URI, for instance — is a pre-dispatch refusal.

### 9.4. Configuration points

This family has **four** named configuration points — `server` resolution ([§9.3](#93-servers-and-the-target-url)), `requestMedia` ([§9.2](#92-request-and-response-media)), and the two interaction points below. Each row defines the meaning of one **effective** choice and the artifact answer or binding convention when none is supplied. How a runtime chooses among per-call, standing, or other configuration sources is outside this specification; those scopes cannot change the point's semantic effect. All binding conventions are content-independent: decided by declarations and framing, never payload bytes.

| ------------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`requestMedia`** | no preference among admissible concrete declarations; a required range-only body requests retryable preflight context | Which concrete request media type carries the body. A configured concrete value selects the most-specific matching exact or range declaration under §9.2; without configuration a processor may choose any admissible concrete artifact declaration but never instantiates a range or infers JSON. A required range-only body's missing choice is surfaced before input consumption; a supplied optional range body with no prior choice, or an unmatched, unsupported, or inadmissible supplied choice, refuses. It cannot cause an otherwise bodyless invocation to emit a body.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **decode**         | **the governing-response declaration-and-framing rule** (**OAPI-P-07**)                     | An empty body (204 included) completes without an output value and without consulting media. For a non-empty body, the final status selects the governing Response Object per [§8](#8-target-and-interaction), and the response's concrete `Content-Type` selects exactly one exact or range entry in that object's `content` map under §9.2's parameter-aware most-specific rule; an absent, unmatched, normalized-colliding, or ambiguous declaration is a protocol error. JSON, text, and artifact-authorized raw-byte lanes then decode exactly as §9.2 defines. A redirect whose semantics require, or whose configured client policy would perform, a method rewrite is not followed and remains the final response. Field routing is not a configuration point in this family: the artifact and the binding's source-facing input representation answer routing ([§9.1](#91-input-mapping)).

### 9.5. Success and the output value

Which outcomes are successes is decided by the **classify** point. For a successful non-empty unary response, the operation's one output value is the product of the **decode** point; an empty successful response emits none. Each streamed output value is the per-event product of that point. Response headers have **no representation in the abstract invocation** in this candidate — a declared exclusion.

A failure outcome is terminal unsuccessful completion, never an operation output; this specification names no portable failure code of its own, and HTTP status does not select a portable error category. For a non-empty, non-SSE failure response, the final status selects the governing Response Object and the concrete `Content-Type` selects its most-specific exact or range `content` entry under §9.2, and the body decodes through **the same response decode lanes a successful response uses** (§9.2): a JSON-family representation decodes as its JSON value, a raw-byte representation emits its exact octets as the canonical Base64 boundary string, and every other represented selection decodes per §9.2's residual response lane — the text lane under its declared `charset` (defaulting to UTF-8) when its media type is character data, the canonical Base64 byte lane when it is not. This specification admits the lane's decoded value — a scalar, array, object, or JSON null — as **application-authored failure data**. The admitted value is opaque: it is not wrapped, inspected for conventionally named members, transformed, or validated against the operation's successful output schema. How an invocation surface carries it is that surface's contract; when the project's portable invocation interface is used, the admitted value rides its optional error `data` member.

When the failure response is undeclared, empty, SSE-framed, unmatched, normalized-colliding, or ambiguous by media type, or its selected lane cannot faithfully decode the body (an invalid JSON body in a JSON-family lane, an invalid character sequence in the text lane), no application-authored failure data is admitted. Those conditions do not turn native status, headers, raw bytes, decoder prose, or another part of the protocol container into portable failure data. No admission means that no portable application-authored failure value was established; it is distinct from a declared and decoded JSON null. This rule refines failure information without changing the 2xx classification rule, participating in synthesis, or adding failure values to operation schemas.

### 9.6. Security declarations, credentials, and channel assembly

Security metadata is never extracted into the OBI: the artifact's declarations remain authoritative whenever the binding is acted upon. The declaration semantics are the OAS's, incorporated: the operation's `security` **replaces** the document's entirely (an explicit `[]` means anonymous), requirements are an OR of ANDed schemes, and each scheme's definition lives in `components.securitySchemes`.

When more than one Security Requirement Object is satisfiable, **any one complete alternative** may be selected; the array declares alternatives, not an OpenBindings preference order. Consumer credential policy may choose among them. A processor MUST NOT construct apparent satisfaction by combining incomplete fragments from different alternatives. Different selections that each completely satisfy an artifact-declared alternative remain conformant behavior, not a binding-specification ambiguity.

What this specification pins is **wire application** (**OAPI-P-09**): an `apiKey` scheme's credential rides its declared `in`/`name` (header, query, or cookie); `http` schemes with values `basic` and `bearer` ride the `Authorization` header — the credential carrier RFC 9110 §11.6.2 defines — with the scheme value matched case-insensitively per RFC 9110's auth-scheme rule (the editions' own citation is its predecessor RFC 7235, which states the same rule; this specification reads it at its pinned successor); `oauth2` and `openIdConnect` access tokens ride `Authorization: Bearer` — Bearer carriage incorporated from [RFC 6750] §2.1, the `Authorization` request header field with the `Bearer` scheme, the method that section requires every resource server to support. No accepted OAS edition states where these tokens ride, so the **choice of Bearer is this specification's pin**, made because it matches how the ecosystem's oauth2-secured HTTP APIs are deployed; a deployment issuing another token type is outside this pin. A scheme, or an `http` scheme value, that this list does not pin (`http`/`digest`, `mutualTLS`, and any future type) is **surfaced to the consumer** rather than silently skipped. Surfacing has one disposition at the operation boundary: this specification defines no wire carriage for such a scheme, so a security alternative requiring one cannot be completely satisfied under this identifier and is unusable — the operation refuses before dispatch, naming the scheme, unless another complete artifact-declared alternative is selected.

**Channel assembly** (**OAPI-P-10**): declared cookie parameters and cookie-riding credentials merge into the single `Cookie` header — parameters in declaration order, credentials appended after, each contribution rendered `name=value` and joined by a semicolon and a space (`; `). The assembly is **this specification's convention**, stated as its own: no pinned authority governs client `Cookie` assembly (the editions cite no cookie RFC for it; the cookie appendix carried by 3.0.4, 3.1.1 and 3.1.2 records the same semicolon-space delimiter, and this convention agrees with it), and one deterministic order keeps two implementations byte-identical. Within the selected complete security alternative, credential destinations MUST be pairwise non-colliding, and no credential destination may collide with an effective declared parameter at the same location: these are distinct artifact declarations even when the caller omitted the parameter, so one wire value never silently satisfies both. A header credential also MUST NOT collide with a processor-owned request field (`host`, `content-length`, `content-type`, or `accept`). A raw header declaration named `Cookie` is admissible by itself, but cannot coexist with any effective cookie parameter or selected cookie-riding credential: this candidate does not parse a raw cookie string and assign precedence against structured cookie contributions. A security alternative containing any collision this paragraph names — pairwise credential, credential-against-parameter, credential-against-processor-owned-field, or the raw-`Cookie` coexistence — is unusable and is refused before dispatch unless another complete, non-colliding artifact-declared alternative is selected. Header names compare ASCII case-insensitively; query and cookie names compare exactly (no pinned authority states a cookie-name case rule, and exact comparison is the reading that invents no equality). This catches two ANDed schemes that both require `Authorization`, two API keys naming one destination, an API key shadowing a parameter, and an API key attempting to replace media framing. No source silently overwrites, duplicates, or supplies another.

The same ownership rule applies before credentials: an effective header parameter targeting `host` or `content-length` makes the operation unresolvable. An effective raw `Cookie` header parameter is unresolvable when any effective cookie parameter also exists, and it makes a selected security alternative unusable when that alternative contributes a cookie credential. (`content-type` and `accept`, plus `authorization`, have already been removed by the incorporated OAS ignored-header rule.) A header parameter cannot replace target resolution, body framing, or structured cookie assembly merely because it was declared as an ordinary parameter.

How missing credentials are discovered, requested, and resolved is a consumer and runtime concern, not this specification's: the project's [`binding-invoker`](https://openbindings.com/interfaces/binding-invoker) interface defines one such negotiation surface (informative). When that surface is used, a requirement derived from an artifact-authored reusable security scheme carries `durable: true`: this grants the surrounding runtime permission to persist the resolved credential, but does not require persistence, assert that the credential never expires, or override application policy.

### 9.7. Transform positions

This specification defines **no** context bindings at transform positions: a transform on an openapi binding evaluates in the core's closed environment, unaugmented.

## 10. Conformance

Rules carry stable identifiers under the same discipline as the core's: never reused, never renumbered. Source rules bind OBI content governed by this specification; processor rules test whether implementations preserve the specified meaning when acting on it, not whether they expose one invocation API. Verification follows the core's partial-verification posture.

- **OAPI-D-01**: `content`, when present, is the parsed OpenAPI document object or its source text as a string, per [§5](#5-content).
- **OAPI-D-02**: `location`, when present, is an absolute URI addressing the OpenAPI document, per [§4](#4-location).
- **OAPI-D-03**: `ref` is present, and is a JSON Pointer `#/paths/<escaped-path>/<lowercase-method>` addressing an operation object, resolving a `$ref` path item before the method segment evaluates, in the pointer's one verbatim spelling — never percent-decoded — per [§7](#7-ref).
- **OAPI-P-01**: The exact accepted OAS edition set, YAML 1.2.2 string-content grammar pin, edition discrimination, and loud refusal behave per [§2](#2-scope-and-incorporated-authorities) and [§3](#3-accepted-source-representations). Within an accepted line, behavior does not turn on the patch component of the artifact's `openapi` field, and where the patch texts of one line differ the governing reading is the one consistent with every accepted patch of that line — each accepted edition's own §4.1 instructs tooling to make no such distinction, and each states of a `.patch` release that it addresses this document rather than the feature set, hedged with "Typically" in 3.0.0 through 3.0.3 and extended to clarifications in 3.0.4 and the 3.1 line. That reading governs how an accepted edition is interpreted and never widens the accepted domain: it remains the eight enumerated editions, discriminated by the artifact's own `openapi` field, and any other value — including any other 3.0 or 3.1 patch — still refuses loudly at load. Whole-source refusal follows [§3](#3-accepted-source-representations)'s three parts and nothing else: the load gates are the closed set stated there — the accepted-representation grammar decided against YAML 1.2.2's productions rather than any parser's recovery, scalar resolution and key uniqueness, the root's shape, and the edition gate, always evaluated first; below them exactly one derived refusal fires, a source in which no conformant `ref` resolves to an operation object because every position that would have carried one is defective under the governing edition, while an artifact that conformantly declares no target is accepted with no operations and a target that is addressed and then unusable refuses at invocation or is accounted as an exclusion, never at load; and this revision declares no source-scope exclusion.
- **OAPI-P-02**: Parameter serialization follows the OAS `style`/`explode`/`allowReserved` rules and defaults, with `content`-form parameters serialized per their declared media type, per [§9.1](#91-input-mapping). A `form`, `spaceDelimited`, `pipeDelimited` or `deepObject` declaration whose resolved schema carries a member with no defined expansion — an array whose resolved items resolve to `object` or `array`, or an object one of whose resolved property schemas does — is refused at admission and its exclusion accounted, the parameter position excluding its target and the form-body position its alternative; a typeless member, a multi-non-null choice, and an object declaring no members are not reached, because a declaration-keyed rule must not refuse a declaration that admits a scalar. The `form` row's own RFC 6570 §3.2.8 citation is carried by every accepted edition and its expansions append member strings; `spaceDelimited`, `pipeDelimited` and `deepObject` cite no RFC section on any edition, and the `deepObject` row governs without defining the case on 3.0.0 through 3.0.3 and 3.1.0 while 3.0.4, 3.1.1 and 3.1.2 state that the representation of array or object properties is not defined. No representation is authored here.
- **OAPI-P-03**: Input mapping supports the flat and exact routed source representations of §9.1; preserves independent same-named parameter and body declarations without exposing their HTTP identity in the operation contract; retains only the case-colliding-header refusal whose distinction the wire itself cannot express; carries explicitly dynamic objects and declaration-complex exact JSON bodies as one application value rather than flattening runtime or branch-dependent names; routes unmatched fields only where a flattened JSON object body supplies a destination; applies declaration-only body-shape resolution, required-input refusals, candidate election, and whole-body unwrapping; and refuses malformed or unroutable source values before dispatch.
- **OAPI-P-04**: A no-body invocation bypasses request-media selection and emits neither body nor `Content-Type`; a body-emitting invocation preserves the artifact's declared alternatives with no binding-specification preference, lets a configured concrete `requestMedia` select the most-specific matching exact or range declaration, and never instantiates a range or infers JSON without that choice. A required range-only body with no effective choice requests retryable `requestMedia` context before input consumption and performs zero dispatch; an optional range-only body may complete bodyless, but a supplied body with no prior choice refuses rather than requiring replay. A supplied unmatched, unsupported, or inadmissible choice and any other absence of a carriage candidate also refuse before dispatch. Exact JSON-family declarations serialize declaration-complex whole values without branch selection. Exact schema-omitted OAS 3.0 non-JSON declarations, OAS 3.0 raw-binary schemas, and OAS 3.1 opaque-body declarations use the canonical Base64 JSON boundary and emit exact decoded bytes; schema-omitted media ranges do not gain that lane. A `schema` that asserts nothing — the JSON Schema boolean `true` or a memberless Schema Object — is the same declaration as an omitted `schema` and takes those byte lanes with it. OAS 3.1 `contentEncoding` strings remain artifact-encoded wire text; `contentEncoding` and `contentMediaType` have force only on a resolved schema declaring `type: string`, and on a declared non-string type they are inert annotations that neither refuse the part, nor select the encoded-string row, nor emit `Content-Transfer-Encoding` — the part keeps the row its own declared type names, which restates [JSON Schema 2020-12] §8.1/§8.3/§8.4 together with each accepted 3.1 edition's own default rows, and on the 3.0 line neither keyword is in the Schema Object's vocabulary at all. On the 3.0 line a `type: string`, `format: byte` declaration — exact non-JSON, non-form selection or form part alike — carries the caller's artifact-encoded Base64 text without OpenBindings boundary decoding, per the editions' own "base64 encoded characters" definition; the part default is `application/octet-stream` per 3.0.4's `binary`-or-`byte` row read line-uniformly under the editions' own §4.1 instruction, and no `Content-Transfer-Encoding` header is emitted unless the artifact declares it. Every other concrete non-JSON, non-form selection whose governing schema resolves to `type: string` **and whose media type is character data** carries the supplied string under its declared `charset`, defaulting to UTF-8; that lane is selected by the declaration alone, admits the `text` tree and XML alike, keeps a media type outside character data on the byte lanes rather than inventing one, and never builds a document from an object model. Multipart observes the same edition distinction; dynamic member schemas resolve through the governing edition's own dialect before form carriage — exact, pattern, additional-property, and `allOf` declarations on the 3.1 line, and exact, additional-property, and `allOf` declarations on the 3.0 line, whose Schema Object dialect has no pattern-property member (per [§9.2](#92-request-and-response-media)). A resolved part schema declaring no `type` is answered per edition: every accepted 3.1 edition states `application/octet-stream` for it — tabulated as the `type`-absent row in 3.1.1 and 3.1.2, reached through the closing catch-all in 3.1.0 — which this revision defines no JSON-to-octet part boundary to cross, so such a part refuses before dispatch and its alternative is an accounted exclusion; the 3.0 line states no row for it and this specification authors none, so such a part refuses there identically — a typeless part refuses on every accepted edition, and no supplied value's JSON type selects a part's carriage. A property schema declaring one non-null `anyOf`/`oneOf` branch beside null-only branches collapses to that branch, a supplied JSON null eliding the optional part; a choice with more than one non-null branch refuses. A 3.1 array-valued `type` with exactly one non-`"null"` member is the same declaration and takes the same collapse, sibling keywords unchanged; two or more non-null members refuse, and under the 3.0 line, where `type` MUST be a string, an array-valued `type` yields no form carriage at all. Percent-encoding inside a form body follows the OAS's own assignment of the style path to RFC 6570 and the content path to RFC 1866 §8.2.1, so the two paths spell a space differently by incorporation; path selection is by an Encoding Object field's explicit presence rather than its value, on **every** accepted edition — 3.0.4, 3.1.0, 3.1.1 and 3.1.2 state the predicate in their own text, and 3.0.0 through 3.0.3 reach the same behavior through their own §4.1 patch-uniformity instruction together with 3.0.4 §4.7.15.1.2's "Encoding is to be based on `contentType` alone", so no accepted edition runs the style path for a property that writes no explicit `style`, `explode` or `allowReserved`; and within each path the exact literal set stays the artifact authorities' permitted set, which this specification does not narrow to one byte-identical body. `Accept` advertises the normative concrete membership set and is omitted when that set is empty rather than inventing a media type, per [§9.2](#92-request-and-response-media).
- **OAPI-P-05**: Server resolution uses the OAS effective server list: a sole member selects itself; multiple members require consumer selection, obtained through the retryable context negotiation before dispatch; variable substitutions honor declared enums; a complete URL may replace the selected member's target without replacing its artifact semantics; unresolvable targets refuse before dispatch, per [§9.3](#93-servers-and-the-target-url).
- **OAPI-P-06**: Response declaration lookup is exact status → matching range → `default`, independently of final-status 2xx classification; streaming capability is statically bounded by all success declarations, while an actual response's interaction and media are governed only by the Response Object selected for its final status. A non-empty body with no governing declaration or no matching concrete media type is a protocol error; SSE events are extracted per the WHATWG processing model, per [§8](#8-target-and-interaction).
- **OAPI-P-07**: The decode configuration point defaults to the governing-response header rule: empty bodies emit no value; non-empty bodies require one parameter-aware, most-specific concrete media match under OAPI-P-06 and then use the defined JSON, text, or artifact-authorized raw-byte lane, including the per-event text default for SSE, per [§9.2](#92-request-and-response-media) and [§9.4](#94-configuration-points); a selected non-JSON representation takes the text lane only when its concrete media type is character data under §9.2's closed test, and a selected representation outside character data emits its exact octets as canonical Base64. Exact schema-omitted OAS 3.0 non-JSON responses emit canonical Base64; schema-omitted media ranges do not gain that lane. Normalized content-map collisions and equal-specificity response ties are a protocol error rather than a selection by source order.
- **OAPI-P-08**: The classify configuration point defaults to the 2xx rule, applied to the final status; redirect following is runtime policy, but any followed redirect preserves the bound operation's method and complete body, and a method-rewriting redirect remains the final response, per [§9.4](#94-configuration-points).
- **OAPI-P-09**: Credentials apply to the wire per scheme as [§9.6](#96-security-declarations-credentials-and-channel-assembly) pins; any one complete artifact-declared security alternative may be selected, incomplete fragments from different alternatives never manufacture satisfaction; unpinned schemes are surfaced, never silently skipped; security metadata is never written into OBI documents.
- **OAPI-P-10**: Channel assembly merges non-colliding parameters and credentials deterministically; an effective header parameter cannot replace processor-owned target, length, or cookie assembly; pairwise credential collisions, credential/effective-parameter collisions, and header-credential/processor-owned-field collisions make the selected security alternative unusable and refuse before dispatch unless another complete declared alternative is selected, per [§9.6](#96-security-declarations-credentials-and-channel-assembly).

Conformance fixtures keyed to these identifiers are maintained in the project's conformance corpus. Deterministic _generation_ of OBI documents from OpenAPI artifacts (operation-key derivation, output-schema selection, schema translation) is a synthesis concern outside this specification; the project's interface-synthesizer and reference-tool documentation record those conventions.
