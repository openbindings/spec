# `openbindings.openapi` Binding Specification

## 1. Status and identifier

This document is the normative text for **`openbindings.openapi@7`**, published by the openbindings project as its defining authority. The identifier is exact and opaque per core [OBI-B-01](../../openbindings.md#104-binding-specification-rules). Published revisions are immutable; an incompatible change publishes the next revision ([OBI-B-03](../../openbindings.md#104-binding-specification-rules)). Revision 7 succeeds immutable `openbindings.openapi@6`. It retains revision 6's whole-JSON rules and gives schema-omitted exact non-JSON OpenAPI 3.0 representations the same protocol-independent raw-byte boundary already used where an artifact authorizes opaque bytes. It neither adds HTTP concepts to the operation contract nor gives the binding specification control over operation naming.

The key words "MUST", "MUST NOT", "REQUIRED", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP 14](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals.

## 2. Scope and incorporated authorities

This is the **openbindings project's** binding specification for [OpenAPI](https://spec.openapis.org/) documents. It is published under this project's authority, not by or for the OpenAPI Initiative: the OpenAPI Specification (OAS) is incorporated by reference and remains authoritative over the artifact and the HTTP mechanics it describes — document structure and reference resolution, parameter locations and serialization, request/response media declarations and encodings, server objects and variables, security scheme declarations, and everything else the artifact says about the wire. Plain HTTP semantics are [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110)'s; `text/event-stream` framing follows the WHATWG HTML server-sent-events processing model at the immutable source snapshot named below. This specification defines only the OpenBindings overlay: how a source carries or addresses an OpenAPI document, how a binding selects an operation, and how caller-facing operation values correspond to an HTTP exchange.

Like the core specification, this document defines portable meaning rather than an invocation API. Its HTTP-exchange, refusal, and ordering language states what acting on the binding denotes and which effects remain conformant; request objects, context negotiation, retries, cancellation APIs, and client architecture remain runtime or SDK surface.

**Normative upstream snapshot.** Revision 7 accepts only the published OAS editions [3.0.0](https://spec.openapis.org/oas/v3.0.0.html), [3.0.1](https://spec.openapis.org/oas/v3.0.1.html), [3.0.2](https://spec.openapis.org/oas/v3.0.2.html), [3.0.3](https://spec.openapis.org/oas/v3.0.3.html), [3.0.4](https://spec.openapis.org/oas/v3.0.4.html), [3.1.0](https://spec.openapis.org/oas/v3.1.0.html), [3.1.1](https://spec.openapis.org/oas/v3.1.1.html), and [3.1.2](https://spec.openapis.org/oas/v3.1.2.html), each interpreted under its own immutable official text. The string carriage grammar is [YAML 1.2.2](https://yaml.org/spec/1.2.2/). The SSE authority is the WHATWG HTML source at commit [`24c5e48bf66ea61bc199ec6338c81258275ba9c6`](https://github.com/whatwg/html/blob/24c5e48bf66ea61bc199ec6338c81258275ba9c6/source); the living rendered page and later upstream revisions are informative and do not alter this identifier. A later OAS patch or minor is never admitted merely because it matches a supported line; accepting another edition or advancing a normative authority pin publishes a new binding-specification identifier.

OpenAPI artifacts are substantially complete as actionable descriptions — routing, media types, and status declarations are native — so this specification's interpretation points ([§9.3](#93-servers-and-the-target-url), [§9.4](#94-configuration-points)) are fewer and narrower than an incomplete family's (compare [`openbindings.usage@1`](../usage/openbindings.usage.md)).

## 3. Accepted source representations

This specification accepts the **exact OpenAPI editions listed in §2** — 3.0.0 through 3.0.4 and 3.1.0 through 3.1.2 — in two carried representations:

- **Object** `content`: the parsed OpenAPI document as a JSON object.
- **String** `content`: the document's source text. This specification pins the string grammar — its own pin, not an OAS mandate: string content parses as **YAML 1.2.2** under the OAS's JSON-compatibility recommendations, of which JSON is a valid subset, so one grammar covers both spellings deterministically. Duplicate mapping keys are refused loudly.

Discrimination is the artifact's own **`openapi` field**: one of the exact accepted values is interpreted under that edition's OAS text; every other value (including a future 3.0 or 3.1 patch, OpenAPI 3.2, and Swagger 2.0's `swagger` field) is refused loudly at load (**OAPI-P-01**). No other representation is defined; there is no non-textual artifact form.

## 4. `location`

A source's `location`, when present, is an **absolute URI addressing the OpenAPI document itself** (**OAPI-D-02**) — `https://example.com/openapi.json`, `file:///srv/api/openapi.yaml`. Dereferencing it yields an accepted representation ([§3](#3-accepted-source-representations)). A bare filesystem path is a relative reference in form and is not a conformant `location` (core [OBI-D-05](../../openbindings.md#102-document-rules)).

## 5. `content`

A source's `content`, when present, MUST be one of the two accepted representations of [§3](#3-accepted-source-representations): the parsed document object, or its source text as a string (**OAPI-D-01**). No other JSON type is an accepted `content` value under this specification.

## 6. Composition

When `content` is present it is the artifact the processor interprets, per the core's content-primacy floor ([§5.4](../../openbindings.md#54-sources)).

A co-present `location` is the document's origin, and it serves as the embedded artifact's **base URI**: references internal to the embedded document (relative `$ref`s, relative server URLs) resolve against it per the OAS's own reference-resolution rules, exactly as they would had the document been retrieved from that address. The base travels in the OBI, so resolution is identical everywhere the OBI goes; the OBI's own retrieval URI is never a base (core [§7](../../openbindings.md#7-reference-resolution)). Embedded content with **no** co-present `location` has no base and MUST be self-contained: every internal reference resolves without one (bundle before embedding).

Self-containment is RECOMMENDED even when a `location` is present: a document whose embedded artifact leans on its base for `$ref` resolution requires that address to be reachable to interpret, which reintroduces the network dependence embedding exists to remove.

For a `location`-only source, the document's base URI is the `location`, per the OAS.

## 7. `ref`

A binding's `ref` is REQUIRED — the OAS defines no whole-artifact invocation — and MUST be a JSON Pointer of the form `#/paths/<escaped-path>/<method>`, addressing an **operation object**: the path segment carries [RFC 6901](https://www.rfc-editor.org/rfc/rfc6901) escaping (`/` → `~1`), and `<method>` is one of the OAS's HTTP method keys, **lowercase exactly as the artifact spells them** (**OAPI-D-03**). `#/paths/~1tasks/post` addresses the POST operation on `/tasks`.

The pointer is a **verbatim string**. Its `#/` shape is JSON Pointer notation, not an invitation to URI processing: no percent-decoding is ever applied, at authoring or at resolution. Each addressable operation has exactly one conformant spelling — the RFC 6901-escaped form above — and a `ref` matches it byte-for-byte, extending the core specification's literal-form doctrine (core [§7](../../openbindings.md#7-reference-resolution)) to this family's selector. A percent-encoded rendering of that spelling (`#/paths/~1users~1%7BuserId%7D/get` for `#/paths/~1users~1{userId}/get`) is not the spelling and denotes nothing.

Pointer evaluation follows **OAS reference resolution**, not raw JSON traversal: a path item that is a `$ref` (including a 3.1 `components.pathItems` target) is resolved before the method segment evaluates, so bundled artifacts using path-item references stay addressable. A well-formed `ref` whose path or method is absent from the resolved artifact makes the binding unresolvable; verification requires the artifact, per the core's partial-verification posture.

Only `paths` operations are addressable. **Webhooks and callbacks are excluded** from revision 7: they describe inbound calls the service makes to the consumer, an interaction this revision does not bind. The exclusion is a definition, not an open item.

## 8. Target and interaction

The binding denotes the addressed operation as **one HTTP exchange** against the resolved server ([§9.3](#93-servers-and-the-target-url)).

**Success classification and response declaration lookup are separate.** Classification is the final-status 2xx rule of [§9.4](#94-configuration-points). After a response arrives, its governing OAS Response Object is selected exactly as the OAS Responses Object declares: the exact status-code entry first, then the matching `2XX` range entry, then `default` when neither more-specific entry exists (**OAPI-P-06**). Thus `default` can govern the shape and media of a successful 2xx response; it does not itself make a non-2xx response successful. A **success response declaration** below means any entry that can govern at least one 2xx status under that lookup: an exact 2xx entry, `2XX`, and — unless `2XX` covers the whole class — `default`.

The interaction shape is bounded by declaration and selected by framing (**OAPI-P-06**):

- An operation is **streaming-capable** iff at least one media declaration in a success response can match the concrete type `text/event-stream`: an exact declaration, `text/*`, or `*/*`. Capability is static: a consumer knows from the artifact alone whether streaming can occur.
- For an actual successful response, the exact status first selects its governing Response Object by the lookup above. Only that object's `content` map can govern framing. An actual concrete `text/event-stream` representation selected by an exact or range declaration there yields a **server-streaming** interaction; every other selected concrete representation yields a **unary** interaction. A media declaration belonging only to a different status, response range, or shadowed `default` entry is irrelevant to this response.
- A non-empty successful response with no governing Response Object, or whose concrete `Content-Type` does not select one declaration in that object's `content` map, contradicts the artifact and is a protocol error. An empty body needs no media declaration and is unary. Thus a `text/event-stream` response is never accepted merely because SSE appears somewhere else in the operation.

A **unary** interaction carries zero or one caller input value and **zero or one output value**: a non-empty successful response emits one decoded value, while an empty successful response completes without emitting a value. Absence of a representation is not the JSON value `null`; a non-empty JSON body whose bytes spell `null` emits that explicit value. A **server-streaming** interaction likewise carries zero or one caller input value; each received SSE event emits one output value per the WHATWG processing model: the event's `data` lines joined with U+000A form the event's text, comment-only and empty-`data` events emit no value, and the `event`, `id`, and `retry` fields **never enter the output value** — whether an implementation surfaces them out of band is its own concern. Stream end completes the interaction; abnormal termination — transport failure before stream end — is a failure outcome, and output values already emitted **stand**. NDJSON and other streaming framings are excluded from revision 7.

## 9. Operation-boundary correspondence

### 9.1. Input mapping

The operation-facing input is one JSON object (or absent). Parameter and body values are application data; their HTTP destinations are binding facts and do not become required operation property names, schemas, or caller-visible wrappers. The source-facing value at the binding's input-transform boundary has two representations (**OAPI-P-03**):

1. A **flat object** MAY be used when every effective parameter and every property in a finite, named selected request-body property set has a unique name. Fields map by that name, preserving revision 1 behavior.
2. A **routed one-tuple** carries independent source fields when names collide, an explicitly dynamic object body as one application value, or a declaration-complex JSON body as one complete application value. It has the exact form below. This representation is binding-private: an OBI may produce it with core `inputTransform`; it is not an operation contract and synthesis MUST NOT copy its HTTP identity members into the operation schema.

The one-item array makes the routed representation structurally disjoint from the object-shaped application input. Therefore `$openbindings` and even an otherwise envelope-shaped application object always remain ordinary flat application fields; no valid caller property can be mistaken for private routing data. The tuple exists wholly below the operation boundary.

```json
[
  {
    "$openbindings": "openbindings.openapi@7",
    "value": { "account": "a", "request": "q", "record": "b" },
    "parameters": [
      { "in": "path", "name": "id", "field": "account" },
      { "in": "query", "name": "id", "field": "request" }
    ],
    "body": {
      "properties": { "id": "record" },
      "whole": "payload"
    }
  }
]
```

`value` is the transformed application object. Each `parameters` entry identifies one effective OAS parameter by its exact name-plus-location identity and names the field in `value` that supplies it. Duplicate entries for one identity refuse. `body.properties` maps each artifact body-property name to its field in `value`; `body.whole` names the field used for a selected non-object body, an explicitly dynamic object body, or a declaration-complex JSON body. The selected candidate determines which body form applies. A referenced field's presence is distinct from its value, so explicit JSON `null` is preserved. A malformed routed tuple, an entry that does not identify a declaration, or a supplied field with no derivable destination refuses before dispatch.

Deterministic generation of the operation-facing field names and the transform expression is a synthesis concern, not a rule of this specification. A synthesizer can therefore retain application names and descriptions, choose collision-free protocol-neutral names, and keep the concrete routing solely in the binding transform. For an explicitly dynamic or declaration-complex JSON body, synthesis preserves the complete resolved schema as one operation property (for example, the protocol-neutral `payload` field shown above) rather than pretending that its possible runtime keys form one finite operation-property set. The binding specification defines the transform's source-facing representation because core [§5.5](../../openbindings.md#55-transforms) requires that boundary to be portable; it does not dictate an OBI generator's operation-key or property-naming policy.

The remaining mapping is incorporated or declaration-driven:

- The effective parameter set merges path-level and operation-level `parameters`, operation-level winning on the same name-and-location identity, and applies the OAS ignored-header rule for `Accept`, `Content-Type`, and `Authorization` case-insensitively.
- `path`, `query`, `header`, and `cookie` parameters ride their OAS destinations. Serialization follows the OAS `style`/`explode`/`allowReserved` and `content`-form rules wholesale (**OAPI-P-02**).
- Same-named parameters in different locations and parameter/body-property collisions remain independent and are carried by distinct routed fields; no value is duplicated or identified by inference. Effective header parameters whose names differ only by ASCII case remain unresolvable because HTTP field names are case-insensitive and the wire itself supplies no two distinct destinations.
- A field matching no parameter or declared body-property route passes through under its own name only for a flattened object-valued JSON-family body, where the artifact supplies that destination without invention. It refuses for no body, a whole-value body, multipart, and form-urlencoded candidates. Runtime members of an explicitly dynamic object and every member of a declaration-complex JSON value belong to that whole application value, not to unmatched top-level operation fields.
- Object-or-not is decided from the resolved candidate declaration. Direct `properties` and explicit object type are object-shaped; `allOf` contributes the recursively collected property union; reference identities are visited once. A typeless schema is non-object.
- An object is **explicitly dynamic** when its resolved top-level schema, including any `allOf` member, declares at least one `patternProperties` entry or explicitly declares `additionalProperties` as `true` or as a Schema Object. Such a body uses `body.whole`; it is never flattened. A merely omitted `additionalProperties` does not select this revision's dynamic carriage, even where the governing schema dialect gives the keyword an open default. This narrow trigger preserves the immutable flattened contract for ordinary named-property artifacts while closing every case in which the author explicitly declared runtime property names.
- A schema is **declaration-complex at the JSON body boundary** when its resolved top level, including an `allOf` member, contains `oneOf`, `anyOf`, `not`, `if`, `then`, or `else`, declares at least one `dependentSchemas` entry, or explicitly permits `unevaluatedProperties`. For an exact JSON-family media declaration, that complete schema and value use `body.whole`; no branch is selected and no body property is routed independently. JSON serialization applies to the supplied value exactly as it does for every other JSON-family body. This rule preserves the authored validation contract and needs no value-dependent binding logic. It does not define form, multipart, text, raw, or media-range serialization for such a schema; those candidates remain inadmissible unless another rule independently supplies faithful carriage.

**Required declarations.** No input while any parameter or request body is required refuses before dispatch. A supplied value missing a path parameter always refuses because the URL cannot be built. Other missing declarations are sent as supplied; the server's validation remains authoritative.

**Body and candidate election.** Each supported media candidate is evaluated using its own resolved Media Type Object and schema. A configured concrete `requestMedia` can cause a media-range declaration to govern; its schema, not another declaration's schema, then decides routing and admissibility. A JSON-family object body with no fields is `{}` when required and omitted otherwise. No-body invocation bypasses media selection and emits neither a body nor `Content-Type`.

### 9.2. Request and response media

Media types throughout this section are parsed under RFC 9110. Type, subtype, and parameter names compare case-insensitively; parameter ordering and quoted-string versus equivalent token spelling do not create distinct identities; parameter values compare under the parameter's governing media-type semantics, and otherwise byte-for-byte after quoted-string unescaping. Two keys in one OAS `content` map that denote the same parsed media type are a **normalized collision** and make that request or response candidate set unresolvable — no first-key rule is invented.

Parameters are never discarded. A concrete media type or media range **matches** a concrete selected media type when its non-wildcard type and subtype agree and every parameter present in the declaration is present with the same value in the concrete selection; additional selected parameters do not disqualify it. Matching declarations are ordered first by range specificity — exact type/subtype, then `type/*`, then `*/*` — and then by greatest number of declared parameters. If several distinct declarations tie at the greatest specificity, selection is ambiguous and refuses rather than depending on content-map order. This most-specific-subset rule is an explicitly labeled OpenBindings convention: OAS requires the most-specific matching content entry but, together with HTTP, does not supply the parameter tie-break needed at this boundary.

For **request selection**, `requestMedia`, when supplied, is one concrete media type. It selects the most-specific matching declaration under the rule above, and that declaration's Media Type Object governs the value. The emitted `Content-Type` is the configured concrete value, including its parameters; a range key is never emitted as a field value. Without configuration, a processor may choose any admissible **concrete** declaration in the artifact, preserving the artifact's unordered alternatives. A range alone supplies no concrete representation, so `requestMedia` is required whenever that range will carry a body. For a **required** range-only body, the requirement is knowable during preflight: before reading caller input, a processor requests a retryable choice and performs no dispatch; under the project's portable invocation interface this is `context-required` with one `config.value` requirement for the `requestMedia` point. An optional range-only body still bypasses media selection when the caller supplies no body. If the caller supplies that optional body without a prior effective choice, a portable processor refuses before dispatch rather than requesting retry after consuming a potentially non-replayable input; a runtime that explicitly buffers and replays may reacquire the choice through its own API, but this specification does not assume that capability. Object shape, examples, or payload bytes never imply `application/json`. Once a concrete value is supplied, a value that matches no declaration, selects an unsupported lane, or is inadmissible for the input is likewise a pre-dispatch refusal.

For **response matching**, the actual `Content-Type` is the concrete selected media type. It selects the most-specific matching exact or range declaration under the same range-specificity and parameter-subset rule used for configured requests. The selected declaration's Media Type Object governs decoding; the actual field value supplies the concrete framing and is not exposed as an operation value. An absent, unmatched, normalized-colliding, or equally specific ambiguous declaration is a protocol error. No body bytes are inspected to repair or replace the selection.

When the invocation will emit a body, the governing declaration is selected from the operation's **declared** `requestBody.content` under the **`requestMedia`** configuration point (**OAPI-P-04**, [§9.4](#94-configuration-points)). Once a concrete media type and governing declaration are known, revision 7 defines these request carriage lanes:

- Exact or range-selected `application/json` and `+json` types serialize the application value as JSON.
- `multipart/form-data` and `application/x-www-form-urlencoded` serialize object fields under the OAS's `encoding` rules. For an explicitly dynamic object, each runtime member name resolves its effective property schema by applying an exact `properties` schema and every matching `patternProperties` schema, or the `additionalProperties` schema when neither exact nor pattern schemas match; applicable constraints contributed by `allOf` all apply. JSON Schema regular expressions use the governing OAS edition's dialect. An OAS Encoding Object can govern only a statically named property as required by OAS; a dynamic member with no such entry uses the OAS default encoding. When that effective property schema is unconstrained, its JSON application type supplies the corresponding OAS per-type multipart default. An invalid value or a member for which the resolved schema leaves no faithful form carriage refuses before dispatch.
- `text/plain` carries a supplied string as text.
- Under OAS 3.0.x, an exact non-JSON, non-form, non-text declaration whose Media Type Object omits `schema`, or whose governing schema resolves to `type: string` with `format: binary`, carries raw octets. The caller's JSON string is this specification's Base64 boundary representation; the binding decodes it and emits the exact octets. `application/octet-stream: {}`, `image/png`, `application/pdf`, and vendor media types are instances of the same artifact-authorized byte rule, not an allowlist. A media range with an omitted schema does not gain this lane: revision 7 does not infer one representation for all of its possible concrete instantiations.
- Under OAS 3.1.x, a non-JSON, non-form, non-text concrete selection whose governing Media Type Object omits `schema` carries opaque raw octets. The caller uses the same Base64 boundary representation. This follows OAS 3.1's binary-body form, in which `image/png: {}` or `application/octet-stream: {}` may omit a schema; it also gives an untyped representation exact byte carriage without inventing a logical schema.
- Under OAS 3.1.x, a non-JSON, non-form governing schema with `type: string` and `contentEncoding` carries the caller's string as the artifact-declared encoded text. The binding does **not** Base64-decode that string merely because the declared encoding is `base64`: OAS 3.1 states that the encoded text is the transferred payload. Artifact encoding and the OpenBindings raw-byte boundary encoding are distinct.

The Base64 boundary form above is canonical RFC 4648 §4 Base64: the standard alphabet, no whitespace or other non-alphabet characters, required `=` padding when needed, and zero unused pad bits. A non-canonical or invalid boundary string refuses before dispatch. A synthesizer representing this direct caller contract uses a JSON string schema with `contentEncoding: "base64"`; that keyword describes the protocol-independent JSON boundary value, not an HTTP header or media type. A body value is never sniffed to choose or change a lane.

The artifact's content map declares alternatives, not a preference order. Different admissible concrete choices remain conformant. A configured media type that matches no declaration, selects a declaration for which revision 7 defines no carriage, or is inadmissible for the supplied value refuses before dispatch; configuration never substitutes another declaration's schema. A body-emitting invocation with no admissible candidate likewise refuses. A no-body invocation bypasses this point as defined in [§9.1](#91-input-mapping).

For a successful non-empty unary **response**, the selected declaration and actual concrete media type define one of these lanes (**OAPI-P-07**):

- An actual `application/json` or `+json` representation parses as strict JSON.
- An actual `text/*` representation decodes as text using its declared `charset`, defaulting to UTF-8. `text/event-stream` instead follows the per-event rule in §8.
- Under OAS 3.0.x, an exact non-JSON, non-text selected declaration whose Media Type Object omits `schema`, or whose resolved schema is `type: string`, `format: binary`, emits the exact response octets as canonical Base64. A schema-omitted media range does not gain this lane.
- Under OAS 3.1.x, a non-JSON, non-text selected Media Type Object that omits `schema` emits the exact response octets as canonical Base64.
- Every other selected non-JSON representation retains the revision-3 text lane. Unsupported or invalid character decoding is loud; revision 7 does not pretend to have decoded an artifact-defined XML, CBOR, or other codec into its logical schema value.

The Base64 form is the same canonical, protocol-independent boundary defined above. It is the output value itself, not an object containing a status, header, media type, or other HTTP fact. A synthesizer uses `{ "type": "string", "contentEncoding": "base64" }` when all represented outcomes using that schema position are raw-byte lanes. When a media range admits more than one lane, synthesis represents the union of the application values those concrete instantiations can produce; an unconstrained JSON alternative necessarily leaves the operation output unconstrained.

**Synthesis coverage.** A represented request media-range alternative records `configuration.requestMedia`, because acting through that alternative always needs a concrete instantiation even when another exact alternative supplies a no-context path. The represented target also records `configuration.requestMedia` exactly when a body is required and no represented concrete request candidate can carry it without that choice. Thus a range-only required body has both the target-wide and alternative requirement; a mixed exact-plus-range operation has the requirement only on each range alternative. The requirement stays in coverage and invocation context, never in the operation input schema.

**Degenerate media/schema combinations.** `multipart/form-data` or `application/x-www-form-urlencoded` is not a candidate when its own resolved declaration is non-object; `text/plain` is a candidate only for a non-object declaration and a supplied string value. The OAS specifies multipart and form-urlencoded serialization over object properties, while the text lane carries one string. An OAS 3.1 Media Type Object with an explicit schema that neither selects one of those lanes nor declares an encoded string is not silently reinterpreted as opaque bytes. Candidate exclusion is decided by declarations (and, for text, the value's required string type), never by payload sniffing.

**Multipart parts.** Under OAS 3.0.x, a part schema with `type: string` and `format: binary` uses the same canonical Base64 boundary representation and emits the decoded octets. Under OAS 3.1.x, `format` has no content-encoding effect; a `type: string` property with `contentEncoding` carries its artifact-encoded string without OpenBindings boundary decoding, and `contentMediaType` without `contentEncoding` is identity-encoded string content rather than a raw-byte signal. Other parts serialize per the artifact's `encoding` object where present, else per the OAS's per-type part defaults. Nothing here is decided by the value's bytes; the artifact's declarations decide.

The request `Accept` header advertises the declared media types and media ranges of the operation's success response declarations ([§8](#8-target-and-interaction)). Membership and artifact-declared parameters are normative; ordering and quality preferences are not. When that set is empty, the header is omitted unless consumer configuration supplies one — this specification does not invent `application/json` for an artifact that declared no response media.

### 9.3. Servers and the target URL

The target URL is the resolved server joined with the operation's path template. Server resolution is a **named configuration point** (**OAPI-P-05**) with the effective-choice semantics below:

- The **effective server list** is the OAS's: the operation's `servers`, else the path item's, else the document's, else the OAS-defined implied server of `url: "/"`.
- An effective list with exactly one entry selects that entry. With more than one, the artifact has declared alternatives without a preference and the **server** point is required: consumer configuration selects a member, or invocation refuses before dispatch. Consumer configuration may supply that member's server-variable values or replace its resolved base URL outright; a URL replacement changes the target, not which artifact server's declarations and security semantics govern.
- A supplied server-variable value honors the artifact's declared `enum`; a value outside it is refused. A complete-URL replacement is a distinct target override, not a claim that an out-of-enum substitution satisfies the Server Variable Object. The concrete carriage of a supplied override is implementation surface, not specification content; the reference SDKs document their shapes.

A relative effective-server URL (the implied `/` included) resolves against the artifact's base URI ([§6](#6-composition)) per RFC 3986. A missing selection from a multi-entry list, an out-of-enum variable value, or a server URL that cannot resolve to an absolute URL — the implied `/` with no base URI, for instance — is a pre-dispatch refusal.

### 9.4. Configuration points

This family has **four** named configuration points — `server` resolution ([§9.3](#93-servers-and-the-target-url)), `requestMedia` ([§9.2](#92-request-and-response-media)), and the two interaction points below. Each row defines the meaning of one **effective** choice and the artifact answer or binding convention when none is supplied. How a runtime chooses among per-call, standing, or other configuration sources is outside this specification; those scopes cannot change the point's semantic effect. All binding conventions are content-independent: decided by declarations and framing, never payload bytes.

| ------------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`requestMedia`** | no preference among admissible concrete declarations; a required range-only body requests retryable preflight context | Which concrete request media type carries the body. A configured concrete value selects the most-specific matching exact or range declaration under §9.2; without configuration a processor may choose any admissible concrete artifact declaration but never instantiates a range or infers JSON. A required range-only body's missing choice is surfaced before input consumption; a supplied optional range body with no prior choice, or an unmatched, unsupported, or inadmissible supplied choice, refuses. It cannot cause an otherwise bodyless invocation to emit a body.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **decode**         | **the governing-response declaration-and-framing rule** (**OAPI-P-07**)                     | An empty body (204 included) completes without an output value and without consulting media. For a non-empty body, the final status selects the governing Response Object per [§8](#8-target-and-interaction), and the response's concrete `Content-Type` MUST select exactly one exact or range entry in that object's `content` map under §9.2's parameter-aware most-specific rule; an absent, unmatched, normalized-colliding, or ambiguous declaration is a protocol error. JSON, text, and artifact-authorized raw-byte lanes then decode exactly as §9.2 defines. For a server-streaming interaction the selected actual media is `text/event-stream`; the point applies **per event** to the event's U+000A-joined data text ([§8](#8-target-and-interaction)), whose default output is that text — SSE carries no per-event media declaration, so JSON-emitting event data requires consumer configuration at this point. |
| **classify**       | **the 2xx rule** (**OAPI-P-08**)                                                            | Success **iff** the final status ∈ 2xx. Declared `responses` refine what a failure _means_, never whether it is one — a declared 404 documents a failure's shape, it does not bless the failure. OpenAPI does not define redirect following, so whether to follow is runtime policy; any followed redirect MUST preserve the bound operation's HTTP method and complete request body. A redirect whose semantics require, or whose configured client policy would perform, a method rewrite is not followed and remains the final response. Classification applies to the **final** status after any semantics-preserving redirects, and a surviving 3xx is not a success. Limits and cross-origin policy remain runtime concerns. |

Field routing is not a configuration point in this family: the artifact and the binding's source-facing input representation answer routing ([§9.1](#91-input-mapping)).

### 9.5. Success and the output value

Which outcomes are successes is decided by the **classify** point. For a successful non-empty unary response, the operation's one output value is the product of the **decode** point; an empty successful response emits none. Each streamed output value is the per-event product of that point. Response headers have **no representation in the output value** in revision 7 — a declared exclusion. Failure outcomes are not operation results and have no representation in this specification; what a consumer surfaces about them — and any error-code vocabulary — is its own concern, outside this document.

### 9.6. Security declarations, credentials, and channel assembly

Security metadata is never extracted into the OBI: the artifact's declarations remain authoritative whenever the binding is acted upon. The declaration semantics are the OAS's, incorporated: the operation's `security` **replaces** the document's entirely (an explicit `[]` means anonymous), requirements are an OR of ANDed schemes, and each scheme's definition lives in `components.securitySchemes`.

When more than one Security Requirement Object is satisfiable, **any one complete alternative** may be selected; the array declares alternatives, not an OpenBindings preference order. Consumer credential policy may choose among them. A processor MUST NOT construct apparent satisfaction by combining incomplete fragments from different alternatives. Different selections that each completely satisfy an artifact-declared alternative remain conformant behavior, not a binding-specification ambiguity.

What this specification pins is **wire application** (**OAPI-P-09**): an `apiKey` scheme's credential rides its declared `in`/`name` (header, query, or cookie); `http` schemes with values `basic` and `bearer` — matched case-insensitively, per RFC 9110's auth-scheme rules — ride the `Authorization` header per their RFCs; `oauth2` and `openIdConnect` access tokens ride `Authorization: Bearer`. A scheme, or an `http` scheme value, that this list does not pin (`http`/`digest`, `mutualTLS`, and any future type) is **surfaced to the consumer** rather than silently skipped.

**Channel assembly** (**OAPI-P-10**): declared cookie parameters and cookie-riding credentials merge into the single `Cookie` header — parameters in declaration order, credentials appended after. Within the selected complete security alternative, credential destinations MUST be pairwise non-colliding, and no credential destination may collide with an effective declared parameter at the same location: these are distinct artifact declarations even when the caller omitted the parameter, so one wire value never silently satisfies both. A header credential also MUST NOT collide with a processor-owned request field (`host`, `content-length`, `content-type`, or `accept`). A raw header declaration named `Cookie` is admissible by itself, but cannot coexist with any effective cookie parameter or selected cookie-riding credential: revision 7 does not parse a raw cookie string and assign precedence against structured cookie contributions. Such a security alternative is unusable and is refused before dispatch unless another complete, non-colliding artifact-declared alternative is selected. Header names compare ASCII case-insensitively; query and cookie names compare exactly. This catches two ANDed schemes that both require `Authorization`, two API keys naming one destination, an API key shadowing a parameter, and an API key attempting to replace media framing. No source silently overwrites, duplicates, or supplies another.

The same ownership rule applies before credentials: an effective header parameter targeting `host` or `content-length` makes the operation unresolvable. An effective raw `Cookie` header parameter is unresolvable when any effective cookie parameter also exists, and it makes a selected security alternative unusable when that alternative contributes a cookie credential. (`content-type` and `accept`, plus `authorization`, have already been removed by the incorporated OAS ignored-header rule.) A header parameter cannot replace target resolution, body framing, or structured cookie assembly merely because it was declared as an ordinary parameter.

How missing credentials are discovered, requested, and resolved is a consumer and runtime concern, not this specification's: the project's [`binding-invoker`](https://openbindings.com/interfaces/binding-invoker) interface defines one such negotiation surface (informative).

### 9.7. Transform positions

This specification defines **no** context bindings at transform positions: a transform on an openapi binding evaluates in the core's closed environment, unaugmented.

## 10. Conformance

Rules carry stable identifiers under the same discipline as the core's: never reused, never renumbered. Source rules bind OBI content governed by this specification; processor rules test whether implementations preserve the specified meaning when acting on it, not whether they expose one invocation API. Verification follows the core's partial-verification posture.

- **OAPI-D-01**: `content`, when present, is the parsed OpenAPI document object or its source text as a string, per [§5](#5-content).
- **OAPI-D-02**: `location`, when present, is an absolute URI addressing the OpenAPI document, per [§4](#4-location).
- **OAPI-D-03**: `ref` is present, and is a JSON Pointer `#/paths/<escaped-path>/<lowercase-method>` addressing an operation object under OAS reference resolution, in the pointer's one verbatim spelling — never percent-decoded — per [§7](#7-ref).
- **OAPI-P-01**: The exact accepted OAS edition set, YAML 1.2.2 string-content grammar pin, edition discrimination, and loud refusal behave per [§2](#2-scope-and-incorporated-authorities) and [§3](#3-accepted-source-representations).
- **OAPI-P-02**: Parameter serialization follows the OAS `style`/`explode`/`allowReserved` rules and defaults, with `content`-form parameters serialized per their declared media type, per [§9.1](#91-input-mapping).
- **OAPI-P-03**: Input mapping supports the flat and exact routed source representations of §9.1; preserves independent same-named parameter and body declarations without exposing their HTTP identity in the operation contract; retains only the case-colliding-header refusal whose distinction the wire itself cannot express; carries explicitly dynamic objects and declaration-complex exact JSON bodies as one application value rather than flattening runtime or branch-dependent names; routes unmatched fields only where a flattened JSON object body supplies a destination; applies declaration-only body-shape resolution, required-input refusals, candidate election, and whole-body unwrapping; and refuses malformed or unroutable source values before dispatch.
- **OAPI-P-04**: A no-body invocation bypasses request-media selection and emits neither body nor `Content-Type`; a body-emitting invocation preserves the artifact's declared alternatives with no binding-specification preference, lets a configured concrete `requestMedia` select the most-specific matching exact or range declaration, and never instantiates a range or infers JSON without that choice. A required range-only body with no effective choice requests retryable `requestMedia` context before input consumption and performs zero dispatch; an optional range-only body may complete bodyless, but a supplied body with no prior choice refuses rather than requiring replay. A supplied unmatched, unsupported, or inadmissible choice and any other absence of a carriage candidate also refuse before dispatch. Exact JSON-family declarations serialize declaration-complex whole values without branch selection. Exact schema-omitted OAS 3.0 non-JSON declarations, OAS 3.0 raw-binary schemas, and OAS 3.1 opaque-body declarations use the canonical Base64 JSON boundary and emit exact decoded bytes; schema-omitted media ranges do not gain that lane. OAS 3.1 `contentEncoding` strings remain artifact-encoded wire text. Multipart observes the same edition distinction; dynamic member schemas resolve through exact, pattern, additional-property, and `allOf` declarations before form carriage. `Accept` advertises the normative concrete membership set and is omitted when that set is empty rather than inventing a media type, per [§9.2](#92-request-and-response-media).
- **OAPI-P-05**: Server resolution uses the OAS effective server list: a sole member selects itself; multiple members require consumer selection; variable substitutions honor declared enums; a complete URL may replace the selected member's target without replacing its artifact semantics; unresolved or unselected targets refuse before dispatch, per [§9.3](#93-servers-and-the-target-url).
- **OAPI-P-06**: Response declaration lookup is exact status → matching range → `default`, independently of final-status 2xx classification; streaming capability is statically bounded by all success declarations, while an actual response's interaction and media are governed only by the Response Object selected for its final status. A non-empty body with no governing declaration or no matching concrete media type is a protocol error; SSE events are extracted per the WHATWG processing model, per [§8](#8-target-and-interaction).
- **OAPI-P-07**: The decode configuration point defaults to the governing-response header rule: empty bodies emit no value; non-empty bodies require one parameter-aware, most-specific concrete media match under OAPI-P-06 and then use the defined JSON, text, or artifact-authorized raw-byte lane, including the per-event text default for SSE, per [§9.2](#92-request-and-response-media) and [§9.4](#94-configuration-points). Exact schema-omitted OAS 3.0 non-JSON responses emit canonical Base64; schema-omitted media ranges do not gain that lane. Normalized content-map collisions and equal-specificity response ties refuse rather than selecting by source order.
- **OAPI-P-08**: The classify configuration point defaults to the 2xx rule, applied to the final status; redirect following is runtime policy, but any followed redirect preserves the bound operation's method and complete body, and a method-rewriting redirect remains the final response, per [§9.4](#94-configuration-points).
- **OAPI-P-09**: Credentials apply to the wire per scheme as [§9.6](#96-security-declarations-credentials-and-channel-assembly) pins; any one complete artifact-declared security alternative may be selected, incomplete fragments from different alternatives never manufacture satisfaction; unpinned schemes are surfaced, never silently skipped; security metadata is never written into OBI documents.
- **OAPI-P-10**: Channel assembly merges non-colliding parameters and credentials deterministically; an effective header parameter cannot replace processor-owned target, length, or cookie assembly; pairwise credential collisions, credential/effective-parameter collisions, and header-credential/processor-owned-field collisions make the selected security alternative unusable and refuse before dispatch unless another complete declared alternative is selected, per [§9.6](#96-security-declarations-credentials-and-channel-assembly).

Conformance fixtures keyed to these identifiers are published with the project's conformance corpus. Deterministic _generation_ of OBI documents from OpenAPI artifacts (operation-key derivation, output-schema selection, schema translation) is a synthesis concern outside this specification; the project's interface-synthesizer and reference-tool documentation record those conventions.
